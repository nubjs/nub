# Deprecated — NOT canonical, do not build on this

Everything here is superseded. It is kept because it may hold information worth recovering, and
it lives in a directory named `deprecated` so it stops turning up in a grep and reading as
current. **If you find yourself citing something in here as how nub works, you have the wrong
file.**

## The criterion

The build-jail catalog is REGENERATED BY MEASUREMENT. Curated per-package lists — someone sitting
down and writing out the packages they happened to know about — are the thing it replaces. They
do not scale to an ecosystem and they are silently wrong in both directions: a package missing
from the list breaks with no error, and a stale entry is dead weight nobody notices.

**But not every hardcoded list is one of these.** The test is what a WRONG ENTRY COSTS:

- **Costs a broken package → deprecate it.** The list is guessing at behaviour, and guessing is
  what measurement is for.
- **Costs latency, or names a real tool → keep it.** `is_likely_native_build` in
  `aube/commands/install/critical_path.rs` orders prefetching and says so itself: *"False
  positives are also fine (the package fetches earlier, no harm)."* Nothing breaks when it is
  wrong. `node_gyp_bootstrap.rs` naming `node-gyp` is not a guess at all.

## Why `NUB_PROJECT_CONTEXT_EJECT` exists at all

Not because those 21 packages are special. nub's default linker puts packages in a GLOBAL store
and symlinks them into the project — MEASURED:
`node_modules/.store/@puppeteer+browsers@3.0.6 -> ~/.cache/nub/pm/store/@puppeteer+browsers@3.0.6-<hash>`.
A lifecycle script that walks UP looking for the project root therefore lands in `~/.cache/`,
finds nothing, and exits 0. The list copies those packages into the project so the walk works.

It is a patch for a LAYOUT decision, not for package behaviour, which is why no grant can fix
the underlying problem: a script that cannot find the project will not write to it however much
permission it holds.
