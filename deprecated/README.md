# Deprecated — NOT canonical, do not build on this

Kept because it may hold information worth recovering, and parked in a directory named
`deprecated` so it stops turning up in a grep and reading as current. **If you find yourself
citing something in here as how nub works, you have the wrong file.**

## THE RULE: no package lists in source. Any of them.

A list of package names hardcoded in a `.rs` file is data wearing code's clothing. It does not
matter whether the list is a guess or a fact, whether a wrong entry breaks a package or merely
costs a few hundred milliseconds, or whether the mechanism reading it is general. **Data lives in
the catalog. Rust holds mechanism.**

An earlier version of this file proposed a softer rule — deprecate lists whose wrong entries
break packages, keep the ones that only cost latency. That line is wrong. It leaves curated lists
in the source, where the next reader finds them and assumes they are canonical, and where nobody
notices they have gone stale because nothing fails loudly.

**Most of these should not become catalog entries either — they should be DERIVED.** "Is this a
native build?" is not a fact anyone needs to write down: a package whose install script invokes
`node-gyp`, `prebuild-install` or `node-gyp-build` IS one, and that is readable from the manifest
the generator already parses. A list is what you keep when you have not worked out the rule.

## Inventory

| list | location | what it encodes | where it belongs |
| --- | --- | --- | --- |
| `NUB_PROJECT_CONTEXT_EJECT`, 21 names | `crates/nub-cli/src/pm_engine/phantom_closure.rs:116` | which packages read the project during install | a general placement rule — UNDER DESIGN |
| `is_likely_native_build`, 15 names + 8 scope prefixes | `vendor/aube/crates/aube/src/commands/install/critical_path.rs:16` | which packages build natively, for prefetch ordering | DERIVE from the manifest: an install script invoking node-gyp / prebuild-install / node-gyp-build |
| `DEFAULT_TRUST_POLICY_EXCLUDES`, 17 names | `vendor/aube/crates/aube-resolver/src/trust.rs:285` | packages EXEMPTED from the trust-downgrade check because they published without attestation | its own dynamic surface — this is RESOLVER policy, not jail policy, so the build-jail catalog is the wrong home. `trustPolicyExclude` already exists as a user config field (mirrors pnpm); only the DEFAULTS are compiled in |
| v1 catalog (`packageGrants`, `packageNetwork`, `fullDisk`, `projectReads`/`projectWrites`, `siblingDirs`, `dependencyDirs`, `homePaths`) | `crates/nub-sandbox/src/catalog.rs`, 35 refs | every grant | the v2 catalog, generated by `tests/build-jail-search/` |

Earlier v1 catalog data and harness scripts are archived out of the tree entirely at
`catalog-legacy/` (gitignored).

**Highest consequence of the three.** A wrong entry in the trust excludes does not break a
package — it silently SKIPS A SUPPLY-CHAIN CHECK for it. A stale exemption is a hole nobody
notices, which is exactly the failure mode a compiled-in list produces.

**Checked and NOT a list:** `LEFTHOOK_READS` (`nub-sandbox/src/compiler/curated.rs:289`) is
`#[cfg(test)]` — test-only, never compiled into a shipping binary. An earlier revision of this
file wrongly inventoried it as live code; the `#[cfg(test)]` sits on the line directly above the
declaration.

## Why `NUB_PROJECT_CONTEXT_EJECT` exists at all

Not because those 21 packages are special. nub's default linker puts packages in a GLOBAL store
and symlinks them into the project — MEASURED:
`node_modules/.store/@puppeteer+browsers@3.0.6 -> ~/.cache/nub/pm/store/@puppeteer+browsers@3.0.6-<hash>`.
A lifecycle script that walks UP looking for the project root therefore lands in `~/.cache/`,
finds nothing, and exits 0 — a silent no-op.

It patches a LAYOUT decision, not package behaviour, which is why no grant can fix the underlying
problem: a script that cannot find the project will not write to it however much permission it
holds.
