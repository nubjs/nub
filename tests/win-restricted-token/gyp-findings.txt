#   integrity=S-1-16-8192 (Medium)   elevated=False   in_admins=False
#   privileges(2)=SeChangeNotifyPrivilege SeIncreaseWorkingSetPrivilege
#   -> no SeAssignPrimaryToken, no SeIncreaseQuota, no SeImpersonate.
# `probe` is a local account in BUILTIN\Users only. Reached by SSH-ing AS probe,
# so the token is sshd's, not a re-derived one.

# SETUP FACTS (measured; cost time, recorded so the next run skips them)
# - windows-2022's guest agent DOES wire nothing useful for ssh either; the
#   startup script must install OpenSSH.Server, start sshd, and write the key.
#   Appending to sshd_config lands the directive INSIDE the trailing
#   `Match Group administrators` block -> sshd will not start. Insert before the
#   first Match line. (Same trap as the windows-2025 run.)
# - MEASURED: `Start-Process -Credential` to cross into another local account
#   from an SSH session does NOT work here — the child logon succeeds (the
#   profile is created) but the process dies at init producing zero output, and
#   PowerShell reports an EMPTY $p.ExitCode. Cross-user window-station attachment
#   in the services session, the same class of problem AppContainer hits.
#   REMEDY, simpler than the wrapper: put the pubkey in the probe account's own
#   authorized_keys and SSH AS probe. sshd sets the station up correctly.
# - MEASURED: a scheduled task cannot create the probe profile either —
#   BUILTIN\Users holds no SeBatchLogonRight by default, so `schtasks /run` as a
#   standard user fails. The first interactive logon is what creates the profile.
# - MEASURED: `node-gyp` is NOT on PATH from a bare shell. npm puts its own shim
#   dir C:\node\node_modules\npm\bin\node-gyp-bin on PATH for lifecycle scripts;
#   without it EVERY from-source package fails "'node-gyp' is not recognized",
#   which reads exactly like a jail failure and is not one.
# - HARNESS BUG THE SMOKE ARM CAUGHT: a PowerShell function returns its whole
#   PIPELINE, so `Layout` returning $d actually returned npm's output lines too;
#   the first was used as a directory ("A drive with the name 'npm notice To
#   update run' does not exist"). Caught only because the il=none smoke arm
#   failed. Functions here must emit nothing.

VERDICT: FROM-SOURCE NATIVE COMPILATION WORKS UNDER THE LOW-IL
JAIL. It needs ONE grant beyond the four already known.
================================================================
⭐ GRANT #5 — the node-gyp DEVDIR / header cache. MEASURED, three arms, control
included. On node-gyp >= 9 this is %LOCALAPPDATA%\node-gyp (verified: it holds
3,330 entries after a cold fetch, while %USERPROFILE%\.node-gyp stays at 0
entries — the older <=8 location is dead here, but grant both to be version-
agnostic). Load-bearing ONLY when the header cache is COLD, which a fresh
machine always is:
  D_cold_none      il=none, cold   rc=0  174,080 B   <- rules out "cold is the problem"
  D_cold_low_all   il=low,  cold   rc=0  174,080 B   <- headers fetched over HTTPS INSIDE the jail
  D_cold_low_no_devdir              rc=1  absent
    gyp ERR! stack Error: EPERM: operation not permitted, mkdir
      'C:\Users\probe\AppData\Local\node-gyp\Cache'
    at async go (node-gyp/lib/install.js:161:23)
  C_no_nodegyp     il=low,  WARM   rc=0  174,080 B   <- warm headers are READ-only, no grant needed
D_cold_low_all's headers came over the wire from nodejs.org at low IL (95 s vs
17 s warm), so this is also a second independent confirmation that HTTPS works
inside the jail — by download latency and a byte-identical artifact, not by rc.

⭐ THE TEMP GRANT IS LOAD-BEARING IN A NEW AND ACTIVELY MISLEADING WAY. Withhold
it and node-gyp does not report a permission error — it reports that MSVC is not
installed:
    gyp ERR! find VS could not use PowerShell to find Visual Studio 2017 or newer
    gyp ERR! find VS Failure details: undefined
node-gyp's find-visualstudio shells out to PowerShell `Add-Type`, which COMPILES
a C# assembly into %TEMP%. No writable TEMP -> no VS detection -> "could not find
a version of Visual Studio 2017 or newer". cpu-features' own buildcheck.js fails
the same way with `Error: Unable to detect compiler type`. Anyone debugging this
in the field will go hunting for a broken toolchain. Worth an error-message
mapping in nub.

✅ NO SIXTH GRANT IS NEEDED. Everything else MSBuild and the VS toolchain touch
is either already writable via the five, or not needed at all. Specifically
measured DENIED under the jail while all four compiles still succeeded:
  %LOCALAPPDATA%\Microsoft\VisualStudio    DENY - not needed
  %LOCALAPPDATA%\Microsoft\Windows\PowerShell DENY - not needed (PowerShell's
                                            ModuleAnalysisCache write is
                                            best-effort; find-visualstudio still
                                            works, given TEMP)
  %USERPROFILE%\.vs                        DENY - not needed
  %APPDATA%\npm-cache                      DENY - not needed (nub points
                                            npm_config_cache at its own granted cache)
  C:\BuildTools (the VS install tree)      DENY *even at il=none* - a standard
                                            user cannot write it with no jail at
                                            all, so READ-ONLY genuinely suffices
                                            and the jail need not arrange it.
  HKCU write                               DENY
Also scanned every successful low-IL build log for a SUPPRESSED failure
(`denied|EPERM|EACCES|warning MSB|MSB4|cannot open|failed to write`): zero hits.
The builds are not quietly degrading around a refused write.

⭐ HKCU IS NOT A PROBLEM FOR THE COMPILE PATH. This was the open worry, because
HKCU has no file-label remedy. MSBuild, cl.exe, link.exe and the VS toolchain
perform NO load-bearing HKCU write: all four packages compile to byte-identical
artifacts with HKCU writes denied. Verified as a one-variable check rather than
inferred — the probe key was deleted, the low-IL arm re-run, `reg add HKCU\...`
returned DENY, and the key was still absent afterwards. The §5e HKCU residual
therefore does NOT extend to from-source compilation.

⚠️ THE PM CACHE GRANT IS NOT NEEDED FOR THE FROM-SOURCE PATH (C_no_cache passes
with byte-identical artifacts). It remains required for the PREBUILT-DOWNLOAD
path, which is what §5e measured. Both grants are needed overall because a real
install mixes the two; neither subsumes the other.
