Nub runs your code on stock Node and provisions the version your project pins. Pin a version, run a file, and the matching Node is downloaded and cached with no second command.

```console
$ echo {{NODE_VERSION}} > .node-version
$ nub index.ts
Using Node.js {{NODE_VERSION}} (resolved from .node-version)
Installing from nodejs.org... (24 MB)
Installed in 8.0s
# ...your script runs, on exactly the Node you pinned
```

The `nub node` subcommands cover the explicit steps: warming the cache, listing and removing versions, and writing a pin.

## Automatic provisioning

A pin can be a `.node-version`, a `.nvmrc`, or an `engines.node` range in `package.json`. When that Node is already on your machine, Nub uses it. Otherwise Nub downloads the stock build from nodejs.org, verifies its SHA-256, and caches it under `~/.cache/nub/node`.

With no pin, Nub uses the `node` on your `PATH`. On a machine with no Node at all, it provisions the latest release, reusing the newest cached version if there is one:

```console
$ nub app.ts          # fresh machine: no pin, no Node on PATH
Using Node.js {{NODE_VERSION}} (resolved from latest)
Installing from nodejs.org... (30 MB)
Installed in 5.1s
# ...your script runs
```

Each unpinned run there uses the latest release; [`nub node pin`](#nub-node-pin) makes it reproducible.

## Version precedence

Nub first picks a version from the nearest pin, and then finds a binary that satisfies it.

### Pin sources

Nub walks up from your working directory to the nearest pin. Highest precedence first:

1. **`NODE_EXECUTABLE`** — an absolute path to a Node binary
2. **`nodeExecutable`** in `nub.jsonc` — a path, or a command that prints one
3. **`package.json#/devEngines/runtime`** — the `node` entry
4. **`.node-version`**
5. **`.nvmrc`**
6. **`.tool-versions`** — the asdf/mise file
7. **`package.json#/engines/node`**
8. **No pin** — the `node` on `PATH`, else the latest release

The first two name a binary and skip version resolution entirely; see [`nodeExecutable`](/docs/config#nodeexecutable). Both `package.json` fields are read from the workspace root when there is one, so a monorepo pins its Node once. Dependency build scripts use that root pin during an install, while `nub run` inside a member uses the member's own pin.

Both fields take the `engines.node` grammar, so either can hold a range or an exact version:

```json title="package.json"
{
  "devEngines": { "runtime": { "name": "node", "version": "22.15.0" } },
  "engines": { "node": ">=20 <23" }
}
```

An exact version pins the patch too, and a range resolves to the newest published release that satisfies it. The `onFail` policy does not apply to the `node` entry. A `devEngines.runtime` that names only another runtime, such as Bun, stops the run unless its `onFail` is `"warn"` or `"ignore"`.

<Callout>
Read the [full docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#devengines) for the `devEngines` and `engines` fields on docs.npmjs.com.
</Callout>

### Binary sources

Once a version is pinned, Nub looks for a binary in this order:

1. **The `node` on `PATH`**, when its version satisfies the pin, so `fnm`, Volta, and `mise` auto-switching is honored
2. **Nub's download store** (`~/.cache/nub/node/<version>/`)
3. **An `nvm`-installed version**
4. **A download from nodejs.org**, SHA-256 verified and cached

## `nub node install`

Provision a version into the cache now, instead of on the next run. Use it to warm a CI cache (the [GitHub Action](/docs/deployment/github-action) does this) or to fetch a Node before going offline.

```bash
nub node install {{NODE_MAJOR}}          # newest {{NODE_MAJOR}}.x
nub node install 22.13       # newest 22.13.x
nub node install 20.11.0     # an exact version
nub node install lts         # newest LTS line; also lts/<codename>
nub node install latest      # newest release
nub node install 20 22       # several at once
nub node install             # the project's pin
```

A version already in the cache is a no-op. A version already on your `PATH`, from a system install or another version manager, is skipped:

```console
$ nub node install {{NODE_VERSION}}
Node {{NODE_VERSION}} is already available on PATH — skipped
```

## `nub node ls`

List the versions in Nub's cache, newest first, with the one your current directory resolves to marked. Versions installed by `nvm`, `fnm`, or the system are not listed.

```console
$ nub node ls
→ {{NODE_VERSION}}
  22.13.0
  20.11.0
```

## `nub node uninstall`

Delete a version from Nub's cache. Nub refuses to remove the version your current directory resolves to.

```console
$ nub node uninstall 20.11.0
Removed Node 20.11.0 from the cache
```

## `nub node pin`

Write a `.node-version` so every later `nub` in the project uses that version.

```console
$ nub node pin {{NODE_MAJOR}}
pinned Node {{NODE_MAJOR}} → /path/to/project/.node-version
```

- **Location** — the project root (the nearest `package.json` directory), or the workspace root in a monorepo, wherever you run it from.
- **Existing file** — a project with a `.nvmrc` and no `.node-version` gets its `.nvmrc` updated in place.
- **Spec** — written verbatim, aliases like `lts` included, with no network access.

Other version managers, including `nvm`, `fnm`, Volta, and `asdf`, read `.node-version` too.

## `nub node which`

Print the Node that runs in the current directory. The path goes to stdout and the resolution source to stderr, so a captured value is only the path.

```console
$ nub node which
/Users/you/.nvm/versions/node/v{{NODE_VERSION}}/bin/node
» resolved from .node-version ({{NODE_VERSION}})
```

An alias pin such as `lts/*` resolves against the release index from the last `nub node install`, so `which` and every run work offline once the version is cached. Bare `nub node` prints a status block with the version, path, and resolution source.

## `nub node shim`

Make `node` itself resolve through Nub, so a machine with no Node installed can run `node file.js`. After installing Nub, one command sets it up:

```console
$ nub node shim
node shim in /Users/you/.local/share/nub/node-shim (created)
  `node` now resolves through nub (version management only — no
  augmentation; run `nub` for that)
  added /Users/you/.local/share/nub/node-shim to PATH in /Users/you/.zshrc
  restart your shell, or run: source /Users/you/.zshrc
```

The shimmed `node` resolves and provisions the version by the [precedence above](#version-precedence) and adds nothing else. So `node app.ts` type-strips as stock Node does, while `nub app.ts` transpiles it.

The link lives in `$XDG_DATA_HOME/nub/node-shim`, or `~/.local/share/nub/node-shim` when that variable is unset. That directory goes first on your PATH, so a Node you install later is shadowed until you unshim. Re-run `nub node shim` after `nub upgrade`.

```console
$ nub node unshim
removed /Users/you/.local/share/nub/node-shim
  PATH: removed the node-shim block from /Users/you/.zshrc
```

## Mirrors and proxies

Node downloads use `HTTP(S)_PROXY`, `NO_PROXY`, and the system trust store. To fetch Node from an internal mirror, set the `NODEJS_ORG_MIRROR` environment variable or pnpm's `.npmrc` key, in a project or user file:

```ini title=".npmrc"
node-mirror:release=https://artifactory.corp.example/node/
```

The environment variable wins over the `.npmrc` key. On Alpine, point the mirror at one carrying the `unofficial-builds` layout for musl.
