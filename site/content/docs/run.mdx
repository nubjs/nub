---
title: Script runner
description: A drop-in for pnpm run and npm run, with pnpm's workspace flags and npm's lifecycle hooks.
---

Pass a script name from `package.json` to run it:

```bash
nub run build
nub run test --watch            # trailing arguments go to the script
nub run -r build                # every workspace package
nub run --filter @org/api dev   # one workspace package
nub run                         # no name: list the scripts
```

The runner takes pnpm's `run` flags with the same spelling and semantics. Package management stays with whatever the project already uses, whether that is pnpm, npm, Yarn, or Bun.

Dispatch happens in Rust with no Node bootstrap, so the runner adds a few milliseconds before the script's first byte:

Scripts always run through `nub run`. A bare `nub build` does not fall through to a script; it fails with a hint to run `nub run build`. See [Running files](/docs/runtime) for what `nub <file>` does.

## Argument forwarding

Arguments after the script name go to the script. The `--` separator that `npm run` requires is optional.

```bash
nub run test --watch          # forwards --watch to the test script
nub run test -- --watch       # same result
```

Nub's own flags go before the script name:

```bash
nub run --silent build        # Nub's --silent: no preamble
nub run build --silent        # forwarded to the build script
```

## Lifecycle hooks

Nub runs `pre<script>` and `post<script>` hooks automatically, matching `npm run`:

```json title="package.json"
{
  "scripts": {
    "prebuild": "rimraf dist",
    "build": "tsc -p .",
    "postbuild": "cp README.md dist/"
  }
}
```

```bash
nub run build                   # prebuild, then build, then postbuild
nub run --ignore-scripts build  # build only
```

## Multiple scripts

A `/regex/` in place of a script name runs every script whose name matches, as `pnpm run` does. Matching scripts run concurrently, up to `min(4, CPU count)` at a time, with each line prefixed by its script name.

```bash
# build:js, build:css, … concurrently
nub run "/^build:/"
# one at a time, in package.json order
nub run --workspace-concurrency 1 "/^build:/"
```

The selector must be a slash-delimited regular expression. A plain `build:*` is a literal script name, not a glob.

Equivalents for `npm-run-all` / `npm-run-all2`:

| npm-run-all | Nub |
|---|---|
| `run-p build:js build:css` | `nub run "/^build:(js\|css)$/"` |
| `run-p "build:*"` | `nub run "/^build:/"` |
| `run-s "build:*"` | `nub run --workspace-concurrency 1 "/^build:/"` |

<Callout>
Read the [full docs](https://pnpm.io/cli/run#running-multiple-scripts) for pnpm's regex selector on pnpm.io.
</Callout>

## Workspaces

Nub reads the workspace from the `"workspaces"` field in `package.json` (npm, Yarn, Bun) or from `pnpm-workspace.yaml` (pnpm). It walks up from the current directory to find the root, so these commands work anywhere inside the monorepo.

### `-r, --recursive`

Run the script in every workspace package. Packages run in topological order: a package's dependencies run before it does.

```bash
nub run -r build              # every workspace package
nub run --recursive test      # long form
nub run --workspaces lint     # npm-style alias
nub run -r --if-present test  # skip members without the script
```

### `--filter`

The `--filter` flag (or `-F`) takes pnpm's filter grammar. Select by exact name, scope glob, name wildcard, or path glob:

```bash
nub run --filter @org/api dev          # one package by name
nub run --filter "@org/*" build        # every package in a scope
nub run --filter "*-utils" test        # name wildcard
nub run --filter "./packages/*" lint   # path glob
nub run --filter '!@org/legacy' build  # exclude a package
nub run --filter @org/api --filter @org/web build  # union of both
```

The `...` forms walk the dependency graph:

```bash
nub run --filter "@org/web..." build   # @org/web + its dependencies
nub run --filter "...@org/web" build   # @org/web + its dependents
nub run --filter "@org/web^..." build  # @org/web's dependencies only
nub run --filter "...^@org/web" build  # @org/web's dependents only
```

A `[ref]` selects packages changed since a git ref, the common CI pattern for testing only what moved:

```bash
nub run --filter "[main]" test           # changed since main
nub run --filter "[HEAD~1]" build        # changed since HEAD~1
# changed packages and their dependents
nub run --filter "...[origin/main]" test
```

<Callout>
Read the [full docs](https://pnpm.io/filtering) for the filter grammar on pnpm.io.
</Callout>

### `-w, --workspace-root`

The `-w` flag targets only the root package, wherever you run it from. It is pnpm's boolean root selector, not npm's member selector.

```bash
nub run -w lint                          # "lint" at the workspace root
nub run -r --include-workspace-root lint # all members plus the root
# npm-style member selection; repeatable
nub run --workspace @org/api build
```

### `--parallel`, `--sequential`

A workspace run executes up to `min(4, CPU count)` packages at a time, in topological order. These flags change that:

```bash
nub run -r --workspace-concurrency 8 build   # cap at 8 concurrent scripts
nub run -r --parallel dev                    # all at once, no order or cap
nub run -r --sequential migrate              # one at a time, no order
```

Use `--parallel` for long-running dev servers and `--sequential` for scripts that must not overlap.

### `--no-bail`

A workspace run stops at the first package that fails. The `--no-bail` flag runs every package and reports failures at the end.

```bash
nub run -r --no-bail test
```

### `--resume-from`

Restart a failed topological run from one package, skipping its topological predecessors:

```bash
nub run -r --resume-from @org/api build
```

## Output

These flags control how a workspace run lays out each package's output.

### `--stream`, `--aggregate-output`

On a terminal, Nub streams interleaved output and prefixes each line with the package directory and script name (`packages/api build: <line>`), as `pnpm -r` does. In CI or when output is piped, it buffers each package's output and flushes it when the package finishes.

```bash
nub run -r --stream build            # force interleaved live output
nub run -r --aggregate-output build  # force per-package buffering
```

### `--reporter`

The `ndjson` reporter prints one JSON event per line, for CI. Nub has no `--report-summary`; use `--reporter ndjson` for machine-readable per-package results.

```bash
nub run -r --reporter ndjson build
```

The `--reporter-hide-prefix` flag drops the per-line label, so a CI annotation matcher reads the script's own `error: file:line` output. Nub's own framing lines keep their label.

```bash
nub run -r --stream --reporter-hide-prefix build
```

### `--silent`

The `--silent` flag (or `-s`) drops Nub's `$ <command>` preamble. The script's own output is unchanged.

```bash
nub run --silent build
```

### `--color`

Prefixed output is piped, so most tools switch their own color off. With `--color`, scripts keep their colors:

```bash
nub run -r --parallel --color=always dev  # scripts keep their colors
nub run -r --no-color build               # plain text from Nub and scripts
```

Nub passes the choice to scripts as `FORCE_COLOR`: `1` for `--color=always` and `0` for `--no-color`, matching pnpm. Without the flag, the usual environment variables decide:

```bash
NO_COLOR=1 nub run -r build      # off, whatever the terminal says
FORCE_COLOR=1 nub run -r build   # on, even when the output is piped
```

## Environment

Scripts get the npm-compatible environment, so tools that read `npm_*` variables behave as they do under `npm run`. The `node_modules/.bin` chain is on `PATH`, so installed CLIs run by bare name.

```json title="package.json"
{
  "scripts": {
    "build": "tsc && echo \"built $npm_package_name@$npm_package_version\""
  }
}
```

The injected set:

```bash
npm_lifecycle_event
npm_lifecycle_script
npm_execpath
npm_node_execpath
npm_command
npm_config_user_agent
npm_package_name
npm_package_version
npm_package_json
npm_package_config_*       # per-package keys from package.json#config
npm_config_registry        # the resolved registry from the .npmrc chain
npm_config_node_gyp        # path to a runnable node-gyp, for native builds
INIT_CWD                   # the directory you invoked `nub run` from
```

<Callout>
Read the [full docs](https://docs.npmjs.com/cli/v11/using-npm/scripts#environment) for npm's script environment on docs.npmjs.com.
</Callout>

## The script shell

Nub runs every script body through a POSIX `sh`, so one script behaves the same on macOS, Linux, and Windows. Operators such as `&&`, pipes, `$(…)`, `${PORT:-3000}`, and inline `NODE_ENV=production` assignments work everywhere.

On macOS and Linux the shell is the system `/bin/sh`. Windows has no POSIX shell, so Nub ships busybox next to its binary and uses it instead of `cmd.exe`. Dependency install scripts run through the same shell during `nub install`.

The shell is POSIX `sh`, not bash. Bash-only syntax such as `[[ … ]]`, arrays, and `${VAR^^}` is not guaranteed. That is the same contract `npm` gives, whose `sh -c` is dash on Debian and Ubuntu.

To pin a different shell, set `script-shell` in `.npmrc`, or pass `--script-shell` for one run:

```ini title=".npmrc"
script-shell = /bin/bash
```

```bash
nub run --script-shell /bin/bash build
```

<Callout>
Read the [full docs](https://pnpm.io/settings/other#scriptshell) for pnpm's `scriptShell` setting on pnpm.io.
</Callout>

## Dependency freshness

Before a script runs, Nub checks `node_modules` against `package.json`. A missing dependency, or one installed outside its declared range, prints a warning and the script still runs:

```
nub: dependencies may be out of date (`chalk` is not installed).
Run `nub install`.
```

The check reads a tree from any installer, and it also runs before `nub <file>`, `nub exec`, and `nubx`. Nub does not install anything here; run `nub install` when the warning appears.

Set the policy with `verify-deps-before-run` in `.npmrc`:

```ini title=".npmrc"
verify-deps-before-run = warn
```

| Value | Behavior |
| --- | --- |
| `warn` | Warn, then run. The default. |
| `error` | Print the message and refuse to run. |
| `off` | Skip the check. |

The pnpm values `install` and `prompt` act as `warn`. A project [`nub.jsonc`](/docs/config) sets the same policy under [`verifyDeps`](/docs/config#verifydeps), where `off` is spelled `false`:

```jsonc title="nub.jsonc"
{
  // ...
  "verifyDeps": "error"  // stop rather than run against a stale tree
}
```

To override the files:

```bash
NUB_VERIFY_DEPS=off nub run build   # for this shell
nub run --no-check build            # for one run; --no-install is an alias
```

A tree Nub installed under a different Node major is reinstalled before the run, because native addons are built per Node major. The `off` policy disables this too.

```
nub: dependencies were installed for Node 22, this run uses Node 26.
Reinstalling — native addons are built per Node major.
```

<Callout>
Read the [full docs](https://pnpm.io/settings/build#verifydepsbeforerun) for pnpm's `verifyDepsBeforeRun` setting on pnpm.io.
</Callout>

## Undeclared dependencies

Nub warns about a phantom dependency: a package your source imports without declaring it, which resolves only because a transitive dependency was hoisted into `node_modules`. It works under a flat npm or Yarn install and breaks under an isolated one.

```
nub: src/index.ts imports `ansi-styles`, which isn't in package.json.
Run `nub add ansi-styles` (WARN_PHANTOM_DEP).
```

The warning never changes the exit code. Turn it off with `phantom-check` in `.npmrc`, or with `NUB_PHANTOM_CHECK=off` for one shell:

```ini title=".npmrc"
phantom-check = off
```

## `--node`

During a `nub run`, `node` resolves to Nub, so a subprocess that spawns `node` gets Nub's augmentation too. That covers a `#!/usr/bin/env node` shebang and `child_process.spawn("node", …)`. The `--node` flag turns augmentation off for one invocation; see [the runtime overview](/docs/runtime#--node) for the full contract.

```bash
nub run --node test
```

Script lookup, workspace selection, `npm_*` variables, `node_modules/.bin` on `PATH`, and lifecycle hooks still apply. Use it when a script expects plain Node, or to rule Nub out when bisecting a bug.
