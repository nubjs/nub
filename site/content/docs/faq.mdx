## Basics

The [introduction](/docs) shows Nub in use, and these answers cover what it is.

### What is Nub?

Nub is a Rust CLI that runs your files, scripts, and CLIs, installs dependencies, and manages Node versions. It runs on stock Node and augments it through Node's public extension surfaces.

```console
$ npm install -g @nubjs/nub
$ nub index.ts             # run a TypeScript file
$ nub run dev              # run a package.json script
$ nubx prisma generate     # run a CLI from node_modules/.bin
```

### Is Nub a replacement for Node?

No. Nub is not a new runtime or a fork of Node. It patches no Node source, ships no custom Node binary, and embeds no `libnode`.

When `nub index.ts` runs, the process is a stock `node` binary. Nub spawns it with a load hook for TypeScript, JSX, and data files, plus a preload for polyfills. See [How does it work?](#how-does-it-work)

### How is it different from plain `node`?

Running `nub <file>` takes the same arguments and flags as `node <file>`, and adds:

- Full TypeScript, including `enum`, `namespace`, parameter properties, and decorators
- The `paths`, `baseUrl`, `extends`, and `jsx` settings from `tsconfig.json`
- JSX and TSX files
- Automatic `.env` loading
- YAML, TOML, JSON5, JSONC, and text imports
- Polyfills and unflagged experimental APIs, per Node version

See [Runtime](/docs/runtime) for each one.

### What npm packages can I stop using once I install Nub?

Nub replaces these directly:

```text
dotenv
cross-env
tsx, ts-node
nodemon
tsconfig-paths
npx                 # → nubx / nub exec
nvm, fnm            # the pin file alone provisions the right Node
corepack            # → nub pm
the PM CLI itself   # nub install / nub run, against your existing lockfile
```

Modern Node already replaces a second set, which you inherit by running on a current Node:

```text
node-fetch, cross-fetch, whatwg-fetch   # native fetch since 18
abort-controller                        # native since 15
uuid (v4 case)                          # crypto.randomUUID since 14.17
rimraf                                  # fs.rmSync recursive+force, 14.14
mkdirp                                  # fs.mkdirSync recursive, 10.12
glob, globby (basic cases)              # fs.glob since 22
form-data                               # native FormData since 18
# native WebSocket since 22.0, unflagged down to 20.10
ws client
```

### Is it faster than Node.js?

No. Your code runs in Node, so execution speed is Node's. The CLI is faster, because a native binary skips the Node startup that `pnpm run` and `npx` pay to look up a script:

- Running a script with `nub run` is 24× faster than `pnpm run` on cold start.
- Running a bin with `nubx` is 19× faster than `npx` on cold start.

Transpiled output is cached on disk, so only the first run of a file transpiles it.

### How do I install Nub?

```bash
npm install -g @nubjs/nub
```

Homebrew, mise, the install script, the Docker image, the GitHub Action, upgrades, and canary builds are covered under [Install](/docs#install).

## Compatibility

The [runtime overview](/docs/runtime#supported-versions-and-tiers) has the full table of Node versions and tiers.

### Will my existing Node code work on Nub?

Yes. The process is stock Node, so every `node:` core module and every package behaves as it does on Node.

<Callout title="The contract">
Code targeting Node runs on Nub byte-for-byte. Any divergence is a bug.
</Callout>

### What about CommonJS / `require()`?

Yes. CommonJS, `require()`, `require.cache`, and `module.exports` all run unchanged. Nub's load hook transpiles TypeScript and JSX for `require()` as well as `import`.

### What about native (N-API) addons?

Yes. Addons compile against Node's N-API ABI and load on the stock Node binary as they do on plain Node. Building one from source under the default install layout has one upstream caveat; see [GYP-based native builds](/docs/install/virtual-store#gyp-based-native-builds).

### What Node versions does it support?

- **Augmented runs** need Node 18.19+, the floor for the loader-hook API Nub uses.
- **Compatibility mode** (the [`--node` flag](#whats-the---node-flag)) is best-effort on any Node version.

On Node older than 18.19, an augmented command fails with an error naming the floor and compatibility mode. See [supported versions](/docs/runtime#supported-versions-and-tiers) for the tiers above the floor.

### Does it work on Linux / macOS / Windows?

Yes: macOS (arm64, x64), Linux (x64, arm64), and Windows (x64, arm64).

## Package management

The [package manager](/docs/install) page covers the install commands, and the [package meta-manager](/docs/pm) page covers how Nub picks the tool a project pins.

### Does it replace my package manager?

It can. Nub's installer, powered by the embedded aube engine, takes pnpm's CLI grammar and writes back the lockfile format your project already uses:

| Lockfile | Behavior |
| --- | --- |
| `pnpm-lock.yaml` | Round-trips in place |
| `package-lock.json` | Round-trips in place |
| `bun.lock` | Round-trips in place |
| `yarn.lock` | Read-only; an install that would rewrite it is refused, with the yarn command to run instead |

The installer is optional: `nub run` and `nubx` work with any package manager's `node_modules`. Yarn Plug'n'Play projects run through their `.pnp.cjs`; see [Yarn Plug'n'Play](/docs/runtime/resolution#yarn-plugnplay). To run the project's own package manager at its pinned version, see [pm](/docs/pm).

### Is it monorepo-friendly?

Yes. Nub reads workspaces from the `package.json` `"workspaces"` field and from `pnpm-workspace.yaml`, with pnpm's [`-r` and `--filter` syntax](https://pnpm.io/filtering):

```bash
nub run -r build                        # all workspace packages
nub run --filter @org/api dev           # one package by name
nub run --filter "./packages/*" test    # glob match
nub run --filter "@org/web..." build    # @org/web and its dependencies
```

Topological ordering, parallelism, and `--workspace-root` work as in pnpm. Nub skips the ~150 ms `pnpm` startup, which `pnpm -r run build` pays once per package.

### Does it replace `npx`?

Yes. The `nubx` command runs a bin from `node_modules/.bin`, walking up the directory tree, and fetches an uninstalled tool from the registry. Unlike `npx`, the first registry fetch of a tool prompts, and CI fails closed unless you pass `-y`. See [registry fetches](/docs/nubx#registry-fetches).

## Running code

Each answer links to the page that covers the feature in full.

### Does it replace `tsx` / `ts-node`?

Yes. Nub runs TypeScript directly, with the full TypeScript surface, your `tsconfig.json`, and stack traces that point at your `.ts` source. See [TypeScript](/docs/runtime/typescript).

### Why not Node's built-in TypeScript support?

Node 22.18+ runs `.ts` files by default, but only strips types. Anything beyond erasable annotations is rejected or ignored:

- Enums, namespaces, and parameter properties → syntax errors (Node 26 removed `--experimental-transform-types`, the flag that handled them)
- JSX and `emitDecoratorMetadata` → unsupported
- The `tsconfig.json` settings `paths`, `baseUrl`, `jsx`, `experimentalDecorators`, and `extends` → ignored ("intentionally unsupported," per the Node 26 docs)
- Extensionless `.ts` imports → unresolved, and no source maps

Nub transpiles each file through its native addon instead.

### What about `dotenv-cli`?

Nub loads your `.env` files into the environment before Node starts. Highest precedence first:

```text
.env.[mode].local
.env.local
.env.[mode]
.env
```

The mode comes from `APP_ENV`, not `NODE_ENV`, and `APP_ENV=test` skips `.env.local`. Automatic files expand `${VAR}` references; a file passed with `--env-file` loads verbatim, as on Node. See [Environment variables](/docs/runtime/env).

### Does it replace `nodemon` / `tsx watch`?

Yes. Run `nub watch script.ts` (or `nub --watch script.ts`) and Nub restarts the process when a file in the import graph, a `.env*` file, or `tsconfig.json` changes. It restarts rather than hot-swapping modules, so in-memory state does not survive. See [Watch mode](/docs/watch).

### What polyfills does it ship?

Nub polyfills modern globals such as `Temporal`, `URLPattern`, `Worker`, and `reportError` where the running Node lacks them. It also turns on experimental Node APIs such as `WebSocket`, `EventSource`, and `node:sqlite` on the versions that need a flag.

A native implementation always wins. See [Modern APIs](/docs/runtime/modern-apis) for every API and its version band.

### Does it have a dev server, test runner, or bundler?

No. Keep the tools your project already uses:

- **Dev server** — `nub run dev` runs your `dev` script, which starts Vite, Next.js, or whatever it names.
- **Test runner** — `node:test`, Vitest, and Jest run under Nub. Their workers inherit Nub's augmentation, so TypeScript test files run directly.
- **Bundler** — Nub's transpiler is for running code, not for building production artifacts.

### What's the `--node` flag?

The `--node` flag turns off Nub's runtime augmentation for one command: the transpile hook, `.env` loading, polyfills, unflagging, and the `PATH` shim. Nub's CLI work, such as workspace selection, scripts, and lifecycle hooks, keeps running.

```bash
node script.js               # your shell's plain Node
nub script.js                # Nub augmentation active
nub --node script.js         # the pinned Node, no augmentation
nub run --node test          # Nub's script runner, no augmentation
nubx --node prisma generate  # Nub's bin resolution, no augmentation
```

It helps when a script expects plain Node, when you bisect a suspected Nub bug, or when CI needs exact Node behavior with Nub's `--filter`. See [compatibility mode](/docs/runtime#--node).

## Comparisons

Bun and Deno are separate runtimes, and `node --run` is Node's own script runner. Nub runs your code on stock Node.

### How is it different from Bun?

Bun is a separate JavaScript runtime built on JavaScriptCore, with its own module loader, package manager, test runner, bundler, and `Bun.*` APIs. Code that uses those surfaces runs only on Bun:

```text
Bun.serve()
bun:sqlite
bun:test
the Bun global
@types/bun
```

Nub keeps application code on Node's public surface:

```text
no globalThis.nub
no nub:* module namespace
no @nub/* npm scope
no "nub" field in package.json
```

Each augmentation Nub applies also works on plain Node with the matching `module.register()` hook, `--import` preload, or npm addon. See [Migrating from Bun](/guides/bun-to-nub) for a map of `Bun.*` APIs to their Node replacements.

### How is it different from Deno?

Deno is a separate runtime built on V8, with its own permissions model, standard library, module resolution (URL imports, `jsr:` specifiers), and `Deno.*` APIs. Code that uses those surfaces runs only on Deno:

```text
Deno.serve()
Deno.env
Deno.readTextFile
```

Deno implements Node compatibility inside Deno. Nub runs on the Node binary itself, so a package that works on Node works on Nub.

### How is it different from `node --run`?

Node 22.0 added a built-in script runner, `node --run`. It is fast and deliberately minimal, without three things many projects rely on:

- Pre and post lifecycle hooks
- Workspaces, so no recursive or filtered runs across a monorepo
- The `npm_*` environment variables (`npm_package_*`, `npm_config_*`, `npm_lifecycle_event`) that many scripts read

The `nub run` command matches its speed in the [script-runner benchmark](https://github.com/nubjs/nub/tree/main/tests/bench/script-runner) and supports all three.

## Under the hood

The [runtime overview](/docs/runtime#how-it-works) has a shorter summary of the mechanism.

### How does it work?

When you run `nub script.ts`, the Rust binary:

1. Resolves the Node version your project pins and provisions it from nodejs.org if it is missing. With no pin, it uses the `node` on your `PATH`.
2. Reads the nearest `package.json`, `tsconfig.json`, and `.env*` files.
3. Spawns that Node with a preload and the experimental flags that Node version needs.
4. The preload installs Nub's load hook, which transpiles TypeScript, JSX, and data files through an `oxc` N-API addon. It installs polyfills where Node lacks an API, then runs your script.
5. Child processes inherit the same augmentation, such as a `node hello.js` inside a script or your test runner's workers.

### What Node features does it rely on?

Every augmentation Nub applies can be set up by hand on plain Node through public surfaces:

- **`module.registerHooks()`** (Node 22.15, April 2025) — synchronous loader hooks for the transpile-on-import path.
- **`module.register()`** (Node 20.6, August 2023) — programmatic loader registration without the `--loader` flag.
- **`--import` preload** (Node 19.0, October 2022, stable since 20.6) — setup code that runs before your entry, ESM-aware. It installs polyfills and the load hook.
- **`--require` preload** (Node 1.6, 2012) — the CommonJS preload, for CommonJS-only setups.
- **`NODE_OPTIONS` and V8 flag injection** — turns on `--experimental-*` flags Node already implements but keeps gated.
- **N-API addons** (stable since Node 8.6, October 2017) — the ABI-stable native-addon contract. The `oxc` transpiler ships as one.

### How does Nub resolve modules?

Nub's resolver implements Node's ESM resolution algorithm in Rust, on top of `oxc_resolver`. It adds `tsconfig.json` `paths` and extensionless `.ts` imports. See [Module resolution](/docs/runtime/resolution).

### Why hasn't anyone else done this?

The [Node extension surfaces](#what-node-features-does-it-rely-on) Nub builds on are recent: `module.register()` landed in 2023 and `module.registerHooks()` in April 2025. Deno and Bun predate them, so shipping integrated TypeScript then meant writing a runtime around it. Today it can sit on top of Node, which keeps Node's compatibility.

## Lock-in

Nub adds no APIs that your code imports or calls, so the code itself does not depend on Nub.

### Does Nub add anything to my `package.json` or `tsconfig.json`?

Nub writes only the standard `packageManager` and `devEngines.packageManager` fields: when you run `nub pm use` or `nub pm pin`, and on the first `nub install` in a project with no lockfile. Otherwise it reads the standard `package.json` fields the way Node, npm, pnpm, and yarn read them:

```text
scripts
workspaces
bin
type
exports
imports
engines.node
```

The fields that shape dependency resolution, such as `overrides`, `resolutions`, and `packageExtensions`, are standard too; see [resolution](/docs/install#resolution). Nub reads `tsconfig.json` the way `tsc` does and adds nothing to it.

### What if I want to stop using Nub?

Your code runs on plain Node unchanged, because Nub adds no APIs to it: no `nub` global, no `nub:*` imports, no `@nub/*` scope, and no `"nub"` field in `package.json`.

Removing Nub brings back what the previous toolchain needed:

- TypeScript files need a compile step or a loader such as tsx.
- Env files need `dotenv-cli` or `import "dotenv/config"`.
