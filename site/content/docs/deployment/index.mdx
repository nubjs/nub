title: Deployment
description: Deploy Nub projects through GitHub Actions, the official container image, or the installer and npm package used by managed builders.
---

Choose the deployment path your platform exposes:

1. **GitHub Actions** — use [`nubjs/setup-nub@v0`](/docs/deployment/github-action) to install Nub, provision the project's Node, and cache the store.
2. **Containers** — use [`ghcr.io/nubjs/nub`](/docs/deployment/docker) as the base image. It contains Node and Nub for `linux/amd64` and `linux/arm64`.
3. **Managed builders** — install Nub with the [installer](/docs#install-script), or add `@nubjs/nub` as a devDependency when the platform owns the install step.

| Platform | Deployment path | Where Nub runs |
| --- | --- | --- |
| [Vercel](/docs/deployment/vercel) | Installer or devDependency | Install and build; Vercel Functions still use Vercel's Node runtime |
| [Cloudflare](/docs/deployment/cloudflare) | Preinstalled in Workers Builds; devDependency on Pages | Build only; Workers use Cloudflare's runtime |
| [Railway](/docs/deployment/railway) | Dockerfile | Build and runtime |
| [Render](/docs/deployment/render) | Dockerfile | Build and runtime |
| [AWS Lambda](/docs/deployment/aws-lambda) | Dockerfile with Lambda Web Adapter | Build and runtime |
| [Google Cloud Run](/docs/deployment/google-cloud-run) | Dockerfile | Build and runtime |

## Managed builders

A hosted builder that installs from your lockfile cannot find Nub until the project supplies it:

```console
sh: nub: not found
```

Add the CLI as a devDependency and call it from a package script:

```json title="package.json"
{
  "devDependencies": {
    "@nubjs/nub": "^{{NUB_VERSION}}"
  },
  "scripts": {
    "build": "nubx vite build"
  }
}
```

Every package manager links `nub` and `nubx` into `node_modules/.bin`. The Nub launcher sets its own executable bit at runtime, so no install script has to run.

<Callout type="warn">
  Keep development dependencies enabled for the build. Use the installer or a Dockerfile when the platform installs production dependencies only.
</Callout>

## Container services

The official image runs as the non-root `node` user. A web service needs a Dockerfile and a server that listens on `0.0.0.0` at the provider's `PORT`:

```dockerfile title="Dockerfile"
FROM ghcr.io/nubjs/nub:{{NUB_VERSION}}

COPY --chown=node:node package.json package-lock.json ./
RUN nub ci

COPY --chown=node:node . .
EXPOSE 8080
CMD ["nub", "run", "start"]
```

Change `package-lock.json` to the lockfile the project already uses; Nub reads npm, pnpm, Bun, and Yarn lockfiles. See [Docker](/docs/deployment/docker#web-services) for the server and the image variants.

## GitHub Actions and registries

The setup action prepares the runner for tests. Standard Docker actions then build the Dockerfile above and publish the image to GHCR:

```yaml title=".github/workflows/image.yml"
name: Image
on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

jobs:
  image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: nubjs/setup-nub@v0
      - run: nub ci
      - run: nub run test
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

Railway and Render can pull an image from GHCR directly. AWS Lambda requires ECR, and Google recommends Artifact Registry for Cloud Run; each provider page covers its registry.

<Callout>
Read the [full docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) on docs.github.com.
</Callout>

## Node versions

A managed builder selects Node, and Nub runs on that version. Pin it with a source the platform reads, usually `.node-version`, `.nvmrc`, or `engines.node` in `package.json`.

A container carries its own Node. Pin the Nub image tag, and update it to move to a new Nub or Node release.

Environments driven by `.tool-versions` can install the CLI through [mise](https://mise.jdx.dev): `mise use nub@latest` puts `nub`, `nubx`, and `nubr` on `PATH`.
