The features on this page (the `.toml` / `.yaml` loaders) require Nub's global type-declaration package to avoid TypeScript compiler errors.

Import a config or data file directly.

```ts
import config from "./config.yaml";  // parsed object
import flags from "./feature.jsonc"; // parsed object (comments stripped)
import pkg from "./Cargo.toml";      // parsed object
import schema from "./schema.json5"; // parsed object (JSON5 superset)
import prompt from "./prompt.txt";   // string
```

## Extensions

Nub picks the loader by file extension. Plain `.json` is not in the set, because Node imports JSON natively.

| Extension | Imports as |
| --- | --- |
| `.jsonc` | JSON with comments, parsed |
| `.json5` | JSON5, parsed |
| `.toml` | TOML, parsed |
| `.yaml`, `.yml` | YAML, parsed |
| `.txt` | a string, unparsed |

## Content mappers

TypeScript 7.1's [content mappers](https://github.com/microsoft/typescript-go/pull/4712) type-check other file types, but TypeScript never runs them. The runtime half is the package's `./register` export, which Nub preloads for every package your tsconfig lists.

```jsonc title="tsconfig.json"
{
  // ...
  "contentMappers": [
    { "package": "motherload", "extensions": [".toml", ".yaml"] }
  ]
}
```

```ts title="main.ts"
import config from "./config.yaml"; // loaded by motherload/register
```

```sh
nub main.ts
```

There is no `--import` to pass and nothing to add to `nub.jsonc`. A mapper takes precedence over Nub's own loaders.

- **Which tsconfig:** the nearest to the entry file, or to the package for `nub run`. `extends` and `references` are followed, and each `package` resolves from the config that declares it.
- **Order:** the longest extension answers first, as in TypeScript, so `.schema.jsonc` wins over `.jsonc`. A [`preload`](/docs/config#preload) entry answers before any mapper.
- **No runtime:** a package that is not installed, has no `./register` export, or whose register needs a newer Node is skipped. Importing one of its extensions fails, and the error names the package.

`--node` and `NODE_COMPAT` load no registers.

### Options

An entry's `options` reach its register as JSON in the `CONTENT_MAPPER_OPTIONS` environment variable.

```jsonc title="tsconfig.json"
{
  "contentMappers": [
    {
      "package": "sql-mapper",
      "extensions": [".sql"],
      "options": { "dialect": "postgres" }
    }
  ]
}
```

The variable is set only while that register's module evaluates, so it never reaches your application or the processes it starts.

### Package authors

A package takes part by exporting `./register` beside its content mapper. Importing that module registers the runtime hooks, and it reads its options at the top level.

```json title="package.json"
{
  "name": "sql-mapper",
  "exports": { "./register": "./register.mjs" },
  "typescript": { "contentMapper": { "exec": ["node", "mapper.mjs"] } }
}
```

```js title="register.mjs"
import { registerHooks } from "node:module";
import { fileURLToPath } from "node:url";
import { compile } from "./compile.mjs";

const options = JSON.parse(process.env.CONTENT_MAPPER_OPTIONS ?? "{}");

registerHooks({
  load(url, context, next) {
    if (!url.endsWith(".sql")) return next(url, context);
    const source = compile(fileURLToPath(url), options);
    return { format: "module", source, shortCircuit: true };
  },
});
```

The same export runs under plain Node, where the variable is yours to set:

```sh
CONTENT_MAPPER_OPTIONS='{"dialect":"postgres"}' \
  node --import sql-mapper/register main.ts
```

## Default export

A data module has a single default export, the parsed value, like Node's own JSON modules. There are no named exports, so destructure the default to pull out top-level keys.

```yaml title="config.yaml"
host: localhost
port: 5432
```

```ts
import config from "./config.yaml"; // { host: "localhost", port: 5432 }
const { host, port } = config;      // "localhost", 5432
```

The object formats are typed `Record<string, unknown>`, so narrow or cast destructured keys where you use them. A file whose top-level value is an array or scalar imports as that value; cast it, since the type assumes an object.

## Values

YAML follows the YAML 1.2 core schema, as the `yaml` package does. `.nan` and `.inf` are numbers, an unquoted `nan`, `yes` or `2001-12-14` is a string, and an integer past `Number.MAX_SAFE_INTEGER` rounds to the nearest number.

TOML values that JSON has no form for keep their type:

| TOML | JavaScript |
| --- | --- |
| `9007199254740993` (past `Number.MAX_SAFE_INTEGER`) | `9007199254740993n` |
| `nan`, `-inf` | `NaN`, `-Infinity` |
| `1979-05-27T07:32:00Z` | `Date` |
| `1979-05-27T07:32:00` (local) | `Date` in the local time zone |
| `1979-05-27` | `Date` at UTC midnight |
| `07:32:00` | `"07:32:00.000"` |

JSON5's `NaN` and `Infinity` are numbers too.

## Text imports

Add the `with { type: "text" }` import attribute to read any file's raw contents as a string. The attribute wins over parsing, so a `.yaml` or `.json` file read this way is the raw text.

```ts
import readme from "./README.md" with { type: "text" };  // string
import query from "./query.sql" with { type: "text" };   // string
import raw from "./config.yaml" with { type: "text" };   // YAML, unparsed
```

<Callout>
Read the [full docs](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/with) for import attributes on developer.mozilla.org.
</Callout>

## Custom extensions

Map an extension of your own onto one of Nub's loaders in a [nub.jsonc](/docs/config#loader).

```jsonc title="nub.jsonc"
{
  // ...
  "loader": {
    ".config": "jsonc",  // JSON with comments
    ".data": "yaml"
  }
}
```

The loader names are:

```text
text  jsonc  json5  toml  yaml  ts  tsx  jsx
```

Any other value stops the command with an error.
