---
title: Environment files
description: Automatic environment-file loading, covering the file set and its precedence, mode selection, variable expansion, explicit files, and turning loading off.
---

Nub loads your `.env*` files into the environment before Node starts, with no `dotenv` import and no flag. It reads them from the nearest directory with a `package.json`, walking up from the working directory.

```bash
nub server.ts   # .env* in the project root are loaded automatically
```

<Callout title="Using Varlock?">
A project with a `.env.schema` and Varlock installed hands its environment to [Varlock](/docs/runtime/varlock) instead, and the automatic loading on this page does not run.
</Callout>

## File precedence

Nub loads four files, highest priority first. The first file to define a key wins, and a variable already set in the shell is never overridden.

1. `.env.[mode].local`
2. `.env.local`
3. `.env.[mode]`
4. `.env`

```bash
# reads .env.production.local, .env.local, .env.production, .env
APP_ENV=production nub server.ts
```

## Selecting the mode

The mode fills the `[mode]` slots, and with no mode only `.env.local` and `.env` load. Set `APP_ENV` to any mode name; when it is unset, `NODE_ENV` selects the mode, but only for `development`, `production`, or `test`.

```bash
APP_ENV=staging nub server.ts      # .env.staging*
NODE_ENV=production nub server.ts  # .env.production*
NODE_ENV=staging nub server.ts     # any other mode: .env and .env.local
```

The `APP_ENV` variable chooses the files without changing `NODE_ENV`, and wins when both are set. To load one specific file instead of a mode, use [`--env-file`](#explicit-files).

## Test mode

When the mode is `test`, the `.env.local` slot is skipped, so only `.env.test.local`, `.env.test`, and `.env` load. Developer-machine values in `.env.local` stay out of test runs.

## Variables a file cannot set

An automatically loaded `.env*` file cannot set `NODE_ENV`; Nub ignores the key with a warning. A file passed with `--env-file` can set it. From any env file, Nub ignores the variables that control how Node starts:

```text
NODE_OPTIONS
NODE_TLS_REJECT_UNAUTHORIZED
NODE_EXTRA_CA_CERTS
NODE_REPL_EXTERNAL_MODULE
```

Set any of these in the shell environment instead.

## Variable expansion

Values in the automatic `.env*` files expand `${VAR}` and `$VAR` references. A reference resolves against the other loaded values first, then the shell environment, and an undefined one becomes the empty string. A value can reference another value that itself holds a reference.

```bash title=".env"
HOST=localhost
PORT=5432
# $HOST works too
DATABASE_URL=postgres://${HOST}:${PORT}/app
```

Escape a literal dollar sign as `\$`. Unescaped, `PASSWORD=foo$bar` becomes `foo` when `bar` is unset.

```bash title=".env"
PASSWORD="foo\$bar"
```

Files named in the `nub.jsonc` [`envFile`](#project-configuration) field expand the same way. Files named with `--env-file` do not expand.

## Explicit files

Passing `--env-file=<path>` turns off automatic discovery, and only the named file loads. It uses the same parser, and the shell environment still wins over it.

```bash
# only .env.ci loads
nub --env-file=.env.ci server.ts
```

Values arrive verbatim, as with Node's `--env-file`: no `${VAR}` expansion, and no `\$` escape, so `PASSWORD="foo\$bar"` keeps its backslash.

Pass the flag more than once to load several files in order. A missing file is an error; `--env-file-if-exists` skips it instead.

```bash
# .env.production wins the keys it shares with .env
nub --env-file=.env --env-file=.env.production server.ts

# loads .env.local if present
nub --env-file-if-exists=.env.local server.ts
```

A named file also takes precedence over a [Varlock](/docs/runtime/varlock) hand-over.

<Callout>
Read the [full docs](https://nodejs.org/api/cli.html#--env-filefile) for `--env-file` on nodejs.org.
</Callout>

## Loading nothing

Pass `--no-env-file` to load no env files at all. It suppresses automatic discovery, ignores any `--env-file` or `--env-file-if-exists`, and skips a [Varlock](/docs/runtime/varlock) hand-over.

```bash
# neither .env* discovery nor the named --env-file loads
nub --no-env-file --env-file=.env.ci server.ts
```

The flag works the same for a file run, `nub run`, `nubx`, and `nub watch`.

## Project configuration

Set the same behavior for every run in a [nub.jsonc](/docs/config#envfile) at the project root.

```jsonc title="nub.jsonc"
{
  // ...
  "envFile": [".env", ".env.local"]  // later files win
}
```

The field takes four forms:

```text
true                     automatic .env* discovery (the default)
false                    load nothing, like --no-env-file
"varlock"                hand the environment to Varlock
[".env", ".env.local"]   these files, in order; later files win
```

A path always goes in an array, even a single one. Paths resolve from the directory holding the config file (see [relative paths](/docs/config#relative-paths)), and expand `${VAR}` and `$VAR` against the environment, so `".env.${APP_ENV}"` reads `.env.staging` under `APP_ENV=staging`.

Passing `--env-file` or `--no-env-file` on the command line overrides the field.
