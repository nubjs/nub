Run a TypeScript file directly, with no tsconfig and no build step.

```sh
nub index.ts
nub server.tsx
nub script.js
```

Nub runs the file on stock Node and adds the following.

| Page | What it adds |
| --- | --- |
| [TypeScript](/docs/runtime/typescript) | Every TypeScript feature, including `enum` and `namespace`, with source maps |
| [JSX](/docs/runtime/jsx) | `.jsx` and `.tsx` files, with the automatic runtime by default |
| [Decorators](/docs/runtime/decorators) | Legacy decorators and emitted design-type metadata |
| [Module resolution](/docs/runtime/resolution) | Path aliases, extensionless imports, and `.js` to `.ts` rewriting, as your editor resolves them |
| [Environment files](/docs/runtime/env) | Automatic `.env*` loading with `${VAR}` expansion |
| [Varlock](/docs/runtime/varlock) | Hands the environment to Varlock when the project has a `.env.schema` |
| [Loaders](/docs/runtime/loaders) | YAML, TOML, JSONC, JSON5, and text files imported as values |
| [Modern APIs](/docs/runtime/modern-apis) | Temporal, URLPattern, WebSocket, `node:sqlite`, and more, per Node version |
| [Web Workers](/docs/runtime/workers) | The browser `Worker` global, with TypeScript entry points |
| [Web Storage](/docs/runtime/web-storage) | `sessionStorage`, and `localStorage` backed by a file |
| [Threadpool](/docs/runtime/threadpool) | A libuv threadpool sized to the available cores |
| [Debugging](/docs/runtime/debugging) | A VS Code launch configuration that runs through Nub |

## A drop-in for `node`

Nub accepts the same arguments as `node`, and every flag reaches Node verbatim.

```bash
nub --max-old-space-size=4096 build.ts  # node flags go before the file
nub --inspect-brk server.ts
nub --import ./instrument.js server.ts
nub script.ts --port 3000 --verbose     # the rest is the script's argv
echo 'console.log(1 + 1)' | nub -       # program from stdin, like node -
```

## Node version resolution

Nub runs your code on the Node version your project pins, such as a `.node-version` file or `engines.node`, and downloads it when it is missing. With nothing pinned, it uses the `node` on your `PATH`.

```sh
$ echo {{NODE_MAJOR}} > .node-version
$ nub hello.ts
Using Node.js {{NODE_VERSION}} (resolved from .node-version)
Installed in 9.8s
Hello world!
```

[Managing Node versions](/docs/node) lists every pin source in precedence order and covers the `nub node` subcommands.

## Supported versions and tiers

Nub supports Node 18.19 and later, except Node 19 and 20.0–20.5, which lack the loader-hook API. It delivers the same augmentations through one of two tiers, chosen by the Node version:

| Tier | Node versions | Module hooks |
| --- | --- | --- |
| Fast | 22.15+ on 22.x, 23.5+ on 23.x, and every release from 24 on | Sync `module.registerHooks()`, in the main thread |
| Compatibility | 18.19+ on 18.x, 20.6+ on 20.x, all of 21.x, 22.0–22.14, and 23.0–23.4 | Async `module.register()`, in a loader-worker thread |

The compatibility tier adds about 80 ms to cold start, plus about 90 µs per module, and does not change execution speed. A fast-tier Node is recommended.

## Project configuration

Settings you want on every run go in a [nub.jsonc](/docs/config) at the project root.

```jsonc title="nub.jsonc"
{
  "preload": ["./instrumentation.ts", "tsx/esm"], // before the entry
  "nodeOptions": ["--enable-source-maps"],        // on every run
  "v8Flags": ["--expose-gc"]                      // on Node's argv
}
```

A preload path resolves from the directory holding the file that names it, and a bare specifier resolves like an import in your project. V8 flags go on Node's command line rather than into `NODE_OPTIONS`, so flags that `NODE_OPTIONS` rejects, such as `--stack-size`, work too.

A command-line flag always wins over the file. See [nub.jsonc](/docs/config) for the full precedence order.

## Compatibility mode

Compatibility mode turns every augmentation off and runs your code on plain Node: no load hook, no preloads, no unflagging, and no `.env` loading. Nub still runs the project's pinned Node and downloads it when missing.

Compatibility mode is separate from the compatibility [tier](#supported-versions-and-tiers), which only changes how augmentation is delivered.

### `--node`

Pass `--node` to run a single invocation with zero augmentation.

```bash
nub --node script.js     # the project's pinned Node, vanilla
node script.js           # your shell's Node, unaugmented, unprovisioned
```

### `NODE_COMPAT`

A truthy `NODE_COMPAT` (`1`, `true`, or `yes`, case-insensitive) has the same effect as `--node`, and every descendant `node` or `nub` inherits it.

```bash
export NODE_COMPAT=1     # every nub/node in this shell now runs vanilla
nub script.ts            # plain Node, still on the pinned version
```

### `nodeCompat`

Setting `nodeCompat` in a [nub.jsonc](/docs/config#nodecompat) applies compatibility mode to every run in the project. The other `nub.jsonc` runtime fields no longer apply.

```jsonc title="nub.jsonc"
{
  // ...
  "nodeCompat": true  // compatibility mode for every run
}
```

## Memory-constrained launches

On Linux x64, Nub sets V8's semi-space to 16 MiB for two Node releases when the process runs under a cgroup memory limit in the range below. Every other release, platform, and budget keeps Node's defaults.

| Node release | Memory budget, inclusive |
|---|---|
| 22.23.2 | 512 MiB–1 GiB |
| 24.20.0 | 512 MiB |

Passing Node options or preloads of your own turns the tuning off, and Workers keep their own defaults. Use [`v8Flags`](/docs/config#v8flags) for an application-specific budget.

## How it works

Nub reads the `.env*` files itself and passes their values to Node in the environment. A preload registers the module hooks that transpile and resolve your code, and installs the missing globals. The fast tier loads it with `--require`, the compatibility tier with `--import`. Transpilation runs in an embedded [oxc](https://oxc.rs) N-API addon.
