If your editor's Go-to-Definition follows an import and `tsc` accepts it, Nub resolves it the same way at runtime. No `tsconfig-paths` package, no build step.

```ts
// tsconfig.json paths alias
import { db } from "@db";

// extensionless, resolves ./config.ts
import { config } from "./config";

// .js→.ts swap, resolves ./handler.ts when no .js exists on disk
import { handler } from "./handler.js";
```

Everything else goes to Node's own resolver unchanged: package names, `exports` and `imports` maps, export conditions, and every subpath into a dependency that declares `exports`.

## Settings from `tsconfig.json`

Nub reads your nearest `tsconfig.json` and applies `paths`, `baseUrl`, and `extends` at runtime.

### `paths`

The `compilerOptions.paths` mappings resolve `@/...`-style aliases, from any importing file, `.js` included.

```json title="tsconfig.json"
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@db": ["src/db/index.ts"]
    }
  }
}
```

```ts
import { db } from "@db";
import { Button } from "@/components/Button";
```

Matching follows the `tsc` rules: an exact pattern wins, then the longest matching wildcard prefix. Node builtins always win, so `import "os"` is `node:os`, never `baseUrl/os.ts`.

<Callout>
Read the [full docs](https://www.typescriptlang.org/tsconfig/paths.html) for `paths` on typescriptlang.org.
</Callout>

### `baseUrl`

With `baseUrl` set and no matching `paths` entry, a bare specifier resolves relative to the base directory.

```json title="tsconfig.json"
{ "compilerOptions": { "baseUrl": "." } }
```

```ts
import { config } from "lib/config";   // <baseUrl>/lib/config.ts
import { z } from "zod";               // no <baseUrl>/zod: node_modules
```

### `extends`

Nub follows `extends` chains as `tsc` does, including array `extends`, configs from packages such as `@tsconfig/node20/tsconfig.json`, and the `${configDir}` template.

Configs are read once per process. After editing `tsconfig.json`, restart the process, or run under [`nub watch`](/docs/watch), which restarts it for you.

## Extensionless imports

In TypeScript files, a relative import without an extension resolves the way `tsc` resolves it.

```ts
// from a .ts / .tsx / .mts / .cts file
import { config } from "./config";   // ./config.ts
import data from "./fixtures";       // ./fixtures/index.ts, or "main"
```

The probe order depends on the importing file's extension:

```text
.ts  parent →  .ts  .tsx  .js  .jsx  .json
.tsx parent →  .tsx  .ts  .jsx  .js  .json
.mts parent →  .mts  .ts  .mjs  .js  .json
.cts parent →  .cts  .ts  .cjs  .js  .json
```

A directory import reads the directory's `package.json` `"main"` first, then probes `index` in the same order. A plain `.js` file still needs relative extensions, as under Node.

## Extension swap

With `moduleResolution: "nodenext"`, `tsc` requires a `.js` extension on an import of a `.ts` file. Nub maps the written `.js` to the `.ts` on disk.

```ts
// resolves ./handler.ts when no ./handler.js exists
import { handler } from "./handler.js";

// also across a package subpath into a TypeScript workspace package
import { createPrompt } from "@repo/lib/prompt.js";
```

The swap only applies when the written file does not exist. It also maps `.jsx` to `.tsx`, `.mjs` to `.mts`, and `.cjs` to `.cts`.

## Package subpaths

A subpath into a dependency without an `exports` map is probed too, from any importing file. An extensionless subpath finds the file on disk, and a workspace package whose `main` points at TypeScript resolves by subpath.

```ts
// node_modules/prismjs/components/prism-python.js
import "prismjs/components/prism-python";

// a workspace package with "main": "./index.ts": packages/lib/prompt.ts
import { createPrompt } from "@repo/lib/prompt";

// a directory subpath: qs/lib/index.js
import { parse } from "qs/lib";
```

The probe order is fixed for subpaths:

```text
.js  .json  .ts  .tsx
```

JavaScript comes first because Nub does not transpile inside `node_modules`, where a published package's `.ts` files are unshipped source. A symlinked workspace package ships no `.js`, so the probe reaches its TypeScript.

<Callout>A dependency that declares `exports` is never probed. Its map alone decides what is reachable, as on Node.</Callout>

## Export conditions

Add your own conditions in a [nub.jsonc](/docs/config#conditions), and every resolution in the project matches against them, a bare-specifier [preload](/docs/config#preload) included.

```jsonc title="nub.jsonc"
{
  // ...
  "conditions": ["development"]  // matched ahead of "default"
}
```

```json title="node_modules/example/package.json"
{
  "exports": {
    ".": {
      "development": "./development.js",
      "default": "./production.js"
    }
  }
}
```

<Callout>
Read the [full docs](https://nodejs.org/api/packages.html) for package entry points and conditions on nodejs.org.
</Callout>

## The `nub` condition

The Nub CLI matches a `nub` condition on every run it augments, so a package that publishes a branch for it resolves there. It works like the `bun` and `deno` conditions those runtimes set.

```json title="node_modules/example/package.json"
{
  "exports": {
    ".": {
      "nub": "./dist/nub.js",
      "default": "./dist/index.js"
    }
  }
}
```

Point the branch at JavaScript. Files inside `node_modules` are [never transpiled](/docs/runtime/typescript#plain-javascript), so a TypeScript target fails to load.

A run under `--node` does not match the condition, and neither does the standalone [runner](https://www.npmjs.com/package/@nubjs/runner), so a file resolves the same way under it as under tsx. Both fall through to `default`.

## Yarn Plug'n'Play

Nub enables Plug'n'Play automatically. It detects a `.pnp.cjs` at the project root and loads it ahead of its own preload, so PnP resolution works for file runs, `nub run`, and `nubx`.

```bash
nub index.ts        # .pnp.cjs is detected and loaded automatically
nub run build       # same for run scripts and nubx
```

Both `require` and `import` resolve under PnP, including packages stored as zips in `.yarn/cache`. Nub runs a PnP project; it does not produce a PnP install.

<Callout>
Read the [full docs](https://yarnpkg.com/features/pnp) for Plug'n'Play on yarnpkg.com.
</Callout>
