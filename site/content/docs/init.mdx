---
title: Creating a Nub project
description: Scaffold a TypeScript project with a manifest, tsconfig, entry file, git repository, and installed dev dependencies in one command.
---

The `nub init` command scaffolds a minimal TypeScript project that runs and typechecks immediately. It writes five files, initializes git, and installs TypeScript plus the type packages the editor needs.

```console
$ nub init -y
created my-app
├── package.json
├── tsconfig.json
├── index.ts
├── .gitignore
├── README.md
└── .git/

devDependencies:
+ @nubjs/types@0.4.13
+ @types/node@26.1.1
+ typescript@7.0.2

Your project is ready!
Try running `nub index.ts`
```

The scaffold has no runtime dependencies, and the entry file runs as is:

```console
$ nub index.ts
Hello from Nub
```

## Generated files

The manifest carries the same `packageManager` pin and `devEngines` range that [`nub pm pin`](/docs/pm#nub-pm-pin) writes, plus the dev dependencies. The install step writes Nub's lockfile, `nub.lock`.

```json title="package.json"
{
  "name": "my-app",
  "version": "0.0.1",
  "type": "module",
  "packageManager": "nub@0.5.0",
  "devEngines": {
    "packageManager": {
      "name": "nub",
      "version": "^0.5.0",
      "onFail": "ignore"
    }
  },
  "scripts": {
    "start": "nub index.ts"
  },
  "devDependencies": {
    "@nubjs/types": ">=0.4.13 <=0.5.0",
    "@types/node": "^26",
    "typescript": "^7"
  }
}
```

The `@nubjs/types` range is capped at the running Nub version. Its lower bound leaves room for the 24-hour [cooling window](/docs/install#cooling-window) to pick a mature release.

The tsconfig follows Node's own TypeScript semantics and loads the installed type packages. It sets `noEmit`, because Nub transpiles at run time and the installed `typescript` is only for the editor and typechecking.

```jsonc title="tsconfig.json"
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "target": "es2024",
    "lib": ["es2024"],
    "types": ["node", "@nubjs/types"],
    "strict": true,
    "noEmit": true
    // ...
  }
}
```

## Flags

In a terminal, `nub init` asks for the project name, the language, and whether to initialize git. Outside a terminal, and with `-y`, it takes the defaults.

| Flag | Effect |
|---|---|
| `-y`, `--yes` | Skip all prompts, take the defaults. |
| `--js` | JavaScript variant: writes `index.js`, no tsconfig, no devDependencies. |
| `--name <name>` | Project name (default: the directory name, sanitized). Scoped names (`@scope/pkg`) are preserved. |
| `--no-git` | Skip `git init`. |
| `--no-install` | Skip the install step. |
| `--force` | Overwrite existing files. |

## Existing files

When any target file already exists, init names the conflicts and writes nothing:

```console
$ nub init -y
Error: nub: refusing to overwrite existing files: package.json,
tsconfig.json, index.ts, .gitignore, README.md
  (pass --force to overwrite)
```

Passing `--force` overwrites the listed files. Inside an existing git repository, init skips `git init`.

## Templates

Framework templates come from `nub create`. It maps the name to the ecosystem's `create-*` package (`vue` → `create-vue`, `@scope/foo` → `@scope/create-foo`), fetches it, and runs it. Everything after the template name goes to the scaffolder, and scaffolders that detect the invoking package manager print Nub commands:

```console
$ nub create vue my-app --default

└  Done. Now run:

   cd my-app
   nub install
   nub run dev
```

<Callout>
Read the [full docs](https://pnpm.io/cli/create) for `pnpm create` on pnpm.io.
</Callout>

Passing a template name to `init` is an error that points at its scaffolder:

```console
$ nub init vite
Error: nub: `init` does not accept arguments (got "vite")
  (to scaffold from a template: nubx create-vite)
```

## Plain Node

The generated project also runs on plain Node. The `devEngines` policy is `ignore`, so nothing enforces Nub, and the only change is a `node` start script. Plain Node runs the TypeScript entry on 22.18+ and 23.6+; on older Node, scaffold with `--js`.
