title: Package meta-manager
description: Provision and run the package manager your project pins, as corepack does, in native Rust. The exact pnpm, npm, or yarn release is fetched, verified, cached, and run on the project's Node.
---

Nub reads your project's package-manager pin and runs that exact version under the project's Node. The first run fetches it from the npm registry, verifies its integrity, and caches it under `~/.cache/nub/pm`.

```console
$ nub pm which
/Users/you/.cache/nub/pm/pnpm/9.15.4/package/bin/pnpm.cjs
» resolved from packageManager (pnpm@9.15.4)
```

There is no corepack `enable` step and no built-in version table, so an older Nub binary still provisions today's pnpm.

## Pin resolution

Nub reads the pin at the workspace root, in this order:

1. **`.yarnrc.yml` `yarnPath`** — a committed Yarn Berry release
2. **`package.json#/packageManager`** — the corepack field, exact only (`pnpm@9.15.4`, optionally `+sha512.<hash>`)
3. **`package.json#/devEngines/packageManager`** — `{ name, version }`, where the version may be a range

Ranges belong in `devEngines`, because corepack, pnpm, and Yarn all reject them in `packageManager`. A lockfile never implies a pin. With no pin, `nub pm which` errors and points at [`nub pm use`](#nub-pm-use).

<Callout title="Yarn Berry">
Nub runs a committed Berry release directly and never provisions Berry, so a `yarn@2+` pin without a `yarnPath` release errors. Yarn classic (1.x) provisions like any other manager.
</Callout>

## CLI

The `nub pm` commands resolve, pin, and cache the package manager a project uses.

### `nub pm which`

Print the resolved package manager, provisioning it if it isn't cached yet. The path goes to stdout and the provenance to stderr:

```bash
PM=$(nub pm which)   # the path only
```

### `nub pm use`

Declare the project's package manager: npm, pnpm, Yarn, or Bun. The command resolves the version, fetches and verifies it, writes the pin, and converts the lockfile.

```bash
nub pm use pnpm           # newest pnpm (latest dist-tag)
nub pm use npm@10         # newest 10.x
nub pm use pnpm@9.15.4    # exact
```

Moving an npm project to pnpm:

```console
$ nub pm use pnpm
Fetching pnpm 11.5.3 (4 MB)...
using pnpm@11.5.3
  package.json: packageManager = pnpm@11.5.3 (+sha512)
  package.json: devEngines.packageManager =
    { name: "pnpm", version: "^11.5.3", onFail: "warn" }
  pnpm-lock.yaml: written (converted from package-lock.json)
  package-lock.json: removed (migrated)
```

It writes three things, and rerunning it is a no-op:

- **`package.json#/packageManager`** — the exact version plus a `+sha512` hash from the verified tarball, the field corepack, pnpm, and turbo read
- **`package.json#/devEngines/packageManager`** — `{ name, version: "^<exact>", onFail: "warn" }`, the range-and-policy form npm and pnpm enforce
- **The lockfile, in the new manager's format** — a lockfile in another format is converted with its resolution state and the old file removed; one already in the target format is left alone

The converted lockfile passes the new manager's frozen install, such as `pnpm install --frozen-lockfile`.

<Callout title="Config is not migrated">
Switching managers converts the lockfile, not your config. The `.npmrc`, any `pnpm.*` fields, `pnpm-workspace.yaml` settings, and other manager-specific config stay as they are.
</Callout>

Four cases stop the command before anything is written:

- **Multiple foreign-format lockfiles** — remove the stale ones first.
- **A binary `bun.lockb` source** — regenerate it as text first with `bun install --save-text-lockfile`.
- **Running `use yarn` onto a Berry (2+) `yarn.lock`** — classic would downgrade the format; use `yarn set version`.
- **Running `use yarn` on a graph using the `workspace:` protocol** — classic Yarn can't express it.

Running `use bun` writes the pin and lockfile but doesn't provision Bun.

### `nub pm pin`

Pin the project to an exact Nub version, the running one by default. See [pinning Nub itself](#pinning-nub-itself) for what the pin does.

```bash
nub pm pin           # pin the running Nub
nub pm pin 0.2.10    # pin an exact version
```

```console
$ nub pm pin
pinned nub@0.2.10
  package.json: packageManager = nub@0.2.10
  package.json: devEngines.packageManager =
    { name: "nub", version: "^0.2.10", onFail: "ignore" }
```

It writes only the two pin fields, with no lockfile conversion or config migration; [`nub pm use nub`](#nub-pm-use) is the full switch onto Nub. The version must be exact.

### `nub pm update`

Bump the pin to the newest version satisfying the `devEngines` range, or the registry `latest` without one. The command provisions it and rewrites `packageManager` with a fresh hash. Alias: `nub pm up`.

```console
$ nub pm update
Fetching pnpm 9.15.9 (4 MB)...
updated pnpm 9.15.4 → 9.15.9
```

### `nub pm cache`

List or clear the cached package managers, stored at `~/.cache/nub/pm/<pm>/<version>`.

```console
$ nub pm cache
pnpm@9.15.4
yarn@1.22.22
$ nub pm cache clear
```

A cached exact pin runs offline. Nub contacts the registry only to resolve a range or fetch a missing version.

### `nub pm shim`

Route bare `pnpm`, `npm`, and `yarn` commands through Nub to the pinned manager; `nub pm unshim` removes the shims. The shims are opt-in, since `nub install` and `nub run` already run the pin. See [Corepack-style shims](/docs/pm/pm-shim).

## Pinning Nub itself

The `packageManager` field can also pin Nub. When the running Nub is a different version, it fetches that exact release, verifies its checksum, and hands off, so every contributor installs with the same Nub.

```json title="package.json"
{
  "packageManager": "nub@0.2.9"
}
```

Only the install verbs hand off:

```console
$ nub install
nub: provisioning pinned nub@0.2.9 (darwin-arm64)...
nub: provisioned nub@0.2.9
```

The file runner, `nub run`, [`nubx`](/docs/nubx), version management, and self-update never read the pin. A corrupt, missing, or wrong-version release is a hard error. Provisioned releases are stored at `~/.cache/nub/self/<version>` and run offline afterwards. A non-exact pin runs the installed Nub with a notice, since the `packageManager` field is exact-only.

To run your installed Nub regardless of the pin, set `NUB_SELF_SHIM=0`. It disables the handoff for the whole process tree:

```bash
NUB_SELF_SHIM=0 nub install
```

## `.npmrc`

The package-manager download goes through your `.npmrc`: `registry=` picks the mirror, and `//host/:_authToken=` authenticates.

```ini title="~/.npmrc"
registry=https://npm.corp.example
//npm.corp.example/:_authToken=${CORP_NPM_TOKEN}
```

Environment placeholders (`${VAR}`) expand in your user `~/.npmrc` and in `npm_config_*` variables. A project `.npmrc` committed to the repo is read literally, so a cloned repository cannot send one of your secrets to a host it chooses. On trusted CI, set `PNPM_CONFIG_NPMRC_AUTH_FILE=.npmrc` to expand the project file too.

To fetch package managers from a different registry than your dependencies, set `COREPACK_NPM_REGISTRY`, with `COREPACK_NPM_TOKEN` for auth.

<Callout>
Read the [full docs](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc) for the npmrc file on docs.npmjs.com.
</Callout>
