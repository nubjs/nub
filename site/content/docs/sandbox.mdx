> **Preview:** This page documents the sandbox engine's configuration grammar. Today the engine is reachable only through the `--sandbox <file>` flag on `nub run`; the `nub.jsonc` bridge is inert. Credential brokering is still being finalized.

A policy grants a command only the files, hosts, and variables it needs. Four axes: `fs`, `net`, `vars` for ordinary environment variables, and `secrets` for sensitive ones.

```jsonc title="sandbox.jsonc"
{
  "fs": { "./src": "r", "./dist": "rw" },
  "net": ["registry.npmjs.org", "api.github.com"],
  "vars": ["NODE_ENV"],
  "secrets": { "GITHUB_TOKEN": { "brokerTo": ["api.github.com"] } }
}
```

```console
$ nub run --sandbox sandbox.jsonc node build.js
```

## Where a policy lives

A `nub.jsonc` sandbox value is a preset name or a file reference, never an inline policy object — keeping the policy in its own file is what lets Nub exclude that file from the filesystem grant.

```jsonc title="nub.jsonc"
{
  "sandbox": "build-jail",                              // a preset name
  "install": { "sandbox": "./policies/install.jsonc" }  // or a file reference
}
```

The policy file holds the axes object directly, or under a `sandbox` key. Unspecified keys fail closed.

<Callout type="warn">
Nub excludes the policy file itself from the filesystem grant, so a confined process can never read or rewrite the policy that confines it.
</Callout>

## Dependency build scripts

Every approved dependency build script runs under the `build-jail` preset, with no configuration. Writes reach the package's own directory and a throwaway home, reads reach the dependency tree, and egress is decided by package identity: a package the curated catalog names reaches exactly what it was measured to need.

If one package cannot run under those limits, exempt that package alone. A root-authored `allowBuilds` value of `"no-jail"` runs its build scripts unconfined and leaves every other package confined:

```json title="package.json"
{
  "allowBuilds": {
    "some-native-addon": "no-jail"    // this package only; everything else stays confined
  }
}
```

Turning confinement off for the whole project is the wider option:

```json title="nub.jsonc"
{
  "install": {
    "buildJail": false
  }
}
```

Nub names each package on every install that runs it unconfined:

```
warning: some-native-addon build scripts are running without the build sandbox (install.buildJail is false in nub.jsonc)
```

<Callout type="warn">
Turning the jail off approves nothing: `approveBuilds` decides **whether** a script runs, the jail decides whether it is **confined**.
</Callout>

### A confined script can fail without saying so

The kernel refuses a denied access inside the script's own process, and does not tell Nub which path was refused. Most scripts report that as a normal error; some ignore it and exit successfully having done nothing, so the install succeeds with the work missing.

If a package installs cleanly but behaves as though its build step never ran, set `install.buildJail` to `false`, install again, and compare. If that fixes it, [open an issue](https://github.com/nubjs/nub/issues) naming the package and version — it will be measured and added.

### Packages that cannot run confined on Windows

Three packages in the measured set fail under the jail on Windows and cannot be fixed by widening the policy. Each needs the per-package exemption above.

| Package | Why |
| --- | --- |
| `cpu-features` | Its compiler probe starts a Visual Studio COM server, which refuses a sandboxed process. An install still succeeds, because the package is an optional dependency of `ssh2` — the native acceleration is skipped, not the install. |
| `jpegtran-bin` | Ships a prebuilt executable with no relocation table. Windows cannot load such an image into a sandboxed process. |
| `mozjpeg` | Ships the same kind of prebuilt executable. |

```json title="package.json"
{
  "allowBuilds": {
    "cpu-features": "no-jail"
  }
}
```

No package in that set fails under the jail on macOS or Linux.

## Rule order

A rule set is an array or an object; either way rules apply in order and the last match wins. (JSON preserves key order, so an object's keys are ordered too.)

```jsonc
{
  "fs": ["./data", "!./data/private"],   // data, except private
  "net": ["*", "!*.tracking.example"]    // everything, except that domain
}
```

Order decides whether a path is allowed at all, not how much access it gets — a read rule never takes write away from a path an earlier rule made writable. Deny it instead, which takes read away too.

An entry is not a grant, so a set of only deny rules is still a deny-all base — it allows nothing, exactly like the empty set.

```jsonc
{ "fs": ["!./data/private"] }   // denies everything, not "everything except private"
```

Start from a broad allow to write a denylist.

## `fs`

The `fs` axis controls filesystem reads and writes. It takes an array (every grant is read-write) or an object (per-path access) — one form per axis, not mixed.

### Grant paths (array form)

Every entry grants read-write, and a path covers everything beneath it.

```jsonc
{
  "fs": ["./src", "./dist", "$cache/my-tool"]
}
```

### Read vs read-write (object form)

Values are `"r"`, `"rw"`, and `false`. There is no write-only mode.

```jsonc
{
  "fs": {
    "./src": "r",
    "./dist": "rw",
    "./secrets": false    // denied
  }
}
```

### Deny a path

Prefix an array entry with `!`, or give an object key the value `false`. Order matters.

```jsonc
{
  "fs": ["./data", "!./data/private"]    // private is denied
}
```

```jsonc
{
  "fs": ["!./data/private", "./data"]    // reversed: the last rule re-allows it
}
```

### Allow or deny everything

```jsonc
{ "fs": [] }     // deny all filesystem access
```

```jsonc
{ "fs": ["."] }  // the whole project — a directory grant is recursive
```

```jsonc
{ "fs": ["/"] }  // the whole filesystem
```

Prefer a directory grant over the glob `["*"]`, which is resolved to its matching paths once at startup: it skips dotfiles like `.git` and never covers a top-level file created after launch. The effect is otherwise the same.

### Use project-relative paths

Relative paths resolve from the project root.

```jsonc
{
  "fs": {
    "./src": "r",
    "dist": "rw",              // leading ./ is optional
    "../shared/schema": "r"
  }
}
```

### Built-in locations

A few names refer to well-known directories: `~` for the home directory, plus a closed set of `$`-prefixed names. An unrecognized `$name` is an error, and `$( … )` is command substitution, distinguished by its parentheses.

| Name | Directory |
| --- | --- |
| `~` | The user's home directory |
| `$cache` | The platform cache directory — `~/Library/Caches` (macOS), `%LOCALAPPDATA%` (Windows), `$XDG_CACHE_HOME` or `~/.cache` (Linux) |
| `$tmp` | A fresh, private temporary directory for this run |

```jsonc
{
  "fs": {
    "~/.config/my-tool": "r",
    "$cache/typescript": "rw",

    // private to this run; omit it to give the command no temp dir
    // "r" is degenerate on a fresh empty dir, so it is treated as "rw"
    // literal /tmp is the host's shared temp, not this one
    "$tmp": "rw"
  }
}
```

<Callout type="info">
On macOS, granting `$tmp` also grants Apple's fixed compiler-cache directory, so native (`node-gyp`) builds work — the only part of `$tmp` that is shared rather than private.
</Callout>

### `$tooldirs` (built-in cache set)

The `$tooldirs` set is the filesystem counterpart to `net`'s [`$trusted`](#trusted-built-in-host-set): it expands to the on-disk caches and stores of common developer tools — the package managers (nub, npm, pnpm, yarn, bun), git, and compiler caches — resolved to their real location on each OS. Because Nub's own store is among them, granting it read is the shorthand that lets a sandboxed command reach its installed dependencies.

```jsonc
{
  "fs": {
    "$tooldirs": "r",    // rw only if the command installs packages
    "./dist": "rw"
  }
}
```

The concrete paths differ per platform; the set resolves them for you, and the full mapping is versioned with the engine.

### Full glob support

Filesystem patterns support `*`, `**`, `?`, character classes, and brace expansion.

```jsonc
{
  "fs": {
    "packages/*/src": "r",
    "packages/**/dist": "rw",
    "logs/worker-?.log": "r",
    "certs/[ab].pem": "r",
    "logs/{app,worker}.log": "r"
  }
}
```

### Reuse another policy's rules

There is no implicit inheritance between policies. To splice another list in, reference it with a `...:` prefix followed by a JSON pointer into the current document. The pointer's list is inserted at that position, and ordering still applies.

```jsonc
{
  "shared": { "fs": ["./src", "$cache/tool"] },
  "sandbox": {
    "fs": ["...:#/shared/fs", "./dist"]
  }
}
```

The same pointer works as an object key, splicing another object's entries. Its value is the placeholder `true`, and spliced entries keep their own modes.

```jsonc
{
  "shared": { "fs": { "./src": "r", "./dist": "r" } },
  "sandbox": {
    "fs": {
      "...:#/shared/fs": true,
      "./dist": "rw"      // written after the spread, so it overrides
    }
  }
}
```

### Resolve a path with a command

A `$( … )` expression runs while the policy compiles, and its single-line output becomes the path. It runs the same POSIX shell on every OS — see [Nub Run](/docs/runner/run) for the shell Nub bundles.

```jsonc
{
  "fs": {
    "$(pnpm store path)": "r",
    "$(npm config get cache)/v3": "rw",   // literal text around the expression is fine
    "$(printenv MY_TOOL_DIR)": "r"        // how to read an env var into a path
  }
}
```

A key holds one `$( … )` expression. A failed command, empty output, multiple output lines, or an unterminated `$(` is an error.

### Env files are blocked in a policy you write

<Callout type="warn">
A policy you write never grants read access to a `.env*` file. The block is the highest-precedence rule on the filesystem axis — no directory grant, glob, or exact path can reopen it.
</Callout>

A broad grant reads the rest of the directory but never the `.env*` files inside it.

```jsonc
{
  // ./.env, ./.env.local, etc. stay denied
  "fs": { "./": "r" }
}
```

The block covers the workspace root and each project root. To pass a value from a `.env` file into a command, read the file yourself and hand it in through `vars` — or `secrets`, to broker it (both below).

#### The build jail works differently

The `build-jail` preset carries no deny rules at all. Neither Landlock on Linux nor AppContainer on Windows can express "deny inside allow", so the preset is a pure allowlist: it withholds a path by never granting it, rather than by blocking it.

That changes what the rule above buys you there. A dependency build script reads any `.env*` file sitting inside a directory the jail already grants it — its own package directory, and the dependency tree it may read. Everything outside those subtrees stays unreachable, your home directory included, because nothing grants it.

So for build scripts the guarantee is the shape of the grant rather than a separate block layered on top: a script reaches its own package and its dependencies, and nothing else. Keep credentials out of a dependency's own directory, and prefer `vars` or `secrets` over an on-disk file for anything a build step needs.

## `net`

The `net` axis controls outbound network access. Fine-grained rules are enforced by a local egress proxy that Nub starts automatically; a non-cooperating program that dials a raw socket fails closed rather than escaping.

### Allow everything or nothing

```jsonc
{ "net": true }   // any host — public, private, and host-local alike
```

```jsonc
{ "net": [] }     // deny all outbound access
```

Inside a list, a bare `*` is the same allow-everything rule, and it takes deny rules after it.

<Callout type="warn">
Cloud-metadata and link-local addresses (for example `169.254.169.254`, the endpoint behind the Capital One breach) are always blocked, even under `"*"`. It is the highest-precedence rule on the network axis and cannot be reopened.
</Callout>

### Allow specific hosts

A list allows only the hosts it names; everything else — including private ranges and loopback — is denied.

```jsonc
{ "net": ["registry.npmjs.org", "api.github.com"] }
```

### `$trusted` (built-in host set)

The `$trusted` set expands to a curated set of read-only developer hosts — artifact CDNs, package mirrors and indexes, language and OS distribution servers, and vendor documentation. Use it as a base and name your own hosts alongside it.

```jsonc
{ "net": ["$trusted", "api.mycompany.com"] }
```

Membership follows one rule: a host must be read-only to the sandboxed command, because reaching a host you can write to is indistinguishable from exfiltrating to it. That leaves out the forges and their APIs, registries whose publish endpoint answers on the same hostname, container registries, telemetry ingest, and multi-tenant object stores like `*.amazonaws.com`. A project that needs one names it directly, as in the [specific-hosts example](#allow-specific-hosts) above.

Three entries are kept despite failing that rule, because each is load-bearing: `registry.npmjs.org` (reading it is how packages install at all), `api.anthropic.com`, and `claude.ai`. A write to each is a request to the same hostname the legitimate use reads from — `npm publish` is a PUT to the registry, and a model API call carries its payload in the body — and a host allowlist cannot separate the two.

<Callout type="warn">
Treat `$trusted` as protection against a script reaching an *unexpected* destination, not as a guarantee that a script holding a valid token cannot use it. Scope credentials with [secrets](#secrets) rather than relying on the host list alone.
</Callout>

### `$downloads` (built-in host set)

The `$downloads` set expands to the hosts that dependency install scripts download their own binaries from. Any policy that runs an install can use it.

```jsonc
{ "net": ["$downloads"] }
```

The set is small and stays that way. A host earns a place only if an install-lifecycle script actually fetches from it — a real `preinstall`/`install`/`postinstall`, or the implicit `node-gyp rebuild` npm runs for a package shipping a `binding.gyp`. Today that is Node's own download server, `binaries.prisma.sh`, and the two Cypress hosts. A download you trigger by hand afterwards, such as `playwright install`, is not part of an install.

Membership follows the same exfiltration rule as `$trusted`, applied more strictly: no host that accepts an authenticated write, and no multi-tenant object store. It inherits none of the three exceptions above, because the code it confines is your dependencies' rather than your own.

Every entry is an exact hostname. That is a security property rather than a formatting choice: the proxy resolves the hostname itself, so a subdomain wildcard would let a confined script put chosen bytes in a DNS label and leak them through the resolver without sending a request at all.

On Windows a per-host rule needs the dedicated-account backend, which one elevated `nub setup-sandbox` installs. Until the machine is provisioned, a policy naming hosts fails closed rather than widening to coarse egress.

<Callout>
Some install scripts still cannot be covered by any allowlist. Packages such as `puppeteer`, `electron`, and `@tensorflow/tfjs-node`, plus everything built on `prebuild-install` or `node-pre-gyp`, fetch from Google Cloud Storage buckets or GitHub release assets — a multi-tenant store and a write-capable forge. Allowing either would reopen the exfiltration route the set exists to close, so those downloads stay blocked until Nub can fetch them on the script's behalf.
</Callout>

The list ships with the engine and grows by pull request. If a package you depend on downloads from a host that is missing, open one with the package name, the file in its install script that builds the URL, and confirmation that the host takes no authenticated write.

### Allow a domain and its subdomains

A leading `*.` matches subdomains at any depth, but not the apex. List the apex separately to allow it too.

```jsonc
{
  "net": [
    "example.com",     // the apex
    "*.example.com"    // api.example.com, a.b.example.com — not notexample.com
  ]
}
```

A bare `*` and a leading `*.` are the only host wildcards.

### Allow an IP range

Rules match on the resolved address, so a hostname that resolves into a denied range is still blocked.

```jsonc
{ "net": ["203.0.113.0/24", "2001:db8::/32"] }
```

### Reach private or local networks

Within a named allowlist, private ranges and host loopback are denied unless you name them.

```jsonc
{
  "net": [
    "api.example.com",
    "10.0.5.0/24",   // a private range
    "localhost"      // host-local services
  ]
}
```

### Deny a host

```jsonc
{
  "net": [
    "*",
    "!*.tracking.example",   // subdomains only, same as a *. allow
    "!tracking.example"      // add the apex to deny it too
  ]
}
```

### Reuse another policy's rules

Splice a list in with `...:` and a JSON pointer, or use the same pointer as an object key.

```jsonc
{
  "shared": { "net": ["registry.npmjs.org"] },
  "sandbox": {
    "net": ["...:#/shared/net", "api.example.com"]
  }
}
```

## `vars`

The `vars` axis controls the non-secret environment variables the child sees. Nub builds a fresh environment from the allowed entries, on top of a small safe baseline (`PATH`, `HOME`, `LANG`, `TERM`, `TZ`, and the OS-startup keys a process needs to launch) that always passes. Sensitive values go in [`secrets`](#secrets) instead.

<Callout type="info">
The `vars` and `secrets` keys both govern environment variables — the split is sensitivity, not mechanism. On-disk `.env*` files are a separate filesystem floor (see [Env files are blocked in a policy you write](#env-files-are-blocked-in-a-policy-you-write)); to use a value from one, read it and pass it in here.
</Callout>

### Pass everything or nothing

```jsonc
{ "vars": "*" }   // all ambient variables
```

```jsonc
{ "vars": [] }    // only the safe baseline
```

### Pass selected variables

Array entries are name globs, and a missing variable is not an error.

```jsonc
{ "vars": ["NODE_ENV", "CI", "VITE_*"] }
```

### Strip selected variables

```jsonc
{ "vars": ["*", "!*_TOKEN", "!*_SECRET", "!AWS_*"] }
```

A denylist is convenient but leaky, since secret names vary. An explicit allowlist is safer.

### The object form

Switch to the object form to validate, require, or strip a variable. This is the same syntax `secrets` uses — only `brokerTo` is secrets-only.

```jsonc
{
  "vars": {
    "DATABASE_HOST": true,           // pass it, any value
    "DEBUG": false,                  // strip it — the array !name form
    "PORT": { "format": "port" },    // an extras object
    "VITE_*": true                   // a glob key
  }
}
```

### `format`

Validate the value against a type: `string`, `integer`, `number`, `port`, a `/regex/`, or an `enum:a|b|c` list. A `number` must be finite; a `port` an integer from 1 to 65535.

```jsonc
{
  "vars": {
    "PORT": "port",                    // shorthand for { "format": "port" }
    "REGION": "/^[a-z]{2}-[a-z]+-\\d$/",
    "LOG_LEVEL": "enum:debug|info|warn|error"
  }
}
```

### `optional`

A plain key is required and fails compilation if the variable is absent.

```jsonc
{
  "vars": {
    "DATABASE_HOST": true,                       // required
    "LOG_LEVEL?": "enum:debug|info|warn|error",  // optional
    "VITE_*": true                               // glob keys are always optional
  }
}
```

In the object form the same marker is `optional: true`. It is environment-only — the `fs` and `net` axes have no required-to-exist check for it to relax, since a granted path needn't exist yet and a missing deny is a no-op.

## `secrets`

The `secrets` axis carries sensitive environment variables. The child receives the real value, but Nub scrubs that value from the command's stdout and stderr before forwarding them, and never prints a secret's value in its own errors. A secret can also be brokered so the child never holds the real value at all.

<Callout type="warn">
Scrubbing is log hygiene, not containment. A command that writes a secret elsewhere — the network, a file, a descriptor Nub does not forward — can still surface it. On an interactive terminal the value is shown as it would be on a plain run.
</Callout>

### Name the secrets

```jsonc
{ "secrets": ["DATABASE_URL", "STRIPE_KEY"] }
```

### Validate or require a secret

The object form takes the same `format` and `optional` keys as `vars`.

```jsonc
{
  "secrets": {
    "DATABASE_URL": { "format": "string" },
    "STRIPE_KEY?": true
  }
}
```

### Broker a secret to specific hosts

Add `brokerTo` and the child receives a random marker instead of the real value — see [Credential brokering](#credential-brokering) for how the swap works.

```jsonc
{
  "net": ["api.github.com"],    // required: brokering needs a named host to swap on
  "secrets": {
    "GITHUB_TOKEN": { "brokerTo": ["api.github.com"] }
  }
}
```

Brokering runs in the egress proxy, and only a fine-grained allowlist starts one. Both `"net": true` and an empty `net` are rejected:

```
sandbox.secrets.GITHUB_TOKEN.brokerTo: a brokered secret needs a fine-grained `net`
allowlist that names its host; `net: true` (unrestricted) and an all-deny `net` start
no proxy to perform the marker→secret swap
```

## Credential brokering

Brokering lets a command authenticate to a host without ever holding the real secret. At startup Nub replaces the secret, in the child's environment, with a random marker. The child puts the marker in a request header value; when Nub's proxy sees that marker in a header sent to a brokered host, it swaps in the real value. A marker sent anywhere else stays an inert hash.

```jsonc
{
  "net": ["api.github.com"],
  "secrets": {
    "GITHUB_TOKEN": { "brokerTo": ["api.github.com"] }
  }
}
```

A dependency that reads `GITHUB_TOKEN` and posts it to another host leaks only the marker. Substitution happens in request header values only — Nub never adds a header the child didn't send, and a marker in the request target, query string, or body passes through unreplaced.

## Composition and nesting

A policy is a complete, self-contained statement — there is no implicit inheritance from a global or project scope. Reuse is always explicit, through a `...:` pointer or a file reference.

A policy names the axes it confines, and an omitted axis allows nothing.

```jsonc
{ "fs": ["./dist"] }   // identical to spelling out empty net, vars, and secrets
```

When one sandboxed process launches another, the child runs inside its parent's confinement — whatever the child's own policy requests, it never widens what the parent already allows.

## Complete examples

### Build without network access

```jsonc title="sandbox.jsonc"
{
  "fs": {
    "./src": "r",
    "./package.json": "r",
    "./dist": "rw",
    "$tmp": "rw"
  },
  "net": [],
  "vars": {
    "PATH": true,
    "NODE_ENV?": "enum:development|production",
    "CI?": "string"
  }
}
```

### Development server

```jsonc title="sandbox.jsonc"
{
  "fs": {
    "./": "r",
    "./.next": "rw",
    "$cache": "rw",
    "$tmp": "rw"
  },
  "net": ["api.example.com", "*.sentry.io", "localhost"],
  "vars": {
    "NODE_ENV": "enum:development|production",
    "PORT?": "port"
  },
  "secrets": {
    "DATABASE_URL": true
  }
}
```

### Agent sandbox with a brokered token

```jsonc title="sandbox.jsonc"
{
  "fs": {
    "/": "r",
    "./": "rw",
    "./.git/config": false
  },
  "net": ["api.github.com", "localhost"],
  "secrets": {
    "GITHUB_TOKEN": { "brokerTo": ["api.github.com"] }
  }
}
```
