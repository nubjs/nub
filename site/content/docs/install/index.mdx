Nub has its own install engine: it resolves the dependency graph, writes the lockfile, and links `node_modules`. Its CLI follows pnpm's, so the verbs and flags are the ones you already type.

```bash
nub install               # install what package.json declares
nub add react react-dom   # add dependencies
nub update --latest       # move ranges to the newest release
nub dedupe                # collapse duplicate versions
```

A project Nub owns gets a `nub.lock`. In a repo that already uses npm, pnpm, Yarn, or Bun, Nub installs with that tool's lockfile instead — see [lockfile compatibility](#lockfile-compatibility).

## CLI

Each command takes pnpm's flags, with the same spelling.

### `nub install`

Resolves the graph and links `node_modules`:

```bash
nub install                      # alias: nub i
nub install --frozen-lockfile    # fail if the lockfile is out of date
nub install -P                   # --prod / --production
nub install -D                   # dev only
nub install --node-linker hoisted
nub ci                           # clean install from the lockfile
nub ci -P                        # clean install, no devDependencies
```

The accepted flags are pnpm's spellings:

```bash
--frozen-lockfile / --no-frozen-lockfile / --prefer-frozen-lockfile
--prod, -P            # production install
--dev, -D
--ignore-scripts
--pnpmfile <path>     # run this one instead of the project's
--global-pnpmfile <path>
--ignore-pnpmfile
--no-optional
--offline / --prefer-offline
--lockfile-only
--force
--node-linker
--registry
--dir, -C             # pnpm's spelling, not npm's --prefix
--reporter <name>     # default, append-only, silent
--silent, -s          # alias for --reporter=silent
--loglevel <level>    # debug, info, warn, error, silent
--os <os>             # which platforms' optional deps to install
--cpu <arch>
--libc <libc>
```

Packages like `esbuild` and `rollup` ship one prebuilt binary per platform as optional dependencies, and an install picks the one matching the current machine. Pass `--os`, `--cpu`, or `--libc` to pick a different one, for example when building a Linux container image on a Mac:

```bash
nub install --os linux --cpu x64        # Linux x64 binaries
nub install --os linux                  # Linux binaries, host CPU
nub install --os current,linux          # this machine and Linux
nub install --os '*' --cpu '*'          # every platform variant
```

Each flag is repeatable and takes a comma-separated list. A flag overrides `supportedArchitectures` for the axis it names, for that run only.

Three flags control output. Each works on every install-family command, before or after the verb:

```bash
nub install --silent                # -s: only fatal errors
nub install --reporter=append-only  # no live progress, keeps the summary
nub install --loglevel error        # hide warnings
```

In a workspace, `install` and `ci` take the same selector flags as [script running](/docs/run):

```bash
--filter <sel>, -F        # pnpm's selector grammar
--recursive, -r           # every workspace package
--filter-prod <sel>       # selector, production deps only
--include-workspace-root  # add the root package to the recursive set
--fail-if-no-match        # error if the filter selects zero packages
```

### `nub add`

Resolves a package, links it, and writes the dependency into `package.json`:

```bash
nub add <pkg>                  # alias: a
nub add -D <pkg>               # --save-dev
nub add -E <pkg>               # --save-exact (pin, no ^)
nub add -O <pkg>               # --save-optional
nub add --save-peer <pkg>      # peer + dev dependencies (pnpm parity)
nub add -g <pkg>               # global install
nub add -w <pkg>               # write to the workspace root
nub add --save-catalog <pkg>   # add into the workspace catalog
nub add --allow-build=<pkg>    # pre-approve its build scripts
nub add --no-save <pkg>        # link without persisting to package.json
nub add <pkg>@<version>        # pin an exact version
nub add <pkg>@<version> --lockfile-only  # refresh the lockfile only
```

### `nub remove`

Drops a dependency from `package.json` and relinks `node_modules`:

```bash
nub remove <pkg>           # rm / uninstall / un / uni
nub remove -D <pkg>        # remove only from devDependencies
nub remove -g <pkg>        # remove a global package
nub remove -w <pkg>        # remove from the workspace root
```

### `nub update`

Re-resolves dependencies within their ranges. With `--latest`, it rewrites the `package.json` ranges to the newest versions:

```bash
nub update                 # up — refresh all deps within range
nub update <pkg>           # update a single dependency
nub update <pkg>@<version> # pin one dep, keeping its ^/~ operator
nub update <pkg>@<tag>     # move one dep to a dist-tag, exact
nub update -i              # --interactive: pick each package's target
nub update -L              # --latest: move past the manifest range
nub update -E -L           # pin the rewritten range to an exact version
nub update -D              # devDependencies only
nub update -P              # production only
nub update --lockfile-only # refresh the lockfile, leave node_modules alone
```

The interactive picker shows one row per outdated dependency:

```text wide
Choose dependency updates
                                         keep             latest in range   latest
  dependencies
❯   @effect/opentelemetry@^4.0.0-beta.1  ■ 4.0.0-beta.90  □ 4.0.0-beta.100  □ 4.0.0-beta.100
    chalk@^4.1.0                         ■ 4.1.0          □ 4.1.2           □ 5.6.2
    react@^17.0.0                        ■ 17.0.1         □ 17.0.2          □ 19.2.8
  devDependencies
    typescript@~5.3.0                    ■ 5.3.2          □ 5.3.3           □ 7.0.2
↑/↓ move · space/←/→ cycle · a cycle all · / filter · enter apply · esc cancel
```

- Space, `←`, or `→` cycles a row between the current version, the newest version inside the range, and the registry's `latest`.
- Nothing is selected by default. Enter updates only the rows you changed.
- Targets are colored by semver impact.
- Each spec keeps its style: a `^` range stays `^`, and an exact pin stays exact.

### `nub dedupe`

Collapses duplicate versions in the lockfile to fewer, shared resolutions:

```bash
nub dedupe          # rewrite the lockfile with deduped resolutions
nub dedupe --check  # CI: exit non-zero if dedupe would change anything
```

### `nub import`

Converts another package manager's lockfile to `pnpm-lock.yaml`, without installing:

```bash
nub import          # package-lock / yarn.lock / bun.lock → pnpm-lock
nub import --force  # overwrite an existing pnpm-lock.yaml
```

### Other commands

The rest of pnpm's verb set:

```text
why          outdated      list, ls
patch        patch-commit  patch-remove
approve-builds  prune      rebuild
fetch        link, unlink  audit
licenses     bin           root
store        config        pkg
publish      pack          dlx          create
```

The [package meta-manager](/docs/pm), `nub pm`, is a separate tool. It fetches and runs the exact pnpm, npm, or Yarn release a project pins, as corepack does.

## Global installs

Passing `-g` installs a package for your user rather than a project, and links its executables onto your `PATH`:

```bash
nub add -g cowsay          # or: nub install -g cowsay
cowsay hello

nub remove -g cowsay
```

| | Default | Purpose |
| --- | --- | --- |
| Executables | `~/.local/bin` | Shared with every tool that installs there, and already on `PATH` on most systems |
| Packages | `$XDG_DATA_HOME/nub/global` | Nub's own, beside the content store |

Nub picks the executable directory from, in order:

- `XDG_BIN_HOME`
- `$XDG_DATA_HOME/../bin`
- `~/.local/bin`

Point it elsewhere with a setting:

```bash
nub config set --global global-bin-dir ~/bin
```

Run `nub bin -g` to print the directory in use, and `nub root -g` for where the packages live.

### PATH setup

Most Linux distributions already put `~/.local/bin` on `PATH`; macOS does not. When the directory is missing from `PATH` after a global install, Nub adds it to your shell profile and says so:

```console
$ nub add -g cowsay
Linked 2 bins into /Users/you/.local/bin
  PATH: added /Users/you/.local/bin to /Users/you/.zshrc
  Restart your shell, or source that file, to pick it up.
```

Nub writes the line once, under a `# nub global bin` marker, for bash, zsh, and fish. When it cannot write a profile, it prints the line to add by hand.

### Name collisions

The executable directory is shared, so a name may already be taken. Nub replaces an entry only when it created that entry itself; otherwise it keeps your file and says what it skipped:

```console
$ nub add -g cowsay
warning: not linking cowsay — /Users/you/.local/bin/cowsay already
exists and was not created by this tool; remove it to link cowsay
```

## Resolution

Resolution decides which version of each package ends up in the graph. Every field below lives in `package.json`.

### `overrides`

Force one version of a package everywhere in the graph. A selector is a bare name, a name with a range to match, a path that scopes the pin to one parent, or `$name` to reuse your own dependency's range.

```json title="package.json"
{
  "overrides": {
    "is-number": "7.0.0",
    "is-number@^6.0.0": "7.0.0",
    "is-odd>is-number": "7.0.0",
    "semver": "$semver"
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/settings/dependency-resolution#overrides) on pnpm.io.
</Callout>

### `resolutions`

The same pins in Yarn's spelling, with the same selectors. When both fields pin a package, `overrides` wins.

```json title="package.json"
{
  "resolutions": {
    "is-odd>is-number": "7.0.0"
  }
}
```

<Callout>
Read the [full docs](https://yarnpkg.com/configuration/manifest#resolutions) on yarnpkg.com.
</Callout>

### `packageExtensions`

Patch a dependency's own manifest at resolve time, adding to its `dependencies`, `optionalDependencies`, `peerDependencies`, or `peerDependenciesMeta`. Use it when a published package declares a peer it doesn't need, or omits one it does. An extension only adds what is missing and never replaces a declared range.

```json title="package.json"
{
  "packageExtensions": {
    "react-server-dom-webpack@19.2.7": {
      "peerDependenciesMeta": {
        "react": { "optional": true }
      }
    }
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/settings/dependency-resolution#packageextensions) on pnpm.io.
</Callout>

The top-level field applies in a Nub-owned project. A pnpm project uses `pnpm.packageExtensions`, and a Yarn project uses `packageExtensions` in `.yarnrc.yml`.

Nub also applies a bundled database of these repairs, so most undeclared dependencies resolve with no configuration. It covers what Nub's phantom detector finds across the 10,000 most-downloaded packages on npm, plus every rule from Yarn's curated database. It ships separately as [@nubjs/extensions](https://www.npmjs.com/package/@nubjs/extensions) for other tools to read.

```ini title=".npmrc"
# resolve every manifest exactly as published, repairing nothing
ignore-compatibility-db=true
```

### `patchedDependencies`

Apply a patch file to a package's contents, keyed by name and version. Running `nub patch <pkg>` writes both the patch and this entry. A key that matches no installed package fails the install.

```json title="package.json"
{
  "patchedDependencies": {
    "is-odd@3.0.1": "patches/is-odd@3.0.1.patch"
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/cli/patch#patcheddependencies) on pnpm.io.
</Callout>

### `workspaces`

Monorepo member globs. Members resolve to each other through a `workspace:` specifier instead of the registry.

```json title="package.json"
{
  "workspaces": ["packages/*"]
}
```

<Callout>
Read the [full docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#workspaces) on docs.npmjs.com.
</Callout>

### `workspaces.catalog`

Name a version once and let every member reference it. The default catalog is `catalog:`, and a named catalog is `catalog:<name>`. A reference to an undefined entry fails the install.

```json title="package.json"
{
  "workspaces": {
    "packages": ["packages/*"],
    "catalog": { "react": "19.2.0" },
    "catalogs": { "testing": { "vitest": "3.2.4" } }
  }
}
```

```json title="packages/app/package.json"
{
  "dependencies": { "react": "catalog:" },
  "devDependencies": { "vitest": "catalog:testing" }
}
```

<Callout>
Read the [full docs](https://pnpm.io/catalogs) on pnpm.io. The `catalog:` syntax matches pnpm's; the definitions live in `package.json` rather than `pnpm-workspace.yaml`.
</Callout>

### `allowScripts`

Which dependencies may run install scripts — see [lifecycle scripts](#lifecycle-scripts). The field applies in every project, whichever tool owns it.

```jsonc title="package.json"
{
  "allowScripts": {
    "esbuild": true,  // a registry dep, by name
    "sharp": false,   // a denial beats any allow

    // anything else, by full specifier
    "buildy@file:./buildy-1.0.0.tgz": true
  }
}
```

<Callout>
Version 12 of npm gates its own install scripts on this same field, so one map covers both tools. Read npm's [approve-scripts docs](https://docs.npmjs.com/cli/v12/commands/npm-approve-scripts).
</Callout>

### `dependenciesMeta`

Per-dependency flags. Setting `injected` hard-copies a workspace dependency instead of linking it, and `built: false` denies that package's install scripts.

```json title="package.json"
{
  "dependenciesMeta": {
    "ui": { "injected": true },
    "esbuild": { "built": false }
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/package_json#dependenciesmeta) on pnpm.io.
</Callout>

### `peerDependenciesMeta`

Mark one of your own peer dependencies optional, so a consumer that doesn't install it gets no error.

```json title="package.json"
{
  "peerDependencies": { "react": "^19.0.0" },
  "peerDependenciesMeta": {
    "react": { "optional": true }
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/package_json#peerdependenciesmeta) on pnpm.io.
</Callout>

### `allowedDeprecatedVersions`

Which deprecated versions may resolve without a warning, by package and range.

```json title="package.json"
{
  "allowedDeprecatedVersions": {
    "request": "*",
    "lodash": "<4.0.0"
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/settings/dependency-resolution#alloweddeprecatedversions) on pnpm.io.
</Callout>

### `engines`

The Node and package-manager versions the project requires. Nub provisions the Node named here, and `engineStrict` decides whether a mismatch warns or fails.

```json title="package.json"
{
  "engines": {
    "node": ">=22.15"
  }
}
```

<Callout>
Read the [full docs](https://pnpm.io/package_json#engines) on pnpm.io.
</Callout>

## Layout

The default `node_modules` layout is isolated under every incumbent: direct dependencies sit at the top level, and everything else links from a virtual store. A project that relies on undeclared (phantom) dependencies can switch to npm's flat layout:

```ini title=".npmrc"
node-linker=hoisted
```

The `--node-linker hoisted` flag does the same for one command, and [`install.linker`](/docs/config#installlinker) sets it in `nub.jsonc`. When an undeclared package fails to resolve at runtime, Nub's error names it and points at this setting.

[Store and layout](/docs/install/virtual-store) covers the shared store, the hoisting settings, and where Nub keeps packages on disk.

## Lifecycle scripts

Dependencies can declare `preinstall`, `install`, and `postinstall` scripts. Nub denies them by default, and you allow the packages that may build:

```bash
nub approve-builds                # approve packages, then build them
nub add --allow-build=<pkg> <pkg> # pre-approve as you add it
nub rebuild                       # re-run already-approved scripts
nub install --ignore-scripts      # skip dependency build scripts
```

Approving builds runs the approved packages' scripts in the same invocation, as pnpm does. No follow-up install is needed.

Permission comes from the [`allowScripts`](#allowscripts) field in any project. A project owned by another package manager can also use that tool's own field:

- pnpm: `pnpm.onlyBuiltDependencies`, `pnpm.allowBuilds`
- Bun: `trustedDependencies`

A package with build scripts that is not allowed is skipped. The `WARN_NUB_IGNORED_BUILD_SCRIPTS` warning names it and suggests `nub approve-builds`.

### Build failures

A failed build fails the install. The exception is a package reachable only through `optionalDependencies`: its failure is reported and the install continues, as in npm and pnpm.

```console
# captured: nub 0.7.5, optfail@1.0.0 postinstall exits 3, allowScripts set
$ nub install
WARN optfail@1.0.0 is an optional dependency and failed to build;
     continuing without it: lifecycle script postinstall failed for
     optfail@1.0.0: script `postinstall` exited with code 3
     code=WARN_NUB_OPTIONAL_BUILD_FAILED
optionalDependencies:
+ optfail@1.0.0
```

A package that anything depends on through a normal dependency is required, even if another package depends on it optionally. The warning appears only on the install that ran the build. Run `nub rebuild <pkg>` to try the build again.

### Default-trust floor

A curated set of well-known packages, such as `esbuild`, may build without approval. All three gates must hold:

| Gate | Requirement |
|---|---|
| **Registry provenance** | Resolved from a registry. Git, file, link, tarball, and npm-alias specifiers never qualify. |
| **Advisory vetting** | The [advisory check](#advisory-gate) ran against this graph, or the graph came from an already-checked lockfile (a frozen install, `nub ci`, a teammate's clone). |
| **Cooling window** | The version is older than the [cooling window](#cooling-window). An unknown publish time fails the gate. |

Explicit decisions outrank the floor: a package you approve always builds, and an explicit denial always wins.

A fresh resolve, or a lockfile Nub wrote, carries the publish times the floor needs:

```console
# captured: nub 0.0.44, pnpm, esbuild@0.21.5 — no allowScripts entry
$ nub install
WARN defaultTrust: running build scripts for esbuild@0.21.5  # ✓ gates ok
dependencies:
+ esbuild@0.21.5
```

When a gate fails, the package is skipped like any other unapproved build:

```console
# captured: nub 0.0.44, esbuild — minimumReleaseAge set past every release
$ nub install
WARN ignored build scripts for 1 package(s): esbuild@0.21.5.
     Run `nub approve-builds` to review and enable them.
     code=WARN_NUB_IGNORED_BUILD_SCRIPTS   # ❌ cooling gate closed
dependencies:
+ esbuild@0.21.5
```

A foreign lockfile with no publish times, such as `bun.lock`, fails the cooling gate the same way (see the [Bun page](/docs/install/bun#install-behavior)).

## Supply-chain checks

Three checks apply when Nub resolves a new version: a minimum age, a malware advisory lookup, and a comparison of publishing evidence.

### Cooling window

A registry version must be older than `minimumReleaseAge`, 24 hours by default, before Nub installs it. When nothing in the range is old enough, the install fails.

Adding a package without naming a version resolves to the newest release that clears the window:

```console
$ nub add some-tool
+ some-tool@2.3.0  latest 2.4.0   # 2.4.0 is still inside the window
```

The `nub outdated` command follows the same rule, so it never offers a version inside the window.

Two flags adjust the window for one command:

```console
$ nub add some-tool
ERR_NUB_NO_MATURE_MATCHING_VERSION       # ❌ every version is too new

$ nub add some-tool --minimum-release-age=0                 # off, this run
$ nub add some-tool --minimum-release-age=2h                # or shorten it
$ nub add some-tool --minimum-release-age-exclude=some-tool # exempt one
```

The duration takes a unit (`s`, `m`, `h`, `d`, or `w`), and a bare number means minutes, as in pnpm. Both flags work on every command that installs, including [`nubx`](/docs/nubx).

The exclude flag replaces the configured `minimumReleaseAgeExclude` for that run, as in pnpm. Name every package you still need:

```console
$ nub add some-tool --minimum-release-age-exclude='@internal/*' \
    --minimum-release-age-exclude=some-tool
```

Publish dates come from the registry's `time` metadata:

| Registry metadata | Outcome |
|---|---|
| A publish date for the resolved version | Checked against the window |
| Dates for other versions, none for this one | Blocked |
| No per-version dates, document older than the window | Allowed |
| No per-version dates, document newer than the window | Blocked |

Some private mirrors and older Verdaccio releases publish no dates at all, so they fall under the last row. That refusal is `ERR_NUB_RELEASE_AGE_MISSING_TIME`, and `nub outdated` warns about it on stderr:

```console
$ nub outdated
warn: internal-pkg has no registry publish times, so minimumReleaseAge
      cannot admit any version; `nub update` will fail for it
All dependencies up to date.
```

Exempt the package, or turn the window off:

```ini title=".npmrc"
minimumReleaseAgeExclude=internal-pkg   # exempt one (comma-separated)
minimumReleaseAge=0                     # turn the window off
```

Nub also reads pnpm's `minimumReleaseAgeStrict=false`. That setting counts an undateable version as clearing the window, so the window looks enforced but is not. Prefer `minimumReleaseAge=0`.

### Advisory gate

On a fresh resolve, Nub checks the graph against OSV `MAL-*` advisories at `api.osv.dev`. A confirmed hit aborts the install with `ERR_NUB_MALICIOUS_PACKAGE`. When osv.dev is unreachable, the check warns and the install proceeds. To fail instead:

```ini title=".npmrc"
advisoryCheck=required
```

A frozen reinstall (`nub ci`, `--frozen-lockfile`, a teammate's clone) reuses the vetting recorded when the lockfile was written. The cooling and provenance gates still apply on every install.

### Trust downgrades

Nub compares a version's trust evidence with earlier releases of the same package: OIDC provenance, a trusted publisher, a staged-publish approval. A version with weaker evidence than an earlier-published version is refused. A pipeline that suddenly publishes without its usual attestation is a common sign of a stolen token.

Nub then takes the best version in the range that still carries the evidence, and names what it skipped:

```console
# captured: fast-glob → @nodelib/fs.walk → fastq; 1.20.2 hand-published
$ nub install
WARN skipped fastq@1.20.2 (trustPolicy=no-downgrade): earlier published
     version 1.20.0 had trusted publisher but this version has no trust
     evidence; resolved to fastq@1.20.1 instead
     code=WARN_NUB_TRUST_DOWNGRADE_SKIPPED
```

The substitute always satisfies the declared range. When no version in the range clears the check, the install stops with `ERR_NUB_TRUST_DOWNGRADE`. The check runs only when a version is newly resolved, so an install from an up-to-date lockfile trusts its recorded pins.

A maintenance release on an older major, published after a newer major adopted provenance, can trip the check. Versions older than 14 days are exempt. Adjust the check in `.npmrc`:

```ini title=".npmrc"
trustPolicyIgnoreAfter=20160        # exemption, minutes (default 14d)
trustPolicyExclude=tailwind-merge   # exempt one package regardless of age
trustPolicy=off                     # disable the check entirely
```

## Lockfile compatibility

In a repo that already uses npm, pnpm, Yarn, or Bun, Nub installs as that package manager: same lockfile format, same config files, same manifest fields. It writes no `nub.lock` there. Nub identifies the incumbent from, in order:

- `packageManager`
- `devEngines.packageManager`
- Lockfile on disk

In a workspace, Nub reads these at the root, from any member.

| Incumbent | Lockfile | Round-trip |
|---|---|---|
| **npm** — [docs →](/docs/install/npm) | `package-lock.json`, `npm-shrinkwrap.json` | read + write |
| **pnpm** — [docs →](/docs/install/pnpm) | `pnpm-lock.yaml` (v9) | read + write |
| **Yarn** — [docs →](/docs/install/yarn) | `yarn.lock` | **read-only** |
| **Bun** — [docs →](/docs/install/bun) | `bun.lock` | read + write |
| **Nub** — [docs →](/docs/pm) | `nub.lock` (pnpm v9 bytes) | read + write |

An install that leaves the graph unchanged leaves the lockfile untouched.

<Callout title="Optional">
The installer is optional. Keep running `npm`, `pnpm`, `yarn`, or `bun` as you do today, and use Nub for everything else — running files, scripts, and binaries.
</Callout>

A field the incumbent would ignore, Nub ignores too, and it says which field it skipped. In a pnpm project, a top-level `overrides` block changes nothing, because pnpm reads `resolutions` and `pnpm.overrides`:

```console
# captured: nub 0.7.2, pnpm project with a top-level overrides block
$ nub install
nub: `overrides` ignored — this project uses pnpm, which doesn't apply
it. move these pins to `resolutions`.
dependencies:
+ is-odd@3.0.1
```

Declaring the same pin in both fields stays silent. A Nub-owned project reads no tool's branded config, including `pnpm.*` fields, `pnpm-workspace.yaml`, and `.pnpmfile.cjs`. To keep pnpm hooks or pnpm workspace config active, keep the project pnpm-owned or run `nub pm use pnpm`.

### Layout settings

Nub does not read layout settings from an incumbent's branded config. It reads the rest of that config (registries, auth, resolution settings, overrides) as usual.

| Package manager | Its own layout settings | Under Nub |
|---|---|---|
| **npm** | `install-strategy`, `global-style`, `legacy-bundling` | Not read |
| **pnpm** | `nodeLinker`, `hoist`, `symlink`, and related keys in `pnpm-workspace.yaml` or global `config.yaml` | Not read |
| **Yarn** | `nodeLinker`, `nmHoistingLimits`, `nmMode` | Not read. Plug'n'Play is refused before any write, because Nub installs a `node_modules` tree |
| **Bun** | `linker`, under `[install]` in `bunfig.toml` | Not read |

Set layout with [`install.linker` and `install.publicHoist` in `nub.jsonc`](/docs/config#install), their `.npmrc` spellings, or command-line flags. These work under every incumbent. Nub warns when it finds a branded layout setting.

### Switching to Nub

Running `nub pm use nub` moves a project onto Nub: it migrates pnpm workspace config into the neutral `package.json` fields, aligns the manifest, and writes `nub.lock`. A first `nub install` in a project with no declaration and no lockfile does the same.

Either way, Nub records itself with a range rather than an exact pin:

```jsonc title="package.json"
{
  "devEngines": {
    "packageManager": {
      "name": "nub",
      "version": "^0.7.1",   // a floor, not a pin
      "onFail": "ignore"     // nothing enforces it
    }
  }
}
```

To pin an exact version that corepack can see, run `nub pm use nub@<version>`. Config that a Nub-owned project no longer reads produces a warning:

```console
# captured: Nub-owned project (nub.lock) with a stray pnpm-workspace.yaml
$ nub install
nub: pnpm-workspace.yaml is not read under nub identity — migrate it
     (`nub pm use nub`), delete it, or return to pnpm (`nub pm use pnpm`).
```

### Conflicting signals

When the signals disagree, Nub stops rather than guess. Two lockfiles for different managers are an error unless a declaration names one of them:

```console
$ nub install
Error: ERR_NUB_LOCKFILE_AMBIGUOUS

  × multiple lockfiles found: pnpm-lock.yaml, package-lock.json —
  │ cannot tell which package manager owns this project
  help: remove the stale lockfile, or run nub pm use <pm> naming a specific
        manager
```

A hosted builder that runs its own install beside your committed lockfile is a common cause. See [Cloudflare](/docs/deployment/cloudflare) for the build-level fix. In a Nub-owned project, `nub.lock` beside a foreign lockfile is the same error.

A declaration whose lockfile is missing is also an error:

```console
$ nub install   # packageManager: "pnpm@9.0.0"
Error: ERR_NUB_LOCKFILE_DECLARATION_MISMATCH

  × package.json declares `pnpm` (via `packageManager`), but
  │ pnpm-lock.yaml is missing — found package-lock.json instead
  help: nub pm use <pm> to declare it, or remove the stale lockfile
```
