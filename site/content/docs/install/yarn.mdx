---
title: Yarn
description: Nub installs and runs Yarn projects from their lockfile, Classic or Berry, but never writes it.
---

Yarn is supported read-only. Install and run work, and any command that would rewrite `yarn.lock` refuses before it touches anything:

```console
$ nub add lodash
Error: nub add: refusing to modify yarn.lock —
       adding a dependency re-resolves and rewrites yarn.lock
  Run it with yarn directly:
    yarn add lodash
```

## `yarn.lock`

Nub reads both lockfile formats: Classic (Yarn 1.x, no `__metadata` block) and Berry (Yarn 2+, with `__metadata`). These commands work:

```bash
nub install        # reads yarn.lock, links, runs lifecycle scripts
nub ci             # frozen: drift from yarn.lock is an error
nub run <script>   # runs package.json scripts
nubx <bin>         # one-off binary execution
```

Commands that change the dependency graph refuse. Run them with `yarn`:

```bash
nub add <pkg>       # → yarn add
nub remove <pkg>    # → yarn remove
nub update          # → yarn upgrade
nub dedupe          # → yarn dedupe
```

An `install` or `ci` that would rewrite the lockfile refuses the same way. That covers a Yarn project with no `yarn.lock` yet, a `yarn.lock` that no longer satisfies `package.json`, and the `--force`, `--no-frozen-lockfile`, and `--lockfile-only` flags. Run `yarn install` for those.

Nothing converts to `yarn.lock`. The `nub import` command produces a `pnpm-lock.yaml`:

```console
$ nub import        # in a yarn project
Imported 2 packages from yarn.lock to pnpm-lock.yaml
```

<Callout title="Pinning Yarn is a separate command">
The [meta-manager](/docs/pm) command `nub pm use yarn` pins classic (v1) Yarn in `packageManager` and converts a foreign lockfile to a classic `yarn.lock`. It refuses an existing Berry `yarn.lock`, a binary `bun.lockb`, and a `workspace:`-protocol graph. The install engine on this page never rewrites an existing `yarn.lock`.
</Callout>

## `.yarnrc.yml`

Nub reads the registry, auth, TLS, and proxy settings from `.yarnrc.yml`, plus `packageExtensions`:

```yaml title=".yarnrc.yml"
npmRegistryServer: https://registry.internal/
npmScopes:
  myorg:
    npmRegistryServer: https://npm.myorg.dev/
    npmAuthToken: "<token>"
npmRegistries:
  "https://npm.myorg.dev":
    npmAuthIdent: "user:pass"
```

- `npmRegistryServer` — the default registry; under `npmScopes.<scope>`, a scoped one
- `npmAuthToken`, `npmAuthIdent` — auth for a known registry, including `npmRegistries` entries; under `npmScopes`, only when that scope has its own unique registry
- `httpsCaFilePath` — the CA file; under `networkSettings.<host>`, a per-host CA
- `httpProxy`, `httpsProxy`, `enableStrictSsl` — proxy and strict SSL
- `packageExtensions` — dependency and peer metadata added to resolved packages

The matching `YARN_*` environment variables (registry, auth token and ident, CA, proxy, strict SSL) outrank `.yarnrc.yml`.

Nub reads the global `~/.yarnrc.yml` plus project `.yarnrc.yml` files from the workspace root down to the current directory. Nearer files win.

<Callout>
Read the [full docs](https://yarnpkg.com/configuration/yarnrc) on yarnpkg.com.
</Callout>

## `.yarnrc`

Classic Yarn's `.yarnrc` is read for its registry and auth keys, which are already npmrc-shaped:

```text title=".yarnrc"
registry "https://registry.internal/"
"@myorg:registry" "https://npm.myorg.dev/"
"//npm.myorg.dev/:_authToken" "<token>"
```

Discovery matches classic Yarn: the global `~/.yarnrc` plus project `.yarnrc` files from the filesystem root down to the current directory, nearer files winning. Only the default registry, scoped registries, and `_authToken` / `_auth` entries are read.

## `package.json`

Nub applies top-level `resolutions` the way Yarn does. Top-level `overrides` is npm and Bun's field, and Yarn ignores it, so Nub does too. Put pins in `resolutions`.

The `dependenciesMeta.*.built` field gates which packages run build scripts.

<Callout>
Read the [full docs](https://yarnpkg.com/configuration/manifest#resolutions) on yarnpkg.com.
</Callout>

## Install behavior

Yarn's `nodeLinker`, `nmHoistingLimits`, `nmMode`, and `YARN_NODE_LINKER` do not select the layout Nub installs. Set layout with [`install.linker` in `nub.jsonc`](/docs/config#installlinker), `node-linker` in `.npmrc`, or `--node-linker` for one command:

```ini title=".npmrc"
node-linker=hoisted
```

<Callout>
Read the [full docs](https://yarnpkg.com/configuration/yarnrc#nodeLinker) on yarnpkg.com.
</Callout>

Plug'n'Play is refused, because Nub installs a `node_modules` tree. Yarn Berry defaults to PnP when `nodeLinker` is absent, so both `nub install` and `nub ci` abort before writing anything, with `ERR_NUB_PNP_UNSUPPORTED`. Set `nodeLinker: node-modules` to install with Nub.

A project Yarn already installed in PnP mode still runs under Nub: `nub <file>`, `nub run`, and `nubx` honor `.pnp.cjs`. Install with `yarn`, run with `nub`. See [Plug'n'Play resolution](/docs/runtime/resolution#yarn-plugnplay).

## Gaps

- **No lockfile writes.** Commands that change the dependency graph run with `yarn`.
- **No Plug'n'Play installs.** Install with Yarn, or set `nodeLinker: node-modules`.
- **Per-host `networkSettings` proxies** are not read. The proxy Nub applies is process-wide.
- **Scoped and map-shaped `YARN_*` variables** are not translated.
- **Other `.yarnrc.yml` and `.yarnrc` keys** — constraints, plugins, patch-folder config, cache layout, `network-timeout`, `save-prefix`, and the rest — are ignored.
