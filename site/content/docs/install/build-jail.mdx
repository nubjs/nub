Nub runs approved dependency install scripts in a build jail. It is enabled by default on macOS, Linux, and Windows, with no setup command or administrator access.

```sh
nub install
```

## Operating-system support

Nub checks the facilities required by a policy when it acquires the jail. Linux filesystem confinement requires [Landlock](https://docs.kernel.org/userspace-api/landlock.html); per-host networking and self-process metadata require additional seccomp facilities. macOS uses Seatbelt. Windows uses AppContainer and extended process startup.

Linux coverage includes Ubuntu 24.04 x86-64 on kernel `6.17.0-1022-azure`. macOS coverage includes macOS 14.8.9 arm64. Windows compatibility sequences run on Windows Server 2022 x64 and Windows 11 arm64. Older Linux and Windows floors are not established.

An unavailable confinement facility reports a failed confined launch. The explicit Windows full-disk catalog grant is different: it intentionally omits AppContainer, as described in [Permissions](#permissions). Runtime coverage does not establish the loader floor for a released Nub binary.

macOS reaps descendants that remain in the command's process group. A descendant that deliberately leaves the group can survive while remaining Seatbelt-confined. The build jail has no detached-command operation.

## Build approval

Approval decides which dependencies may run scripts. The build jail limits the access those scripts receive.

```sh
nub approve-builds
```

The command records approval and runs the approved scripts. To declare approval in the project's `package.json`:

```json title="package.json"
{
  "allowScripts": {
    "esbuild": true,
    "sharp": true
  }
}
```

These entries approve scripts without disabling the build jail. See [lifecycle scripts](/docs/install#lifecycle-scripts) for approval rules and the default-trust floor.

## Permissions

Each script receives access to its package directory and the tools needed to build it. Nub's package catalog selects additional filesystem permissions and whether the script may use the network.

- Build scripts run on plain Node.
- Credential variables such as `NPM_TOKEN` and `AWS_SECRET_ACCESS_KEY` are removed.
- Scripts receive a build-specific home and temporary directory.
- Root-project scripts, such as `prepare`, run with the project's ordinary permissions.

Catalog networking is an allow/deny switch, not a hostname allowlist. Recorded download hosts do not restrict a script's connections. Packages without a matching catalog entry receive the baseline policy, which allows outbound networking; a catalog entry can deny it. On Windows, the coarse network allow covers public outbound connections, not unrestricted LAN or loopback access.

The jail reduces exposure to malicious install scripts; it is not isolation for arbitrary untrusted code. On Windows, a full-disk catalog grant omits the AppContainer. That launch has no operating-system filesystem or network boundary, but environment filtering and process cleanup remain.

### Automatic filesystem grants

Nub selects catalog permissions by package name, version, and operating system when it compiles a build script's policy. Filesystem grants are positive: a directory grant includes the directory and its descendants. Nub does not enumerate siblings to exclude credential locations.

| Catalog grant | Expansion |
| --- | --- |
| Read the disk | Grant filesystem reads, including readable credential files. |
| Read or write the real user home | Grant the real home directory and its descendants, including credential locations. |
| Write the disk | Remove filesystem confinement; no credential-location exclusion remains. |

These are internal catalog permissions, not settings in a dependency's `package.json`. The real user home is distinct from the build-specific home assigned to the script.

For example, a real-home grant includes all of these paths:

```text
~/
  .ssh/                 included
  .config/
    gh/                 included
    editor/             included
  projects/             included
  notes.txt             included
```

Files created later inside a granted subtree are included too. Nub does not inspect their contents or subtract `.env`, `.npmrc`, SSH keys, or other named credential locations. Packages without a broad grant remain limited to their package, build-specific home, and other catalog-granted paths.

<Callout type="warn">
Filtering environment variables does not prevent reading credentials from an allowed file. A real-home or disk grant is a compatibility permission, not home access with secrets removed.
</Callout>

## Package exceptions

To run one dependency without the jail, set its approval to `"no-jail"` in the root project's `package.json`:

```json title="package.json"
{
  "allowScripts": {
    "native-addon": "no-jail"
  }
}
```

The package's scripts run with ordinary user access. Nub prints a notice; other dependencies retain their permissions.

For a local dependency, use its full specifier:

```json title="package.json"
{
  "allowScripts": {
    "native-addon@file:./native-addon": "no-jail"
  }
}
```

After changing an installed package's permissions, rerun its build scripts:

```sh
nub rebuild
```

## `install.buildJail`

The project-wide switch belongs in `nub.jsonc`. It defaults to `true`.

```json title="nub.jsonc"
{
  "install": {
    "buildJail": false
  }
}
```

Setting it to `false` removes the jail from every dependency build in the project. It does not approve scripts that were otherwise blocked.

User configuration supplies a default for all projects. Project configuration takes precedence.

```sh
nub config set install.buildJail false --global
nub config delete install.buildJail --global
```
