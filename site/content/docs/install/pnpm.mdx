description: In a pnpm project, Nub installs exactly as pnpm 12 does — the same lockfile bytes, the same node_modules layout, and pnpm's own configuration.
---

A project is a pnpm project when it has any one of these:

```text
"packageManager": "pnpm@<version>"   # in package.json
pnpm-lock.yaml
pnpm-workspace.yaml
```

In a pnpm project, `nub install` installs the way pnpm 12 does. The lockfile it writes is byte-identical to the one `pnpm install` writes, and the output names the pnpm that did the work:

```console
$ nub install
Packages: +2
++
Progress: resolved 2, reused 2, downloaded 0, added 2, done

dependencies:
+ is-odd 3.0.1

Done in 55ms using pnpm v12.4.1
```

## What matches pnpm

Everything about the install follows pnpm's own rules:

| | In a pnpm project |
|---|---|
| Lockfile | `pnpm-lock.yaml`, the bytes pnpm writes |
| Layout | `node_modules/.pnpm`, inside the project |
| Global virtual store | Off, unless `enableGlobalVirtualStore: true` is set |
| Store | pnpm's store — `nub store path` and `pnpm store path` print the same directory |
| Settings | `pnpm-workspace.yaml`, the `.npmrc` chain, and pnpm's global config |
| Build scripts | pnpm's approval gate, configured with `allowBuilds` |

Settings live where pnpm 12 reads them. Layout keys such as `nodeLinker` and save keys such as `savePrefix` go in `pnpm-workspace.yaml`; the same keys in `.npmrc` have no effect, as in pnpm 12.

```yaml title="pnpm-workspace.yaml"
nodeLinker: hoisted
```

Environment variables follow pnpm 12 too. The registry comes from `pnpm_config_registry` or `PNPM_CONFIG_REGISTRY`, and `npm_config_registry` is not read.

<Callout>
Read the [full docs](https://pnpm.io/settings) on pnpm.io.
</Callout>

## Build scripts

A dependency with build scripts that is not approved fails the install, as it does under pnpm 12:

```console
$ nub install
Error: ERR_PNPM_IGNORED_BUILDS

  × installing dependencies
  ╰─▶ Ignored build scripts: core-js@3.45.1
  help: Run "pnpm approve-builds" to pick which dependencies should be allowed
        to run scripts.
```

Approve a package in `pnpm-workspace.yaml`:

```yaml title="pnpm-workspace.yaml"
allowBuilds:
  core-js: true
```

Every build needs that explicit decision. There is no list of packages trusted to build automatically.

## Version pins

A `packageManager` pin that names another pnpm version is honored. Nub provisions that version and runs the install with it:

```console
$ nub install   # "packageManager": "pnpm@10.15.1"
...
dependencies:
+ is-odd 3.0.1

Done in 705ms using pnpm v10.15.1
```

## `nub.jsonc`

A pnpm project takes its install settings from pnpm's configuration, so an `install` block in `nub.jsonc` is an error. See [`install`](/docs/config#install) for the message. The runtime fields of `nub.jsonc` apply as in any project.

## Switching to a Nub project

Running `nub pm use nub` turns a pnpm project into a Nub project. The lockfile is renamed with its bytes unchanged, and settings from `pnpm-workspace.yaml` move to neutral homes:

```console
$ nub pm use nub
using nub@0.9.0
  package.json: devEngines.packageManager =
    { name: "nub", version: "^0.9.0", onFail: "ignore" }
  package.json: top-level overrides migrated
  nub.lock: renamed from pnpm-lock.yaml
    (bytes unchanged — still pnpm-v9 format)
  pnpm-workspace.yaml: deleted (all keys migrated or named below)
  .npmrc: + node-linker=hoisted
  .npmrc: + save-prefix=~
```

Running `nub pm use pnpm` reverses the rename, and the lockfile bytes stay the same:

```console
$ nub pm use pnpm@12.4.1
using pnpm@12.4.1
  package.json: packageManager = pnpm@12.4.1 (+sha512)
  package.json: devEngines.packageManager =
    { name: "pnpm", version: "^12.4.1", onFail: "warn" }
  pnpm-lock.yaml: renamed from nub.lock (bytes unchanged)
```
