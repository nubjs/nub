Nub 0.9 adds `nub compile`, which bundles a TypeScript or JavaScript entrypoint into a single-file executable.

```console
$ nub compile cli.ts

    output  cli  29.5 MB  (node 28.3 MB · app 67 KB · launcher 1.1 MB)
   runtime  Node 26.8.1, embedded  (package.json#engines.node)
  platform  darwin-arm64
       app  extracted on first run  it extracts its embedded Node anyway
   elapsed  3.6s

$ ./cli --name nub
✔ hello, nub
```

The executable runs on a machine with no Node installed. Bun and Deno have had this for years. Node's version has been experimental since 19.7.0, and it leaves the bundling to you. Nub builds on stock Node instead. A hello world compiles to 29.5 MB on my MacBook; the same file under Bun is 63 MB.

## Prior art

Deno shipped [`deno compile`](https://deno.com/blog/v1.6) in December 2020. Bun added `bun build --compile` in [Bun 1.0](https://bun.sh/blog/bun-v1.0). Both work the same way: the bundled code is stapled onto a copy of the runtime, so the file is mostly runtime. Each operating system has its own place to put that payload:

1. **macOS** — a new Mach-O section. Adding one invalidates the code signature, so the file is re-signed afterward.
2. **Linux** — an ELF note section. No signing involved.
3. **Windows** — a PE resource, the same mechanism that stores an executable's icon.

Node's equivalent, [Single Executable Applications](https://nodejs.org/api/single-executable-applications.html), landed as an experiment in 19.7.0 and is still marked **Stability 1.1, "Active development"** today. The ergonomics have improved — Node 25.5.0 collapsed the multi-step injection flow into a single `node --build-sea` command — but SEA still doesn't bundle, and progress depends on contributor interest: [cross-platform generation](https://github.com/nodejs/single-executable/issues/94) has been an open request since April 2024, the [virtual-filesystem hooks](https://github.com/nodejs/node/issues/60021) that packagers ask for went stale this July, and the [SEA team's repo](https://github.com/nodejs/single-executable) has not changed since mid-2025.

Nub uses the same stapling. The runtime is a stock Node from nodejs.org, driven by a small Rust launcher.

## `nub compile`

Nub's augmentations — transpiler-level support for TypeScript, JSX and non-erasable syntax, YAML/TOML/JSONC imports, polyfilled globals like `Temporal` and the browser-style `Worker` — all happen during compilation. Nub is fully _erasable_; it compiles your inputs to something that can run against vanilla Node.js. The output carries no `node_modules` and needs no toolchain on the target machine. The Node it builds against comes from the project's existing pin — a `.node-version` file, or `engines.node` in `package.json`. An import the bundler can't resolve fails the build with the file and line.

The default shape embeds a full Node. A stock `node` binary is 145 MB on darwin-arm64; stripped and recompressed with zstd at level 19, it fits with your app in a 29.5 MB file:

### App size

A CLI built on `commander`, `chalk`, `ora` and `zod`:

```console
$ du -sh node_modules
8.6M	node_modules

$ nub compile cli.ts --smol --target lts --out cli

    output  cli  990 KB  (app 105 KB · launcher 885 KB)
   runtime  Node lts, not embedded  (--target; floor enforced at runtime)
  platform  darwin-arm64
       app  extracted on first run  its chunks import each other in a cycle
   elapsed  0.5s

$ ./cli --name nub
✔ hello, nub
```

Four dependencies and 8.6 MB of `node_modules` become 445 KB of bundled, tree-shaken, minified app, and 105 KB once compressed into the executable.

Nub is slowest in this chart. A stock `node` takes 34 ms on this machine before any user code runs, and a compiled binary adds about 12 ms on top. The launcher's own share is under 2 ms: it decodes the payload, checks the extracted tree, and replaces itself with Node, so the binary you launched is the process you end up with. The rest is Nub's runtime augmentation. The bootstrap preload and the preamble the bundler places ahead of your code install the same globals and polyfills that a file run through `nub` gets, which is the difference between a compiled binary and a plain `node` process.

### Assets

Imports of non-module files resolve at build time too:

```ts
import prompt from "./prompt.md";     // inlined into the bundle, as a string
import logo from "./logo.png";        // an absolute path to the extracted file

// a file named relative to the module resolves too
const table = readFileSync(new URL("./table.bin", import.meta.url));
```

A text file (`.md`, `.txt`) is inlined into the bundle, and the import evaluates to its contents as a string. A binary file ships inside the executable and is written out beside the bundle on first run, and the import evaluates to that file's absolute path. A literal `new URL(..., import.meta.url)` embeds the file it names, and the reference is rewritten to resolve at run time from any directory. Files nothing imports — templates, migrations, a data directory — ship with `--include`.

<Callout title="Computed paths">
A CommonJS dependency bundled into the output keeps `__dirname` and `__filename`. Paths your own code computes from `import.meta.dirname` are the exception: bundling moves every module to the entry's location, so compute asset paths as the entry sees them.
</Callout>

### WebAssembly

A `.wasm` import is a binary asset like any other, so the import evaluates to the extracted file's path and the standard API reads it:

```ts
import wasm from "./model.wasm";

const { instance } = await WebAssembly.instantiate(readFileSync(wasm));
```

### Native addons

Native addons are the hard case for a bundler: a `.node` file is machine code, and `dlopen` loads it from a path on disk. The compiler follows an addon's static import and packs it into the executable:

```console
$ nub compile app.ts
Shipping 1 package unbundled, in its own installed layout:
  @napi-rs/nice — it declares 16 per-platform binary packages (napi-rs layout)

    output  app  29.6 MB  (node 28.3 MB · app 165 KB · launcher 1.1 MB)
   runtime  Node 26.8.1, embedded  (package.json#engines.node)
  platform  darwin-arm64
       app  extracted on first run  it resolves modules at run time
   elapsed  3.0s
```

Packages like `sharp` and `@napi-rs/nice` publish one binary package per platform — 25 of them, in sharp's case — and pick between them at load time with a `process.platform` check. Compiling replaces `process.platform` and `process.arch` with the target's values; the check becomes a constant, and only that platform's addon goes into the executable.

Cross-compiling with an addon means having that target's binary package on disk. When the resolved addon doesn't match the target, the build refuses:

```console
$ nub compile app.ts --platform linux-x64
Fetching the linux-x64 launcher …
error  this native addon is built for macOS, but the binary targets linux-x64: node_modules/@img/sharp-darwin-arm64/lib/sharp-darwin-arm64-0.35.4.node   # ❌
  A native addon is machine code for one platform, and a compiled binary loads it
  from a real file at run time — there is no later step that could translate it. The
  install has to put the target's own platform package on disk before you compile.
```

### Self-extraction

A compiled Nub binary has no virtual filesystem. On first run it unpacks its application files into a cache directory and runs from there, so `dlopen` and every `fs` call get ordinary files on an ordinary disk.

Extraction is established practice. Deno compiles to an in-memory virtual filesystem by default, but its docs recommend the [`--self-extracting` flag](https://docs.deno.com/runtime/reference/cli/compile/) for code that "needs real files on disk, such as native addons." Bun also extracts, [copying each embedded `.node` file to disk before loading it](https://bun.com/blog/bun-v1.2.13). [Claude Code ships as a Bun executable](https://x.com/jarredsumner/status/1943492457506697482), and its binary carries `audio-capture.node` and its siblings under a `bunfs/root/` prefix for exactly that. [opencode](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/script/build.ts) does the same.

A compiled [`sharp`](https://www.npmjs.com/package/sharp) app extracts this tree:

```
~/.cache/nub/compile-app/701130c84e2481d4
├── app.mjs                          ← your program, bundled
├── _nub_commonjs-C_xMe9k8.mjs
├── rolldown-runtime-CQMMWdV6.mjs
├── __nub_compile_bootstrap.cjs
└── node_modules
    ├── sharp                        ← installed layout, byte-for-byte
    ├── detect-libc
    ├── semver
    └── @img
        ├── sharp-darwin-arm64
        │   └── … sharp-darwin-arm64-0.35.4.node   ← the addon, a real file
        └── sharp-libvips-darwin-arm64
            └── … libvips-cpp.8.18.6.dylib
```

The embedded Node extracts separately, keyed by content, and binaries built against the same runtime share one extracted copy.

<Callout title="Locked-down deploys">
Warm the cache when the image is built:

```dockerfile
ENV XDG_CACHE_HOME=/opt/cache
RUN ./app --version || true   # the exit code is irrelevant; the extraction is the point
```

After that the binary writes nothing at run time, so a `readOnlyRootFilesystem` pod is fine. On Lambda the launcher uses the writable temp directory, so no warm-up step is needed.
</Callout>

### Dynamic imports and workers

Flattening a module graph into one file breaks three things that work under plain `node`: lazy dynamic imports, relative asset references, and workers.

A dynamic `import()` with a literal specifier stays lazy. It becomes its own chunk in the binary, loaded the first time that code path runs:

```console
$ ./app deploy
deployed!

$ ls ~/.cache/nub/compile-app/*/
__nub_compile_bootstrap.cjs
_nub_commonjs-Upy-LYoG.mjs
_nub_compile-preamble-Ydg2E6k8.mjs
deploy-DrKhUmBG.mjs
main.mjs
package.json
rolldown-runtime-CQMMWdV6.mjs
worker-330a94350ac07edfd25eb4bbe98201b91ce9087fe792dc5c1fa6d2ed215576ce-code.mjs
worker-330a94350ac07edfd25eb4bbe98201b91ce9087fe792dc5c1fa6d2ed215576ce.mjs
```

Chunks and assets land flat in one directory, which keeps a rewritten asset reference valid from every chunk. Workers compile the same way: a static `new Worker(new URL("./worker.ts", import.meta.url))` becomes a second bundled entry carrying the same runtime preamble as the program, and the thread sees the same `process.execPath` and the same globals.

### Unbundled packages

Some packages can't be bundled at all, because they read files from paths they build at run time. The compiler detects those, ships them in their installed layout — and then bundles each of their *dependencies* individually, emitting one chunk per package at the exact `node_modules` path the parent resolves:

```console
$ nub compile app.ts --smol --out app
Shipping 1 package unbundled, in its own installed layout:
  jsdom — it reads a data file from a path built at run time

    output  app  2.8 MB  (app 1.8 MB · launcher 986 KB)
   runtime  Node 26.0.0, not embedded  (package.json#engines.node; required
            exactly at runtime)
  platform  darwin-arm64
       app  extracted on first run  it resolves modules at run time
   elapsed  5.2s
```

For that jsdom program, npm writes 1,834 files to `node_modules` and the compiled binary extracts 1,006. The package that needed its own files keeps all 657 of them. The clean packages around it collapse: parse5 goes from 33 files to 2, whatwg-url from 19 to 3, mdn-data from 25 to 4. The launcher byte-verifies the whole extracted tree before every run, so each of those 828 files would otherwise be an integrity check on every start.

### Cross-compilation

Every target builds from every host; a single CI runner can produce the whole release:

```bash
# all eight, from one macOS arm64 laptop, ~40s each
nub compile cli.ts --platform darwin-arm64
nub compile cli.ts --platform darwin-x64
nub compile cli.ts --platform linux-x64
nub compile cli.ts --platform linux-arm64
nub compile cli.ts --platform linux-x64-musl
nub compile cli.ts --platform linux-arm64-musl
nub compile cli.ts --platform win32-x64
nub compile cli.ts --platform win32-arm64
```

Everything platform-dependent comes from the target: the embedded Node, the executable format, the `.exe` suffix, the values `process.platform` and `process.arch` fold to in the bundle. The list covers both musl targets and Windows on arm64. `deno compile` has five targets, with no musl and no Windows arm64.

Windows resources cross-compile too:

```console
# from the same macOS arm64 laptop
$ bun build --compile --target=bun-windows-x64 --windows-icon=icon.ico app.ts
error: Using --windows-icon is only available when compiling on Windows      # ❌

$ nub compile app.ts --platform win32-x64 --icon icon.ico                    # ✅
Stripped the embedded Node
note: cross-compiled for win32-x64 — payload verified statically; the run-it self-check needs a win32-x64 host

    output  app.exe  30.1 MB  (node 28.7 MB · app 67 KB · launcher 1.3 MB)
   runtime  Node 26.8.1, embedded  (package.json#engines.node)
  platform  win32-x64  cross-compiled from darwin-arm64
       app  extracted on first run  it extracts its embedded Node anyway
   elapsed  0.6s
```

The produced PE carries real `RT_ICON` and `RT_GROUP_ICON` resources, verified on Windows against an icon-less control. Nub decodes the `.ico` you supply and regenerates the standard set of sizes from it, so the source artwork should scale cleanly.

### Reproducible builds

Two compiles of an unchanged tree produce a byte-identical executable:

```console
$ nub compile cli.ts --smol --target lts --out a
$ nub compile cli.ts --smol --target lts --out b
$ shasum -a 256 a b
61ac2f0b0b27e355715c7d5bf9039f9a3c05c897bb88696bac56485e189a5ec4  a
61ac2f0b0b27e355715c7d5bf9039f9a3c05c897bb88696bac56485e189a5ec4  b
```

The checksum in your release notes is reproducible by anyone who checks out the tag.

### Flags

Everything above is the default behavior of one command. The flags:

```bash
nub compile cli.ts --out dist/cli               # name the output
nub compile cli.ts --platform linux-arm64-musl  # any of the eight targets
nub compile cli.ts --target 24.20.0             # pin the exact Node baked in

nub compile cli.ts --define BUILD='"2026-09-02"'  # compile-time constants
nub compile cli.ts --sourcemap                    # stack traces name your .ts lines
nub compile cli.ts --no-minify                    # readable output, for debugging it
nub compile cli.ts --tsconfig tsconfig.build.json

nub compile cli.ts --include data --exclude 'data/**/*.tmp'   # embed files no import names
nub compile cli.ts --unbundled pino               # ship a package in its installed layout
nub compile cli.ts --external playwright          # leave a package to the target machine
nub compile cli.ts --allow-dynamic-import         # computed import() for plugin systems

nub compile app.ts --icon icon.ico --platform win32-x64        # windows resources
nub compile app.ts --node-options "--max-old-space-size=4096"  # bake in runtime flags
```

Each of these has its own section in [the compile docs](/docs/compile).

## `--smol`

Most machines that run developer tools already have Node installed, so `--smol` skips the embedded runtime and finds one at startup instead. It checks Nub's own Node store, then version-manager installs, then `PATH`, and only provisions from nodejs.org when nothing on the machine satisfies the target.

### Version pinning

Nub does not infer a Node version for this shape. With no pin in the project, compiling stops:

```console
$ nub compile cli.ts --smol
error  no Node version could be inferred for this project.                    # ❌
  Pass --target <version> (e.g. --target 24, --target lts), or add a pin —
  a .node-version file, or package.json "engines": { "node": "…" }.
  (nub compile does not fall back to "latest": a compiled binary's Node
  version must be intentional and reproducible.)

$ nub compile cli.ts --smol --target lts                                      # ✅

    output  cli  990 KB  (app 70 KB · launcher 920 KB)
   runtime  Node lts, not embedded  (--target; floor enforced at runtime)
  platform  darwin-arm64
       app  run from the executable  nothing is written to disk
   elapsed  1.2s
```

A range lets the binary use any qualifying Node already on the machine instead of downloading one:

```bash
nub compile cli.ts --smol --target ">=22 <23"   # accept a host Node in the range
nub compile cli.ts --smol --target 26.0.0       # use or provision exactly 26.0.0
```

### `--install-message`

A first run that downloads Node shows a progress box; `--install-message` replaces the default text:

```bash
nub compile cli.ts --smol --target lts --install-message "Setting up acme (one time, ~10s)"
```

A machine with no Node and no network access exits with an error that points to the default build.

## Comparisons

Node apps were being packaged into executables long before SEA existed, and the tools divide on one question: whether to modify Node.

| Tool | Approach | Status |
| --- | --- | --- |
| [pkg](https://github.com/vercel/pkg) | A patched Node, with the app compiled to V8 bytecode and served from an in-memory `/snapshot/` filesystem. Native addons are extracted to a temp directory at run time. | Archived. Deprecated in January 2024, with 5.8.1 (March 2023) as the last release; the notice points at the forks and at Node SEA. The newest runtime it patched is Node 19.8.1. |
| [@yao-pkg/pkg](https://github.com/yao-pkg/pkg) | The maintained fork. Keeps the patched-Node mode and adds a mode on stock Node through SEA, with a virtual-filesystem library in place of the patches. | Active, on Node 26. [Its docs](https://yao-pkg.github.io/pkg/guide/sea-vs-standard) put the patched mode at 600–850 lines of patches per Node release, name that the project's primary maintenance cost, and set the goal of dropping it. |
| [nexe](https://github.com/nexe/nexe) | A patched Node with a zip of the app appended and read through an in-memory filesystem. Native addons ship alongside the binary. | Last stable release 3.3.7, June 2020. Prebuilt runtimes stop at Node 14; anything newer means building Node from source. |
| [caxa](https://github.com/leafac/caxa) | Stock Node and the project directory in a tarball behind a Go stub, extracted to a temp directory on first run. No patches, no cross-compilation. | Archived; last commit November 2023. |
| [boxednode](https://github.com/mongodb-js/boxednode) | Builds Node from source with a single JS file linked in as a builtin. No patches, no extraction. | Active, on Node 26. Takes one file, builds Node per target, no cross-compilation. |
| [Node SEA](https://nodejs.org/api/single-executable-applications.html) | Stock Node with an injected blob, via `node --build-sea` since 25.5.0. One bundled file; native addons are written out and loaded with `process.dlopen` by hand. | Stability 1.1. [postject](https://github.com/nodejs/postject), the injector the docs prescribed before 25.5, is at 1.0.0-alpha.6 from May 2023. |

Two things recur. Every project that patched Node has moved to stop: pkg's deprecation notice points at SEA, its fork documents the patch cost and is migrating to stock Node, and nexe's prebuilt runtimes froze at Node 14. And every virtual filesystem still writes native addons to disk, because `dlopen` takes a path: pkg under `os.tmpdir()`, its fork under `~/.cache/pkg-native`, and SEA through a code sample in its own docs. Nub starts from both facts. It runs stock Node and extracts everything, and the work went into making extraction cheap: a content-keyed cache directory instead of a temp directory, one shared copy of the runtime, a lock around first-run publication, and a byte check on every start.

caxa made the same choice in 2021, and its author's successor, [@radically-straightforward/package](https://www.npmjs.com/package/@radically-straightforward/package), dropped the single file and ships an archive with a shim instead. Its README lists the reasons: first-run extraction is extra, race-prone work; a temp directory can be cleaned while the app is running; and a payload appended past the end of an executable triggers antivirus software and complicates signing. The cache directory and the lock answer the first two. For the third, Nub's payload is not appended: it goes into a Mach-O section, an ELF note, or a PE resource, and the macOS binary is re-signed after injection.
