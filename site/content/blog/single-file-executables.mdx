Shipping a command-line tool written for Node means asking everyone who wants to run it to install Node first.

The workarounds all relocate that dependency somewhere else. An npm package needs a runtime on the machine. A container image needs a container runtime. Older tools like `pkg` and `nexe` stitched Node into the binary; both have been archived for years. Bun and Deno will compile you an executable today, but each one contains a full copy of its runtime — a program that prints one line comes out at 63 MB under Bun and 75 MB under Deno.

## How a single-file executable works

The recipe is the same in every tool: bundle the JavaScript entry into one file, then attach a runtime. Attaching is the fiddly half, because each operating system has its own executable container:

- **macOS** — the payload goes into a new Mach-O section. Adding a section invalidates the code signature, so Nub's injector re-signs the file afterward, ad-hoc, in pure Rust.
- **Linux** — an ELF note section. No signing involved.
- **Windows** — a PE resource, the same mechanism that stores an executable's icon. Authenticode signing is up to whoever distributes the binary.

Nub writes all three formats from any host. Cross-compilation depends on this, and there is a section on it below.

## Three runtimes, three answers

Deno went first, shipping [`deno compile`](https://deno.com/blog/v1.6) in December 2020. Bun followed with `bun build --compile` in [Bun 1.0](https://bun.sh/blog/bun-v1.0) in September 2023, then made it cross-compile in [1.1.5](https://bun.sh/blog/bun-v1.1.5). Both do the natural thing when you own the runtime: append the user's code to a copy of yourself. Hence the 63 MB hello world — the file is mostly runtime.

Node can't do that, because there is no single Node binary to copy — there are dozens, one per version per platform. [Single Executable Applications](https://nodejs.org/api/single-executable-applications.html) arrived in 19.7.0 and are still marked **Stability 1.1, "Active development"** today. The flow is deliberately low-level:

```bash
# SEA does not bundle. You bring an already-bundled script.
echo '{ "main": "bundled.js", "output": "sea-prep.blob" }' > sea-config.json
node --experimental-sea-config sea-config.json
cp "$(command -v node)" myapp                  # your own copy of the runtime
npx postject myapp NODE_SEA_BLOB sea-prep.blob \
  --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2
codesign --sign - myapp                        # injection invalidates the signature
```

Node 25.5.0 folded most of that into a built-in `node --build-sea sea-config.json`, a real improvement. One constraint remains that no polish can remove: `useCodeCache` and `useSnapshot`, the two options that buy startup time, are **ignored when you generate for another platform**. A V8 code cache only loads on the platform and version that produced it.

Nub is not a runtime either — `nub compile` builds on stock Node, the official binaries from nodejs.org.

## Compile it

The compiler takes an entry file — JavaScript or TypeScript — and produces one executable for one target platform:

```bash
nub compile cli.ts       # → ./cli
./cli                    # runs on a machine with no Node installed
```

TypeScript, JSX and non-erasable syntax are transpiled and bundled at compile time; the output carries no `node_modules` and needs no toolchain on the target machine. The Node it builds against comes from the project's existing pin — a `.node-version` file, or `engines.node` in `package.json`. An import the bundler can't resolve fails the build with the file and line.

The default shape embeds a full Node. It still comes in under half the size of the equivalents, because the embedded runtime is stripped and recompressed with zstd at level 19 before injection:

## Imports that aren't code

Programs import things that aren't modules, and the compiler resolves those at build time too:

```ts
import prompt from "./prompt.md";     // the text, as a string
import model from "./model.wasm";     // an absolute path to a real extracted file

// the ordinary ESM way to name a file beside your module also just works
const table = readFileSync(new URL("./table.bin", import.meta.url));
```

Text formats import as their contents; binary formats import as an absolute path, and every filesystem API works on that path. A literal `new URL(..., import.meta.url)` embeds the file it names, and the reference is rewritten to resolve at run time from any directory. The resolution is per module; a helper in a subdirectory keeps naming its own siblings. Files nothing imports — templates, migrations, a data directory — ship with `--include`.

A CommonJS dependency bundled into the output keeps `__dirname` and `__filename`. Do watch any path your own code computes from `import.meta.dirname`, though: bundling moves every module to the entry's location, so compute asset paths as the entry sees them.

## Native addons

Addons are where bundler-based tools historically gave up. A `.node` file is machine code, `dlopen` loads it, and `dlopen` wants a file on disk. The compiler follows an addon's static import and packs it into the executable:

```console
$ nub compile app.ts
Bundling app.ts …
Shipping 1 package unbundled, in its own installed layout:
  @napi-rs/nice — it declares 16 per-platform binary packages (napi-rs layout)
Stripped + ad-hoc re-signed the embedded Node
Compiled app — embed shape, Node 26.8.1, darwin-arm64, 29.6 MB
```

Packages like `sharp` and `@napi-rs/nice` publish one binary package per platform — 24 of them, in sharp's case — and pick between them at load time with a `process.platform` check. Compiling replaces `process.platform` and `process.arch` with the target's values; the check becomes a constant, and only that platform's addon goes into the executable.

Cross-compiling with an addon means having that target's binary package on disk. When the resolved addon doesn't match the target, the build refuses:

```console
$ nub compile app.ts --platform linux-x64
Fetching the linux-x64 launcher …
Bundling app.ts …
Error: this native addon is built for macOS, but the binary targets linux-x64: node_modules/@img/sharp-darwin-arm64/lib/sharp-darwin-arm64-0.35.4.node   # ❌
  A native addon is machine code for one platform, and a compiled binary loads it
  from a real file at run time — there is no later step that could translate it. The
  install has to put the target's own platform package on disk before you compile.
```

## Real files, not a virtual filesystem

Nub does not emulate a filesystem inside the binary. On first run, the executable unpacks its application files into a cache directory and runs from there, and `dlopen` and every filesystem API see ordinary files.

The big compiled CLIs already work this way. [Claude Code](https://x.com/jarredsumner/status/1943492457506697482) and [opencode](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/script/build.ts) both ship as Bun single-file executables, and Bun handles their embedded `.node` files by [copying each one out to disk before loading it](https://bun.com/blog/bun-v1.2.13). Deno defaults to an in-memory virtual filesystem and added a [`--self-extracting` flag](https://docs.deno.com/runtime/reference/cli/compile/) that its docs recommend for code that "needs real files on disk, such as native addons." Nub drops the virtual filesystem entirely and extracts everything.

Here is what a compiled [`sharp`](https://www.npmjs.com/package/sharp) app extracts:

```
~/.cache/nub/compile-app/701130c84e2481d4
├── app.mjs                          ← your program, bundled
├── _nub_commonjs-C_xMe9k8.mjs
├── rolldown-runtime-CQMMWdV6.mjs
├── __nub_compile_bootstrap.cjs
└── node_modules
    ├── sharp                        ← installed layout, byte-for-byte
    ├── detect-libc
    ├── semver
    └── @img
        ├── sharp-darwin-arm64
        │   └── … sharp-darwin-arm64-0.35.4.node   ← the addon, a real file
        └── sharp-libvips-darwin-arm64
            └── … libvips-cpp.8.18.6.dylib
```

The embedded Node extracts separately, keyed by content, and binaries built against the same runtime share one extracted copy. For a locked-down deploy, warm the cache when the image is built:

```dockerfile
ENV XDG_CACHE_HOME=/opt/cache
RUN ./app --version || true   # the exit code is irrelevant; the extraction is the point
```

After that the runtime hit writes nothing, which covers a read-only root filesystem on Kubernetes. On Lambda the launcher falls back to the writable temp directory on its own.

## What the bundler does with the hard parts

Flattening a module graph into one file breaks three things that work fine under `node`: lazy dynamic imports, relative asset references, and workers.

A dynamic `import()` with a literal specifier stays lazy. It becomes its own chunk in the binary, loaded the first time that code path runs:

```console
$ ./app deploy
deployed!

$ ls ~/.cache/nub/compile-app/*/
__nub_compile_bootstrap.cjs   deploy-DOT-CGau.mjs   rolldown-runtime-CQMMWdV6.mjs
_nub_commonjs-C_xMe9k8.mjs    main.mjs              worker-blob-url.cjs
```

Chunks and assets land flat in one directory, which keeps a rewritten asset reference valid from every chunk. Workers compile the same way: a static `new Worker(new URL("./worker.ts", import.meta.url))` becomes a second bundled entry carrying the same runtime preamble as the program, and the thread sees the same `process.execPath` and the same globals.

## Packages that ship as files don't drag their dependencies along

Some packages can't be bundled at all, because they read files from paths they build at run time. The compiler detects those, ships them in their installed layout — and then bundles each of their *dependencies* individually, emitting one chunk per package at the exact `node_modules` path the parent resolves:

```console
$ nub compile app.ts --smol --out app
Bundling app.ts …
Shipping 1 package unbundled, in its own installed layout:
  jsdom — it reads a data file from a path built at run time
Compiled app — smol shape, Node 26.0.0, darwin-arm64, 2.8 MB
```

For that jsdom program, npm writes 1,834 files to `node_modules` and the compiled binary extracts 1,006. The package that needed its own files keeps all 657 of them. The clean packages around it collapse: parse5 goes from 33 files to 2, whatwg-url from 19 to 3, mdn-data from 25 to 4. The launcher byte-verifies the whole extracted tree before every run, so those 828 missing files were integrity checks on every start of your program.

## The app is the small part

Here is a CLI built on `commander`, `chalk`, `ora` and `zod`:

```console
$ du -sh node_modules
8.6M	node_modules

$ nub compile cli.ts --smol --target lts --out cli
Compiled cli — smol shape, Node 24.20.0, darwin-arm64, 1.0 MB

$ ls -l cli
-rwxr-xr-x  1  1007138  cli        # 941,090 baseline + 66,048 bytes of app

$ ./cli --name nub
✔ hello, nub
```

Four dependencies and 8.6 MB of `node_modules` become 66,048 bytes of bundled, tree-shaken, minified app.

## The flag tour

Everything above is the default behavior of one command. The dials, when a build needs them:

```bash
nub compile cli.ts --out dist/cli               # name the output
nub compile cli.ts --platform linux-arm64-musl  # any of the eight targets
nub compile cli.ts --target 24.20.0             # pin the exact Node baked in

nub compile cli.ts --define BUILD='"2026-09-02"'  # compile-time constants
nub compile cli.ts --sourcemap                    # stack traces name your .ts lines
nub compile cli.ts --no-minify                    # readable output, for debugging it
nub compile cli.ts --tsconfig tsconfig.build.json

nub compile cli.ts --include data --exclude 'data/**/*.tmp'   # embed files no import names
nub compile cli.ts --unbundled pino               # ship a package in its installed layout
nub compile cli.ts --external playwright          # leave a package to the target machine
nub compile cli.ts --allow-dynamic-import         # computed import() for plugin systems

nub compile app.ts --icon icon.ico --platform win32-x64        # windows resources
nub compile app.ts --node-options "--max-old-space-size=4096"  # bake in runtime flags
```

Each of these has its own section in [the compile docs](/docs/compile).

## Eight targets, one machine

Every target builds from every host; a single CI runner can produce the whole release:

```bash
# all eight, from one macOS arm64 laptop, ~40s each
nub compile cli.ts --platform darwin-arm64
nub compile cli.ts --platform darwin-x64
nub compile cli.ts --platform linux-x64
nub compile cli.ts --platform linux-arm64
nub compile cli.ts --platform linux-x64-musl
nub compile cli.ts --platform linux-arm64-musl
nub compile cli.ts --platform win32-x64
nub compile cli.ts --platform win32-arm64
```

Everything platform-dependent comes from the target: the embedded Node, the executable format, the `.exe` suffix, the values `process.platform` and `process.arch` fold to in the bundle. The list covers both musl targets and Windows on arm64. `deno compile` has five targets, with no musl and no Windows arm64.

Windows resources cross-compile too:

```console
# from the same macOS arm64 laptop
$ bun build --compile --target=bun-windows-x64 --windows-icon=icon.ico app.ts
error: Using --windows-icon is only available when compiling on Windows      # ❌

$ nub compile app.ts --platform win32-x64 --icon icon.ico                    # ✅
Compiled app.exe — embed shape, Node 26.8.1, win32-x64, 30.0 MB
```

The produced PE carries real `RT_ICON` and `RT_GROUP_ICON` resources, verified on Windows against an icon-less control. Nub decodes the `.ico` you supply and regenerates the standard set of sizes from it, so supply artwork that survives being rescaled.

## The same source compiles to the same bytes

Two compiles of an unchanged tree produce a byte-identical executable:

```console
$ nub compile cli.ts --smol --target lts --out a
$ nub compile cli.ts --smol --target lts --out b
$ shasum -a 256 a b
61ac2f0b0b27e355715c7d5bf9039f9a3c05c897bb88696bac56485e189a5ec4  a
61ac2f0b0b27e355715c7d5bf9039f9a3c05c897bb88696bac56485e189a5ec4  b
```

The checksum in your release notes is reproducible by anyone who checks out the tag.

## `--smol`

Most machines that run developer tools already have a Node on them, and the ones that don't can fetch one in seconds. That makes 28 MB of embedded runtime a strange thing to put in every download. The `--smol` flag builds an executable with no runtime inside: at startup it looks for a usable Node in Nub's own store, then in version-manager installations, then on `PATH`, and provisions one from nodejs.org only when nothing on the machine satisfies the target.

The binary is 0.94 MB on disk and 504 KB gzipped. All eight targets attached to a GitHub release add up to less than half of one Bun binary.

The version contract stays explicit. In a project with no pin, the compiler refuses to guess:

```console
$ nub compile cli.ts --smol
Error: no Node version could be inferred for this project.                    # ❌
  Pass --target <version> (e.g. --target 24, --target lts), or add a pin —
  a .node-version file, or package.json "engines": { "node": "…" }.
  (nub compile does not fall back to "latest": a compiled binary's Node
  version must be intentional and reproducible.)

$ nub compile cli.ts --smol --target lts                                      # ✅
Compiled cli — smol shape, Node 24.20.0, darwin-arm64, 0.9 MB
```

A range lets the binary adopt a Node the machine already has:

```bash
nub compile cli.ts --smol --target ">=22 <23"   # accept a host Node in the range
nub compile cli.ts --smol --target 26.0.0       # use or provision exactly 26.0.0
```

When first run does have to download a Node, the terminal shows a progress box while it happens, and the message is settable:

```bash
nub compile cli.ts --smol --target lts --install-message "Setting up acme (one time, ~10s)"
```

One failure mode to know about: a machine with no Node and no network access exits with an error naming the default build, which embeds its Node and has no download to make.
