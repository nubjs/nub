Shipping a command-line tool written for Node means asking everyone who wants to run it to install Node first.

Every way around that trades the problem for a different one. A published npm package still needs a runtime on the machine. A container image needs a container runtime. `pkg` and `nexe` stitched Node into the binary years ago, and both are archived now. Bun and Deno answered by being the runtime themselves, which works, and means every executable they produce carries a complete runtime inside it.

That last cost is the one nobody has moved. A program that prints one line compiles to 63 MB under Bun and 75 MB under Deno, because in both cases the file is mostly runtime.

## Three runtimes, three answers

Deno went first, shipping [`deno compile`](https://deno.com/blog/v1.6) in December 2020. Bun followed with `bun build --compile` in [Bun 1.0](https://bun.sh/blog/bun-v1.0) in September 2023, and made it cross-compile in [1.1.5](https://bun.sh/blog/bun-v1.1.5). Both work the same way in outline, and it is the obvious way when you own the runtime: the executable is a copy of that runtime with your code appended.

Node cannot take that route, because there is no *the* Node binary — there are dozens, one per version per platform. [Single Executable Applications](https://nodejs.org/api/single-executable-applications.html) arrived in 19.7.0 and are still marked **Stability 1.1, "Active development"**. The flow is deliberately low-level, and every step is yours:

```bash
# SEA does not bundle. You bring an already-bundled script.
echo '{ "main": "bundled.js", "output": "sea-prep.blob" }' > sea-config.json
node --experimental-sea-config sea-config.json
cp "$(command -v node)" myapp                  # your own copy of the runtime
npx postject myapp NODE_SEA_BLOB sea-prep.blob \
  --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2
codesign --sign - myapp                        # injection invalidates the signature
```

Node 25.5.0 folded most of that into a built-in `node --build-sea sea-config.json`, which is a genuine improvement. The constraints underneath are the interesting part, because they are physics rather than polish: `useCodeCache` and `useSnapshot` — the two options that actually buy startup time — are **ignored when you generate for another platform**, since a V8 code cache loads only on the platform and version that produced it. The fastest-starting SEA is the one you built on the machine it runs on.

Nub is not a runtime either, so it inherits Node's constraint rather than Bun's freedom: it has to work with whatever Node exists. That turns out to be the advantage.

## Compile it

`nub compile` takes an entry file and produces one executable for one target platform:

```bash
nub compile cli.ts       # → ./cli
./cli                    # runs on a machine with no Node installed
```

TypeScript, JSX and non-erasable syntax are transpiled and bundled at compile time, so the output carries no `node_modules` and needs no toolchain on the machine it lands on. The Node it builds against comes from whatever the project already pins — a `.node-version` file, or `engines.node` in `package.json` — and an import the bundler cannot resolve fails the build, naming the file and line, rather than becoming a crash on someone else's machine with nothing to install.

## The runtime does not have to be in the file

Most machines that run a developer tool already have a Node on them, and the ones that don't can get one in a few seconds. `--smol` builds an executable that carries no runtime and settles the question on first run, looking in Nub's own Node store, then version-manager installations, then `PATH`, and provisioning from nodejs.org only when nothing on the machine satisfies the target.

In a project with no pin at all, Nub refuses to guess which Node that should be:

```console
$ nub compile cli.ts --smol
Error: no Node version could be inferred for this project.                    # ❌
  Pass --target <version> (e.g. --target 24, --target lts), or add a pin —
  a .node-version file, or package.json "engines": { "node": "…" }.
  (nub compile does not fall back to "latest": a compiled binary's Node
  version must be intentional and reproducible.)

$ nub compile cli.ts --smol --target lts                                      # ✅
Compiled cli — smol shape, Node 24.20.0, darwin-arm64, 0.9 MB
```

A range is accepted too, so a binary can adopt a Node the machine already has instead of downloading a second one:

```bash
nub compile cli.ts --smol --target ">=22 <23"   # accept a host Node in the range
nub compile cli.ts --smol --target 26.0.0       # use or provision exactly 26.0.0
```

The trade is explicit: a machine with no Node and no way to reach the network exits with an error pointing at the default build, which embeds an exact Node and has no such dependency.

The default shape is 29.5 MB on disk and barely moves under `gzip`, because its payload is already compressed with zstd at level 19 before it is ever written. It carries a stripped, compressed copy of a ~100 MB Node distribution, and compiled binaries built against the same runtime share one extracted copy on the target rather than each unpacking their own.

## The app is the small part

Once the runtime is out of the file, what remains is your code, and there is much less of it than the installed tree implies. Here is a CLI built on `commander`, `chalk`, `ora` and `zod`:

```console
$ du -sh node_modules
5.9M	node_modules

$ nub compile cli.ts --smol --target lts --out cli
Compiled cli — smol shape, Node 24.20.0, darwin-arm64, 1.0 MB

$ ls -l cli
-rwxr-xr-x  1  1007074  cli        # 941,026 baseline + 66,048 bytes of app

$ ./cli --name nub
✔ hello, nub
```

Four dependencies and 5.9 MB on disk come to 66 KB in the binary, because bundling, tree-shaking and minification run over the whole graph: a dependency costs what your code actually reaches inside it, not what npm wrote to disk.

## Eight targets, one machine

Every target builds from every host, which is what a release workflow wants from a single runner:

```bash
# all eight, from one macOS arm64 laptop, ~40s each
nub compile cli.ts --platform darwin-arm64
nub compile cli.ts --platform darwin-x64
nub compile cli.ts --platform linux-x64
nub compile cli.ts --platform linux-arm64
nub compile cli.ts --platform linux-x64-musl
nub compile cli.ts --platform linux-arm64-musl
nub compile cli.ts --platform win32-x64
nub compile cli.ts --platform win32-arm64
```

Everything platform-dependent follows the target rather than the build machine: the Node that gets embedded, the executable format, the `.exe` suffix, and the values `process.platform` and `process.arch` fold to in the bundle. That list includes both musl targets and Windows on arm64, which is where it goes furthest — `deno compile` offers five targets and covers neither.

Windows resources cross-compile too, which is where the difference is easiest to see:

```console
# from the same macOS arm64 laptop
$ bun build --compile --target=bun-windows-x64 --windows-icon=icon.ico app.ts
error: Using --windows-icon is only available when compiling on Windows      # ❌

$ nub compile app.ts --platform win32-x64 --icon icon.ico                    # ✅
Compiled app.exe — embed shape, Node 26.8.1, win32-x64, 30.0 MB
```

The produced PE carries real `RT_ICON` and `RT_GROUP_ICON` resources, verified on Windows against an icon-less control. Nub decodes the `.ico` you supply and regenerates the standard set of sizes from it, so supply artwork that survives being rescaled.

## The same source compiles to the same bytes

Two compiles of an unchanged tree produce a byte-identical executable:

```console
$ nub compile cli.ts --smol --target lts --out a
$ nub compile cli.ts --smol --target lts --out b
$ shasum -a 256 a b
17f1ceabf35fdc63467bf89a7cadaae97b33e39f3bf8d0d30db0360888e9cfdd  a
17f1ceabf35fdc63467bf89a7cadaae97b33e39f3bf8d0d30db0360888e9cfdd  b
```

That makes a published checksum meaningful and a build cache safe to trust.
