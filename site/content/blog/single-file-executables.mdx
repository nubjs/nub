Nub 0.9 adds `nub compile`, which bundles a TypeScript or JavaScript entrypoint into a single-file executable.

The executable is standalone and does not require Node to be installed on the target machine. You can configure the targeted Node version, platform, and architecture.

```bash
nub compile cli.ts --target 24.20.0 --platform linux-x64
```

Native addons, WebAssembly, and static assets need no configuration, because the executable extracts what it needs to disk.

## Some history

Deno shipped a similar feature as [`deno compile`](https://deno.com/blog/v1.6) in December 2020. Bun followed suit with `bun build --compile` in [Bun 1.0](https://bun.sh/blog/bun-v1.0), which undergirds Claude Code and OpenCode. 

These executables all work the same way: the code is bundled and stapled onto a copy of the runtime. The bundled payload lives inside the binary itself, in a platform-specific location:

1. **macOS** — a new Mach-O section. Adding one invalidates the code signature, so the file is re-signed afterward.
2. **Linux** — an ELF note section. No signing involved.
3. **Windows** — a PE resource, the same mechanism that stores an executable's icon.

Node's equivalent, [Single Executable Applications](https://nodejs.org/api/single-executable-applications.html) (SEA) landed as experimental in v18.16 in 2023. It's currently marked as **Stability 1.1** ("Active development") today. Despite some ergonomic improvements in Node 25, development has largely stalled due to the complexity of implementing a virtual filesystem and contributor bandwidth.

## Design

Nub implements the same idea on stock Node: nothing is patched, and a small Rust launcher drives it. The file holds three things:

1. **The launcher** — under a megabyte of Rust.
2. **A stock Node** from nodejs.org, stripped and compressed.
3. **The payload** — your application, bundled, plus anything it needs on disk.

### Bundling

Nub bundles the app with Rolldown, in-process. The augmentations Nub applies on the fly under `nub index.ts` happen at bundle time instead: `tsconfig.json#paths`, JSX, non-erasable TS syntax, YAML/TOML/JSONC imports, the `Temporal` and `Worker` polyfills, `import defer`.

The module graph flattens to one main chunk. A dynamic `import()` with a literal specifier stays lazy, as a chunk loaded the first time that code runs, and a worker becomes a second entry.

### Version pinning

The embedded Node is the version the project pins, in `.node-version` or `engines.node`, and `--target` overrides the pin. With no pin in the project, compiling stops:

```ansi
$ nub compile cli.ts
\e[35m\e[1mnub\e[22m\e[39m \e[2m0.8.3\e[22m \e[2m·\e[22m compiling cli.ts \e[2m→\e[22m \e[96mcli\e[39m
\e[31m\e[1merror\e[22m\e[39m  no Node version could be inferred for this project.                    # ❌
\e[2m  Pass --target <version> (e.g. --target 24, --target lts), or add a pin —\e[22m
\e[2m  a .node-version file, or package.json "engines": { "node": "…" }.\e[22m
\e[2m  (nub compile does not fall back to "latest": a compiled binary's Node\e[22m
\e[2m  version must be intentional and reproducible.)\e[22m

$ nub compile cli.ts --target lts                                             # ✅
\e[35m\e[1mnub\e[22m\e[39m \e[2m0.8.3\e[22m \e[2m·\e[22m compiling cli.ts \e[2m→\e[22m \e[96mcli\e[39m

    \e[2moutput\e[22m  \e[96mcli\e[39m  26.9 MB\e[2m  (node 25.7 MB · app 96 KB · launcher 851 KB · signature 208 KB)\e[22m
   \e[2mruntime\e[22m  Node 24.20.0, embedded\e[2m  (--target)\e[22m
  \e[2mplatform\e[22m  darwin-arm64
       \e[2mapp\e[22m  extracted on first run\e[2m  it extracts its embedded Node anyway\e[22m

\e[32m\e[1m✓\e[22m\e[39m compiled \e[96mcli\e[39m in \e[2m3.0s\e[22m
```

A range works too. The build embeds the newest release that satisfies it:

```bash
nub compile cli.ts --target 24            # the newest 24.x
nub compile cli.ts --target ">=22 <23"   # the newest 22.x
```

### Extraction

There is no virtual filesystem. Everything that isn't JavaScript unpacks on first run into a content-keyed cache directory: binary assets, WebAssembly, native addons, ejected packages.

The program runs from there, so `dlopen` and every `fs` call get ordinary files on an ordinary disk. A compiled [`sharp`](https://www.npmjs.com/package/sharp) app extracts to this:

```console
$ tree -L 2
.
├── index.mjs
└── node_modules
    ├── @img
    ├── detect-libc
    ├── semver
    └── sharp
```

The `sharp` package can't be bundled. It ships in its installed layout, along with the packages it requires at run time. The addon under `@img` is an ordinary file, and `dlopen` loads it the same way it does under plain `node`.

On every start, the launcher decodes the payload, verifies the extracted tree, and execs Node, so no wrapper process stays behind. The embedded Node extracts once per version, shared by every binary built against it.

### Assets

Imports of non-module files resolve at build time too:

```ts
import prompt from "./prompt.md";     // inlined into the bundle, as a string
import logo from "./logo.png";        // an absolute path to the extracted file

// a file named relative to the module resolves too
const table = readFileSync(new URL("./table.bin", import.meta.url));
```

Each kind of file has one rule.

- **A text file** (`.md`, `.txt`) is inlined into the bundle. The import evaluates to its contents as a string.
- **Any other file** — an image, a font, a database — ships inside the executable and is written out beside the bundle on first run. The import evaluates to that file's absolute path.
- **A literal `new URL(..., import.meta.url)`** embeds the file it names, and the reference is rewritten to resolve from the extracted directory.
- **Files nothing imports** — templates, migrations, a data directory — ship with `--include`.

A `.wasm` import follows the same rule. The import evaluates to the extracted file's path, and the standard API reads it:

```ts
import wasm from "./model.wasm";

const { instance } = await WebAssembly.instantiate(readFileSync(wasm));
```

<Callout title="Computed paths">
A CommonJS dependency bundled into the output keeps `__dirname` and `__filename`. Paths your own code computes from `import.meta.dirname` are the exception: bundling moves every module to the entry's location, so compute asset paths as the entry sees them.
</Callout>

### Workers

A worker is a second entrypoint, and Nub treats it as one. A `new Worker` whose argument is a literal `new URL(..., import.meta.url)` bundles the file it names as its own entry:

```ts
new Worker(new URL("./worker.ts", import.meta.url));

import { Worker as NodeWorker } from "node:worker_threads";
new NodeWorker(new URL("./worker.ts", import.meta.url));
```

The worker chunk carries the same preamble as the main chunk, so the thread sees the same globals and reports the same `process.execPath`. The `new URL(..., import.meta.url)` pattern is what makes this static. Pointed at a data file, it embeds the file. Pointed at a module, it embeds a bundled entry. Either way the reference is rewritten to resolve from wherever the executable extracted to, and a computed URL is left alone.

### Native addons

Native addons are the hard case for a bundler. A `.node` file is machine code, and `dlopen` loads it from a path on disk.

The compiler follows an addon's static import and packs the addon into the executable:

```ansi
$ nub compile index.ts
\e[35m\e[1mnub\e[22m\e[39m \e[2m0.8.3\e[22m \e[2m·\e[22m compiling index.ts \e[2m→\e[22m \e[96mindex\e[39m
Shipping 1 package unbundled, in its own installed layout:
  sharp — it declares 24 per-platform binary packages (napi-rs layout)

    \e[2moutput\e[22m  \e[96mindex\e[39m  36.5 MB\e[2m  (node 28.2 MB · app 7.2 MB · launcher 851 KB · signature 283 KB)\e[22m
   \e[2mruntime\e[22m  Node 26.7.0, embedded\e[2m  (package.json#engines.node)\e[22m
  \e[2mplatform\e[22m  darwin-arm64
       \e[2mapp\e[22m  extracted on first run\e[2m  it resolves modules at run time\e[22m

\e[32m\e[1m✓\e[22m\e[39m compiled \e[96mindex\e[39m in \e[2m7.7s\e[22m
```

Most addons ship one binary package per platform. The `sharp` package publishes 24 of them and picks one at load time with a `process.platform` check. Compiling replaces `process.platform` and `process.arch` with the target's values. The check becomes a constant, and only that platform's addon goes into the executable. In the extracted tree above, the addon is a real file with `libvips-cpp.8.18.6.dylib` beside it, and `dlopen` loads it the same way it does under plain `node`.

### Bundle ejection

Some packages break when bundled. They read files from their own `node_modules` directory at run time: a data file, a font, a WebAssembly module, a worker script named as a string.

The compiler detects those packages and ejects them from the bundle. An ejected package ships in its installed layout, and each of its *dependencies* still bundles to one chunk, at the exact `node_modules` path the package resolves:

```ansi
$ nub compile app.ts
\e[35m\e[1mnub\e[22m\e[39m \e[2m0.8.3\e[22m \e[2m·\e[22m compiling app.ts \e[2m→\e[22m \e[96mapp\e[39m
Shipping 1 package unbundled, in its own installed layout:
  jsdom — it reads a data file from a path built at run time

    \e[2moutput\e[22m  \e[96mapp\e[39m  30.4 MB\e[2m  (node 28.2 MB · app 1.0 MB · launcher 851 KB · signature 236 KB)\e[22m
   \e[2mruntime\e[22m  Node 26.7.0, embedded\e[2m  (package.json#engines.node)\e[22m
  \e[2mplatform\e[22m  darwin-arm64
       \e[2mapp\e[22m  extracted on first run\e[2m  it resolves modules at run time\e[22m

\e[32m\e[1m✓\e[22m\e[39m compiled \e[96mapp\e[39m in \e[2m5.7s\e[22m
```

Detection is a set of heuristics over the installed tree. A package is ejected when any of these holds:

- It declares a native build step.
- It depends on an addon resolver such as `bindings` or `node-gyp-build`.
- It publishes per-platform binary packages.
- It reads a non-code file from a path built off `__dirname`.

A few packages defeat every rule, because nothing in their manifest marks them. A pure-JS package that hands a worker a path built at run time is one. The compiler knows those by name: `jsdom`, `pdfkit`, `geoip-lite`, `sql.js`, `pino` and its transports, `keyv`, and `config` all compile and run out of the box. For any other package, `--unbundled <name>` ejects it by hand.

An ejected package ships verbatim, but its dependencies do not inherit that. Nub classifies each of them by the same rules, and a dependency that comes back clean is bundled: every module the ejected package requires from it becomes one chunk, written inside a stub of that dependency at the path Node resolves, with a `package.json` whose `exports` map points at the chunk. The ejected package itself is not rewritten, because it still finds the dependency where it always did.

| Package | Files installed | Files in the binary |
| --- | --- | --- |
| jsdom, ejected | 480 | 480 |
| parse5 | 64 | 2 |
| cssstyle | 116 | 2 |
| tough-cookie | 41 | 2 |
| entities, reached only through parse5 | 86 | 0, inlined into parse5's chunk |
| the whole tree | 1,513 | 537 |

The count matters at startup. The launcher byte-checks the whole extracted tree before every run, at roughly 20 µs a file, so a file that never ships is a file that is never checked.

## Performance

### Executable size

The default shape embeds a full Node, and the file is still a fifth the size of the `node` binary inside it. Three things make the difference:

- The embedded Node is stripped of its symbols.
- It is compressed, and decompressed once on first run.
- The app is bundled, tree-shaken, and minified before it goes in.

A stock `node` binary is 145 MB on darwin-arm64. Stripped and recompressed, it fits with your app in a 29 MB file:

A compiled binary starts a little slower than plain `node` on the same machine. The reason is structural: the artifact runs stock Node, then Nub's bootstrap, then the preload that installs the runtime augmentations, before it reaches the app. Node's own startup is the floor, and everything Nub adds sits on top of it.

<Callout title="Locked-down deploys">
Warm the cache when the image is built:

```dockerfile
ENV XDG_CACHE_HOME=/opt/cache
RUN ./app --version || true   # the exit code is irrelevant; the extraction is the point
```

After that the binary writes nothing at run time, so a `readOnlyRootFilesystem` pod is fine. Where the home directory isn't writable, as on Lambda, the launcher falls back to the temp directory, so no warm-up step is needed.
</Callout>

## Cross-compilation

Every target builds from every host; a single CI runner can produce the whole release:

```bash
# all eight, from one macOS arm64 laptop. The first build for a target downloads
# its Node and launcher; after that each one takes a few seconds.
nub compile cli.ts --platform darwin-arm64
nub compile cli.ts --platform darwin-x64
nub compile cli.ts --platform linux-x64
nub compile cli.ts --platform linux-arm64
nub compile cli.ts --platform linux-x64-musl
nub compile cli.ts --platform linux-arm64-musl
nub compile cli.ts --platform win32-x64
nub compile cli.ts --platform win32-arm64
```

Everything platform-dependent comes from the target. That means the embedded Node, the executable format, the `.exe` suffix, and the values `process.platform` and `process.arch` fold to in the bundle. The list covers both musl targets and Windows on arm64. A SEA cross-compiles only if you download the target's own `node` and turn off its code cache and snapshot. The `pkg` tool fetches its patched runtime per target.

Windows resources cross-compile too:

```ansi
# from the same macOS arm64 laptop
$ nub compile cli.ts --platform win32-x64 --icon icon.ico
\e[35m\e[1mnub\e[22m\e[39m \e[2m0.8.3\e[22m \e[2m·\e[22m compiling cli.ts \e[2m→\e[22m \e[96mcli.exe\e[39m
Stripped the embedded Node
note: cross-compiled for win32-x64 — payload verified statically; the run-it self-check needs a win32-x64 host

    \e[2moutput\e[22m  \e[96mcli.exe\e[39m  29.9 MB\e[2m  (node 28.6 MB · app 57 KB · launcher 1.2 MB)\e[22m
   \e[2mruntime\e[22m  Node 26.7.0, embedded\e[2m  (package.json#engines.node)\e[22m
  \e[2mplatform\e[22m  win32-x64\e[2m  cross-compiled from darwin-arm64\e[22m
       \e[2mapp\e[22m  extracted on first run\e[2m  it extracts its embedded Node anyway\e[22m

\e[32m\e[1m✓\e[22m\e[39m compiled \e[96mcli.exe\e[39m in \e[2m488ms\e[22m
```

The produced PE carries real `RT_ICON` and `RT_GROUP_ICON` resources, verified on Windows against an icon-less control. Nub decodes the `.ico` you supply and regenerates the standard set of sizes from it, so the source artwork should scale cleanly.

One thing does not come from the target: a native addon. Cross-compiling with an addon means having that target's binary package on disk. When the resolved addon doesn't match the target, the build refuses:

```ansi
$ nub compile index.ts --platform linux-x64
\e[35m\e[1mnub\e[22m\e[39m \e[2m0.8.3\e[22m \e[2m·\e[22m compiling index.ts \e[2m→\e[22m \e[96mindex\e[39m
\e[31m\e[1merror\e[22m\e[39m  this native addon is built for macOS, but the binary targets linux-x64:      # ❌
       node_modules/@img/sharp-darwin-arm64/lib/sharp-darwin-arm64-0.35.4.node
\e[2m  A native addon is machine code for one platform, and a compiled binary loads it\e[22m
\e[2m  from a real file at run time — there is no later step that could translate it. The\e[22m
\e[2m  install has to put the target's own platform package on disk before you compile.\e[22m

\e[2m  Select it with nub install --os <os> --cpu <cpu> --libc <libc>, then compile again.\e[22m
\e[2m  If no prebuilt exists for the target, install on the target platform itself — a\e[22m
\e[2m  container is the usual way — or drop --platform to build for this machine.\e[22m
```

Builds are reproducible. Two compiles of an unchanged tree produce a byte-identical executable, so anyone who checks out the tag can verify the checksum in your release notes.

## The `--smol` flag

The `--smol` flag can be used to dramatically reduce the resulting executable size. It works by omitting the Node runtime in favor of a launcher that installs the target version of Node when the executable is first run.

The file is 0.92 MB on disk, 489 KB gzipped. Warm start is 47 ms, within a few milliseconds of the default shape in the startup chart.

At startup the executable looks for a Node that satisfies the target: Nub's own Node store, then version-manager installs, then `PATH`. When the machine has none, it provisions one from nodejs.org into Nub's cache, where every other `--smol` executable on the machine finds it. A range lets the binary use any qualifying Node already on the machine instead of downloading one:

```bash
nub compile cli.ts --smol --target ">=22 <23"   # accept a host Node in the range
nub compile cli.ts --smol --target 26.0.0       # use or provision exactly 26.0.0
```

## Flags

Everything above is the default behavior. The everyday flags, in one invocation:

```bash
nub compile app.ts \
  --out dist/app \
  --platform win32-x64 \
  --target 24.20.0 \
  --smol \
  --define BUILD='"2026-09-02"' \
  --sourcemap \
  --no-minify \
  --tsconfig tsconfig.build.json \
  --include data --exclude 'data/**/*.tmp' \
  --unbundled pino \
  --external playwright \
  --allow-dynamic-import \
  --icon icon.ico \
  --metadata ProductName=Acme \
  --hide-console \
  --node-options "--max-old-space-size=4096"
```

| Flag | What it does |
| --- | --- |
| `--out` | Names the output file. |
| `--platform` | Targets any of the eight platforms. |
| `--target` | Pins the exact Node version. |
| `--smol` | Leaves Node out of the file. |
| `--define` | Sets compile-time constants. |
| `--sourcemap` | Makes stack traces name your `.ts` lines. |
| `--no-minify` | Keeps the output readable, for debugging it. |
| `--tsconfig` | Picks the TypeScript config to compile with. |
| `--include`, `--exclude` | Embed files no import names. |
| `--unbundled` | Ships a package in its installed layout. |
| `--external` | Leaves a package to the target machine. |
| `--allow-dynamic-import` | Keeps computed `import()` calls, for plugin systems. |
| `--icon` | Sets the Windows icon. |
| `--metadata` | Fills the Details tab of a Windows executable. |
| `--hide-console` | Opens no console window on Windows. |
| `--node-options` | Bakes runtime flags into the binary. |

Each of these has its own section in [the compile docs](/docs/compile), along with the advanced set: `--alias`, `--conditions`, `--loader`, `--drop`, and the rest.

## Comparisons

Node apps were being packaged into executables long before Node SEA existed. The tools divide on one question: whether to modify Node.

| Tool | Node | Status | How the app ships |
| --- | --- | --- | --- |
| [Node SEA](https://nodejs.org/api/single-executable-applications.html) | stock | Stability 1.1 | A blob injected into the `node` binary with `node --build-sea`. One bundled file. Native addons are written out and loaded with `process.dlopen` by hand. |
| [pkg](https://github.com/vercel/pkg) | patched | Deprecated Jan 2024 | Compiled to V8 bytecode and served from an in-memory `/snapshot/` filesystem. Native addons are extracted to a temp directory at run time. The last release, 5.8.1, patches Node 19.8.1. |
| [@yao-pkg/pkg](https://github.com/yao-pkg/pkg) | patched or stock | Active on Node 26 | The maintained fork. Same snapshot filesystem, plus a stock-Node mode built on SEA and a virtual-filesystem library. [Its docs](https://yao-pkg.github.io/pkg/guide/sea-vs-standard) put the patched mode at 600–850 lines of patches per Node release and set the goal of dropping it. |
| [nexe](https://github.com/nexe/nexe) | patched | Last release Jun 2020 | A zip of the app appended to the binary, read through an in-memory filesystem. Native addons ship beside the binary. Prebuilt runtimes stop at Node 14. |
| [caxa](https://github.com/leafac/caxa) | stock | Archived Nov 2023 | The project directory in a tarball behind a Go stub, extracted to a temp directory on first run. No cross-compilation. |
| [boxednode](https://github.com/mongodb-js/boxednode) | own build | Active on Node 26 | A single JS file linked into Node as a builtin. No extraction, no cross-compilation. |
| [Bun](https://bun.sh/docs/bundler/executables) | not Node | Active | A copy of the `bun` binary with the bundle appended. Each embedded `.node` file is [copied to disk](https://bun.com/blog/bun-v1.2.13) before it loads. |
| [Deno](https://docs.deno.com/runtime/reference/cli/compile/) | not Node | Active | A copy of the `deno` binary with the module graph appended. An opt-in `--self-extracting` mode unpacks to disk for native addons. |

The caxa project made the same extraction choice in 2021. Its author's successor, [@radically-straightforward/package](https://www.npmjs.com/package/@radically-straightforward/package), dropped the single file and ships an archive with a shim instead. Its README lists three reasons:

- **First-run extraction is extra, race-prone work.** Nub's cache directory and publication lock answer this.
- **A temp directory can be cleaned while the app is running.** The content-keyed cache directory answers this too.
- **A payload appended past the end of an executable triggers antivirus software and complicates signing.** Nub's payload is not appended: it goes into a Mach-O section, an ELF note, or a PE resource, and the macOS binary is re-signed after injection.

## Compiling OpenCode

[OpenCode](https://github.com/anomalyco/opencode) is a coding agent with a terminal UI, and upstream ships it as a Bun executable. [NopenCode](https://github.com/nubjs/nopencode/tree/nub-compile), our fork, builds the same app with `nub compile`, on stock Node.

It is the hardest shape a packager meets. The TUI is Solid on top of OpenTUI, which loads a native library, tree-sitter grammars, and a parser worker through paths it computes at run time. Bun's executable serves all of that from an in-memory filesystem. Nub extracts it to disk instead, and because two of those packages ship in their installed layout, the extracted tree comes to over five thousand files. The build script, [`build-nub.mjs`](https://github.com/nubjs/nopencode/blob/nub-compile/packages/opencode/script/build-nub.mjs), maps each `Bun.build` option onto a flag. In outline:

```bash
nub compile src/index.ts --target 26 \
  --external node-gyp \
  --alias solid-js=<the client build, not the SSR one> \
  --unbundled @opentui/core \
  --unbundled web-tree-sitter \
  --include otui-assets \
  --allow-dynamic-import \
  --define OPENCODE_VERSION="'0.0.0-nub'" \
  --define-file OPENCODE_MODELS_DEV=models.json
```

The diff against upstream is 26 files, and most of it is build scripts and notes. What the app itself needed:

- **A `Bun` global, polyfilled for simplicity.** The shipped graph calls five of its members, `stringWidth`, `file`, `write`, `stdin`, and `hash`, and each maps onto a Node builtin.
- **Node's own modules where it used Bun's.** The Zed integration moved from `bun:sqlite` to `node:sqlite`, and the Windows console guard moved from `bun:ffi` to `node:ffi`.
- **No top-level `await`.** Bundled async modules in an import cycle await each other, and the program hangs before `main` with no error. Thirty-eight awaited dynamic imports became static imports, seven awaited `mkdir` calls became `mkdirSync`, and two awaits inside OpenTUI now resolve lazily.
- **A staged asset root.** OpenTUI's thirteen run-time-resolved files go into one directory, embedded with `--include`, and an environment variable points OpenTUI at it before it loads.

Everything else OpenCode already had. Its OpenTUI packages and its sqlite, pty, and `fff` bindings all ship a `node` export condition, and selecting it is the whole fix for them.

The result runs on darwin-arm64, linux-x64, linux-arm64, linux-arm64-musl, and win32-x64, all cross-compiled from one Mac, TUI included. Nine command surfaces, from `--version` to `providers list`, print byte for byte what the Bun build prints. In the port's measurements the default build is 45 MB on disk, and `--smol` is 18 MB and provisions its own Node on a machine that has none. Bun starts it faster, because Bun is the runtime and Nub's launcher is not. [The port notes](https://github.com/nubjs/nopencode/blob/nub-compile/NUB-PORT.md) carry the measurements and everything the port ran into.
