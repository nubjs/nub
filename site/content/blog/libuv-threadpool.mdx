Nub 0.10 sizes libuv's threadpool to the cores of the machine and runs the threads beyond Node's four at a lower priority.

Node sends async `fs`, `dns.lookup`, `zlib` and `crypto` calls to a pool of four threads. Native addons such as `bcrypt` and `sharp` queue on the same four. The pool is four threads on a laptop and four on a 64-core server.

Routes that use the pool lightly are unchanged. Five interleaved rounds of a 270 KB file read, a `stat` and a 55 KB gzip on the 16-vCPU box read within noise of plain Node. A burst of 400 `dns.lookup` calls finished in 59 ms instead of 84 ms.

## The threadpool

libuv is Node's I/O library. It keeps a pool of worker threads for the calls that block. Node's own [`UV_THREADPOOL_SIZE`](https://nodejs.org/api/cli.html#uv_threadpool_sizesize) environment variable sets the size. libuv reads it once, the first time the pool is used, so only the environment can change it. The usual fix is a line in a Dockerfile:

```bash
UV_THREADPOOL_SIZE=16 node server.js
```

Most deployments never set it. Nub sets it when it starts Node, on every launcher: the direct file run, `nub run`, `nubx`, `nub watch` and lifecycle scripts. The value is the larger of four and the cores available to the process. A container gets its cgroup quota, not the host's core count. On four cores or fewer, nothing changes.

## Node's own attempt

In January, a member of Node's performance team proposed the same default for Node itself, in [nodejs/node#61533](https://github.com/nodejs/node/pull/61533). The pull request collected eight approvals over six months.

A pool sized to the host takes every core it can see. On a box shared with other processes, that is a regression for them. The thread also [reports](https://github.com/nodejs/node/pull/61533#issuecomment-3861852577) a file-read benchmark at −15% with sixteen threads on 16 vCPU. On Windows, each pool thread [commits about 8 MB of stack](https://github.com/nodejs/node/issues/57911). The objection is not to the size. It is to taking the cores unconditionally.

## The mitigations

The size is the one Node's team proposed. Three things around it answer the objections.

### Extra threads run at a lower priority

On Linux, the threads beyond Node's four run at [nice](https://man7.org/linux/man-pages/man7/sched.7.html) 10. Node's four keep their normal priority. A nice 10 thread has about a tenth of the scheduler weight of a normal one. On an idle box it runs at full speed. Under contention it yields most of the CPU to the other work on the machine. Chromium [uses the same level](https://chromium.googlesource.com/chromium/src/+/main/base/threading/platform_thread_linux.cc) for its background threads.

The same twelve processes beside a sixteen-thread pool at normal priority lose 7.5% of their throughput. At nice 10 they lose about 1%, and the idle number is unchanged.

### Children keep Node's default

A `cluster` worker, a PM2 fork or any `child_process` spawn starts with Node's four threads. Nub removes its own value from `process.env` once the pool exists, so children do not inherit it. Eight workers with sixteen threads each is the oversubscription raised upstream. A child that runs through `nub` is sized again. A value you set yourself, in the shell or in an env file, inherits as it does under Node.

### Windows stops at eight

Each pool thread commits its full stack up front on Windows. The pool is capped at eight there instead of sized to the machine.

## Opting out

An explicit `UV_THREADPOOL_SIZE` is used as is. `nub --node` and `NODE_COMPAT=1` leave the pool at Node's default, with the rest of what Nub adds.

The change is in [nubjs/nub#919](https://github.com/nubjs/nub/pull/919) and ships in Nub 0.10. The docs page is [Threadpool](/docs/runtime/threadpool).
