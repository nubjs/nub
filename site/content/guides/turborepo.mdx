Turborepo and Nub solve different problems. Turborepo schedules tasks across your packages and caches their results. Nub runs underneath: it provisions the Node version your project pins and augments the Node each task spawns, so TypeScript and `.env` files work without a build step. You don't reconfigure Turborepo to adopt Nub; you run Turborepo *through* Nub.

## The short version

- Run Turborepo under Nub: `nub run <script>` where the script is `turbo run …`, or `nubx turbo run …`.
- Install with the package manager your `packageManager` field names, because that is the one Turborepo runs each task with.
- To install with Nub instead, switch the repo to Nub with `nub pm use nub`. Turborepo 2.10.3 and later then run every task with `nub run`.

## Installs: keep your package manager, or switch to Nub

For every package that defines a task, Turborepo spawns the repo's package manager with `run <task>`. It picks that manager from the `packageManager` field in the root `package.json`, together with the lockfile: in a pnpm repo, every task is `pnpm run build`.

That manager expects the `node_modules` tree it built itself. `nub install` reads and writes the same lockfile, but it lays `node_modules` out its own way (packages live under `node_modules/.store`, where pnpm keeps them in `node_modules/.pnpm`), and pnpm can refuse to run scripts against a tree it didn't build. So pick one of these:

**Keep your package manager.** Install with it as before, and run Turborepo under Nub:

```bash
pnpm install
nub run build         # root script: "turbo run build"
```

**Switch the repo to Nub.** Turborepo 2.10.3 and later detect Nub from the pin `nub pm use nub` writes, and run each task as `nub run <task>`:

```bash
nub pm use nub   # moves pnpm-workspace.yaml config, renames the lockfile
nub install
nub run build
```

`nub pm use nub` moves `pnpm-workspace.yaml`'s settings into `package.json`, renames the lockfile to `nub.lock`, and pins Nub in `devEngines.packageManager`.

Switching is a project-wide decision: afterwards real pnpm refuses to run in the repo, and `nub pm use pnpm` reverses it. See [`nub pm use`](/docs/pm#nub-pm-use).

## How Nub reaches into every task

Turborepo doesn't execute each package's script body itself. It spawns the package manager, which runs the script with `node_modules/.bin` on the path. That subprocess inherits its environment from Turborepo, which inherits it from whatever launched Turborepo.

That inheritance is the seam Nub uses. Run Turborepo under Nub and the augmentation environment (a `NODE_OPTIONS` preload and a `node` shim on the path) flows down the whole tree: Nub launches Turborepo, Turborepo spawns the package manager, the package manager runs your script, and the `node` your script invokes is Nub's augmented Node.

The result: a package whose build script is plain `node ./build.ts` runs TypeScript directly, with no compile step, and loads that package's `.env`, inside a Turborepo task, with no per-package configuration.

```jsonc
// packages/lib/package.json
{
  "name": "@acme/lib",
  "scripts": { "build": "node ./build.ts" }
}
```

```jsonc
// turbo.json
{
  "tasks": { "build": {} }
}
```

```bash
nub run build         # root script: "turbo run build"
```

```
@acme/lib:build: cache miss, executing
@acme/lib:build: [lib] built ok
 Tasks:    1 successful, 1 total
```

What matters is that **Turborepo runs under Nub**. Launch it with `nub run <script>` (where the script's command is `turbo run …`) or with `nubx turbo run …`. If you invoke the `turbo` binary directly from a plain shell, the tasks run on whatever Node is on your path with no augmentation, and a `.ts` entry fails to parse.

You don't need to rewrite your package scripts to say `nub`. A script of `node ./build.ts` is enough.

## Choosing the Node version

Nub provisions and uses the Node version your project pins, so every task across the monorepo runs on the same version without nvm or Corepack. Pin it the way the rest of the ecosystem does: an `.nvmrc`, a `devEngines.runtime` entry, or `nub node pin`.

This also sidesteps a common monorepo failure: a package manager refusing to run under an old Node it found on the path. Because Nub's `node` shim comes first on the path, the package manager Turborepo spawns runs on the pinned Node rather than on a stale system one.

## What to watch for

- **Turborepo's cache is environment-aware.** Turborepo hashes a task's inputs, including declared environment variables, to decide cache hits. Nub's augmentation rides in `NODE_OPTIONS`, which Turborepo passes through to the task but doesn't fold into the cache hash unless you declare it, so adopting Nub doesn't invalidate your cache.
- **`.env` loading is Nub's, at the task level.** Each task gets the `.env` for the package it runs in. This is independent of Turborepo's `env`/`globalEnv` declarations, which control cache hashing rather than loading. If a value must affect the cache, it still belongs in `turbo.json`.
- **Run Turborepo under Nub, every time.** A bare `turbo run` from a shell that hasn't gone through Nub carries no augmentation. Keeping the entry point as a `nub run` script (or `nubx turbo`) makes this automatic for everyone on the project and in CI.
